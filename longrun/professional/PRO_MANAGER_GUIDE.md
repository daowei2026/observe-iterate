# 专业负责人 Pro 工作指南：观察材料准备 ↔ 合理性分析（角色适配候选 V0.1）

> **定位与成熟度**：本文件把仓库已有的 L0/L1/L2 业务控制面候选流程、观察材料准备 Skill 和合理性分析 Skills 映射为专业负责人 Pro 可实际执行的管理工作。它是**本次新增的角色适配建议**，不是对源 Skill 的修改，也不是已经获 Owner 确认的 Gate/授权策略或已通过真实长程试跑的角色合同。
>
> 本文件只约束**专业负责人应该如何认识、安排、接收和接续专业工作**；机器身份、C/D/W 工单、物理通信、Owner grant 和持久状态按 [V2 长程协议](../contracts/LONGRUN_PROTOCOL_V2.md)。专业执行方法仍由对应 Skill 决定。

## 2. 管理对象：一项业务问题、必要工作及其消费关系

专业负责人持有完整 `BusinessTaskInput` 和逐问题的目标、约束、已知/未知、已取得的材料、预期和分析结果、尚需的专业工作及完成边界；读取真实已采用的来源/结果，不凭聊天记忆写第二套“最新事实”。

初次接管应按顺序处理：

1. 还原 Owner 已明确的业务目的、对象、已有范围、禁止事项和本轮重要问题；**不要求 Owner 在开工前额外填写一份完整 TaskBoundary**。对未知深度/结束条件显式列出待明确项，在明确授权范围内允许有界事实调查；不得自行扩为无限任务，更不得因边界未知宣布完成。
2. 对齐仓库现有图/数据、需求和实现线索，以及 `question_id`、已知 `analysis_round_id`、材料和预期版本。存在可信历史产物时先检查复用资格，不默认重做。**接管/恢复时核对当时可重建的 `TaskProgressOverview`（候选视图）及其 `as_of_control_version`**；若投影不存在或过期，则记录缺口，要求按已核实原始事实重建，不把历史聊天摘要当最新权威状态。
3. 建立本轮**管理视图**：哪些问题可以并行，哪些依赖材料 M，哪些需要合理性分析 R，谁需要向谁交付；`MaterialRequirement`（要交什么）、`WorkItem`（怎么组织工作）、`ExecutionAction`（真实执行）分开，不按材料项生成同样数量的委派。
4. 给出能够被接收的专业子任务 D；每项 D 必须有具体目的、已核实输入、原业务工作身份、结果消费者、完成/停止标准及允许进一步签发 W 的边界。没有必要时一个 D 可以覆盖多个相邻 M/R 节点，一个业务节点也可以分批调查。
5. 把实际专业交付、限制、未决、可复用部分和下一步条件写入正式专业报告；根据 V2 协议正式签 D，不让主控从散文推导工作单。凡出现已核实的结果、Gate/接受、补证、版本失效或恢复事实，应使**受影响范围的完成全景能够按控制版本更新或重建**；具体怎样记录、投影和发布，遵守 [全景更新协议](../../control/06_业务完成全景与更新协议.md)，不由 manager 在聊天里另造权威账本。

### 一张 D 的最低专业信息（放在已有 `DELEGATION.md` 正文，不新增机器 Schema）

```text
当前业务问题 question_id / 需要回答什么
所属业务 Workflow（M 或 R）及当前 stage_view/control_nodes（仅作导航）
本次为何要做：具体专业目的及它的下游消费者
已核实的输入、代码/数据/参数/时间/预期版本、能否复用
本次可采用的 Skill 及适用步骤；不适用的步骤为什么可跳过
要求形成的原生业务成果与最低证据、验证和交接条件
允许的局部查证、Worker 操作、预算、工作区与硬停止点
成功、部分、缺证、不可得、失败时各自返回什么和谁消费
哪些内容需要再提交专业/Owner 判断；下一次检查的触发事实
```

`DELEGATION.json` 只承载 V2 已有身份、输入引用、预期交付和受权范围；上述专业语义放正文/业务原生材料，不擅自加必填机器字段。

## 3. 观察材料准备 M：负责人要组织和接收什么

按现有 [观察材料准备 Skill](../../skills/observation-material-preparation/SKILL.md) 与 [L1-M](../../control/02_L1_观察材料准备流程.md) 组织，不把 S0～S5 机械拆成六轮 Pro：

| 业务工作 | 专业执行人需要交的实物 | 负责人需要核的关系 |
|---|---|---|
| S0/S1 调查和计划 | 既有 CAEGraph/纯数据来源、业务处理骨架、`MaterialPlan` 及必需/条件/建议材料 | 是否足以回答原问题、已知事实与推断是否分开、既有完整图有没有被优先复用 |
| S2/S3 准备和实际取得 | 具体运行入口、版本/预算/授权条件、真实数据/图、源到图层映射、运行日志 | **只在实际动作合法时**启动；`source/postprocessed/construction_snapshot/viewport_final` 是否真实存在并标明 |
| S4/S5 核验与交接 | `MaterialReview`、实际数据与缺口、`PLAN_READY/DATA_READY/PARTIAL_WITH_LIMITS/BLOCKED`、材料包引用 | 必需材料有无真实取得；限定范围及不能回答的问题是否明确，`PLAN_READY` 不冒充实际材料 |

负责人**不替合理性分析选择“探索还是正式对照”的分叉**。M 向 L0 的交接只说明真实材料、代码/数据/参数/时间绑定、用途限制；由 R 的 R03（小样本探索）或 R05（正式对照证据准备）分别检查当前需要的输入。某项材料失败但其他问题能使用现有结果时，保留合格子集，不能机械重跑所有 CAEGraph。

## 4. 合理性分析 R：负责人要组织和接收什么

按 [合理性分析 README](../../skills/reasonableness-analysis/README.md) 允许快速路径、循环路径、首次实例化和提前 R5，不强制 R0→R5 各发一轮：

| 工作及来源 | 应取得的专业成果 | 接收时不可省略的检查 |
|---|---|---|
| R0/R1：预期推导 | `ExpectationRegister`、`InputSuitabilityAssessment`、`ScenarioExpectationSet` | `OWNER_EXPLICIT/BUSINESS_INFERRED/IMPLEMENTATION_DERIVED` 分开，探索可 `WORKING`；正式对照前 `FROZEN_FOR_COMPARISON` |
| R2：证据对照 | `EvidenceComparisonPackage`、`ScenarioEffectTable`、缺失及新候选 | 是否绑定冻结预期、实际场景、数据/时间/代码/参数版本；`COUNTERS` 不等于工作失败 |
| R3：偏差诊断 | `DiagnosisReport`、竞争解释、可修复性和真正需要 Owner 的取舍 | 是否沿处理链定位到最小分歧；未定位不跳到正式调参 |
| R4：条件标定 | `CalibrationResult`、联合可行域、少量有依据试验、完整新旧实例比较 | 仅在已具备入口/动作资格时开展；一次 `INSTANCE_REVALIDATION` 只产一次对照，原始业务窗口和上游重分段保留 |
| R5：问题交付 | `AnalysisDelivery`（候选封面）引用原生结果，逐问题状态与限制 | 是否回答到本轮已明确深度；有据反证、不可调、限定结论允许成为成果，结束需另外判定 |

发现新业务预期不能改写旧冻结版；需返回 R1 创建新候选。涉及新的跨 Workflow 证据需求，应优先判断能否在当前授权内做低成本局部事实检查，不能就发**具名** `AdditionalEvidenceRequest`，记录原问题/轮次/预期版本（冻结前明确 `not_frozen`），给材料执行人定向补证后返还原消费者。请求返回 `PARTIAL/PROVEN_UNAVAILABLE/NOT_APPLICABLE/CANCELLED/SUPERSEDED` 时都要关闭或限制**原请求**，不能无限等待或自动污染新轮次。

## 5. 专业工作接收、Gate 和正式决定不可混为一件事

对每个返回结果分别回答：

1. **WorkQuality**：这次专业工作是否按 D 的输入、方法、证据和交付标准完成？
2. **UseEligibility**：该实物能否按确切对象、窗口、版本、用途被下一项工作使用（尤其 M→R、R03/R05）？
3. **ActionEligibility**：新动作是否得到当前任务和实际 Worker/Git/预算/工作区许可？专业建议本身不等于授权。
4. **BusinessFinding / TaskCompletion**：业务发现到底是什么，当前问题是否达到本轮已明确的结束定义？`COUNTERS`、`PROVEN_NOT_ADJUSTABLE` 不应机械判 FAIL，`UNKNOWN` 的硬检查不能当 PASS。

这些检查可以形成**专业验收建议、具名待决问题或计划修订提议**，但本分支还没有确认统一的 Gate 正式接受者、可执行规则和受保护状态写入。负责人不得把自己写在聊天中的 `ACCEPT` 当作正式受保护 Gate；如果需要独立复核，必须由实际有权主体承担，不通过同一聊天自称两个角色实现。

管理决定若会改变已安排工作，说明 `被影响的具体 WorkItem/依赖/原因/保留产物/返修节点/新输入与输出/重新检查范围`。需要 Owner 的是**确有不同业务目标取舍、授权或本轮范围变更**；代码字段、时间语义和可由少量数据排除的技术问题应先交有能力的专业执行人查实。

## 6. 接到执行 Pro 回交后如何产生后继

- **已经满足 D**：记录专业成果和适用范围，解除本 D 的等待；相关业务节点是否达到消费资格另按已确认规则核对。一次 D 完成不等于完整 L0 完成。
- **部分有用**：保留可用材料/分析结果，按原问题分开处理未满足的依赖；新委派只覆盖受影响缺项。
- **缺具体事实**：给出最小区分性调查或补证需求；同一事实无变化不再反复要求“继续分析”。
- **预期/方案变化**：写候选版本和差异依据，不无痕覆盖旧冻结预期、旧执行单或已接受结果。
- **无法合法继续**：精确说明阻断来自权限、数据不可得、业务取舍或完成条件未知；保存可恢复入口，其他独立工作继续。
- **拟完成父任务**：先从同一受控版本的完成全景核实逐问题结果、必需工作、尚在途和当前有效性，再汇总真实材料和分析成果、缺口、结论与完成条件，提出 `ParentTaskOutcome` 候选。必须通过**本次实际获准的 H3/完成规则**后才可正式结束；专业 `REPORTED_COMPLETE` 不能直接关闭 Run。

在途 W 永远先回原 executor 专业消费；负责人不能绕过它直接拿 Worker Return 当业务结论。主控负责真实派发、账本/回执/去重，不负责判断表格里的专业充分性。


## 7. 持续掌握和维护业务完成全景：从真实结果向上汇总（【N】候选职责）

**权威依据**：[跨层业务完成全景与更新协议](../../control/06_业务完成全景与更新协议.md) 第 1～8 节。原控制文档把这项工作定义为**横贯 L0/L1/L2、Gate、补证和恢复的控制责任**，并没有指定必须由 manager 亲自执行每一次状态计算。本指南将其转换为 manager 的**持续业务管理和核对职责**：确保每项有意义的新事实能被受控登记、能反映到当前任务全景，并据此决定专业工作；**不是**让 manager 用聊天维护第二份状态数据库，也不宣称已有自动投影服务。

### 7.1 管理 Pro 要能回答的五级完成关系

| 汇总层 | 需核的业务完成事实 | 不能采用的推断 |
|---|---|---|
| **L2 实际工作实例** | 用 `question_id + work_item_id + node_id`，必要时连同尝试、范围、输入版本/轮次识别实例；核原生产物、当前接受/待验/返修/合法跳过、证据引用和下游可消费范围 | “M06 曾产出文件”≠ 所有 M06 实例完成；不可得调查结束≠ 必需数据已获得 |
| **L1 阶段实例** | 用 `stage_view + stage_instance_id + 问题/轮次/补证范围` 核该范围的必需工作、条件激活、等价复用、适用 Gate、限制及未满足项 | S0～S5/R0～R5 不是固定调用次数；某个结果通过 Gate ≠ 整个阶段完成 |
| **M/R Workflow** | M 已实际交付哪些材料、哪个范围仍缺；R 哪些轮次/预期的分析被接受、哪些正等待补证，哪些已合法收束 | M→R 某份材料交付 ≠ M 全任务完成；R 得到反证 ≠ R 分析失败 |
| **业务问题** | 按 `question_id`、`analysis_round_id`、预期和材料版本核实际发现、当前有效范围、要求深度、尚需工作与可否结案 | 不用全局单一结论覆盖不同问题；新轮结果不自动覆盖旧轮 |
| **父业务任务** | 已明确的完成要求、每项必答问题的结果、仍需执行的合法工作、具名阻断/未决及 H3 资格 | 所有已知节点跑过、一个 D/W 完成或没有新动作，都不自动等于父任务完成 |

这是**五级聚合**，不是要求建立五套权威状态。原生 Skill 结果、工作项、Gate/决定、实际回执是事实来源，`TaskProgressOverview` 只能是对这些来源的查询投影。不给任务编造未经定义的“完成百分比”。

### 7.2 哪些业务事件之后必须核对受影响全景

manager 在初次接管、恢复以及接收实际有意义的新结果时，应核实相应受控事实能否反映到**工作实例 → 相关阶段 → 对应 M/R → 原业务问题 → 父任务**；不是每收到一条普通聊天都重算整任务：

| 发生的事实 | manager 应核对或提出的更新 |
|---|---|
| 初始 GO、原任务恢复；任务范围合法明确/调整 | 父任务目标、已知必答问题/允许深度、未定完成边界、现有有效版本及 M/R 当前分支；边界未知保持待判，但不妨碍合法有界调查 |
| 新 D/工作项建立、依赖激活、真实派发 | 待办/在途工作、对应的 `node_id / stage_instance_id / question_id`、消费者和回交条件；**派发或运输确认不能标完成** |
| L2 原生结果提交并被核实，或发生部分有效、返修/不可得 | 仅在必需检查和适用 Gate/接受均成立后将该**具体工作实例**视为当前有效完成；不满足则保留候选、可用部分、缺项、返修范围与恢复条件 |
| 阶段 Gate 生效、合法不适用/等价复用、阶段完成/仍待验 | 按该阶段实例真正适用的工作和 Gate 重新判断范围；`FAIL/UNKNOWN/NOT_RUN` 的必需硬检查不能冒充通过，其他已接受成果仍保留 |
| M→R 材料交接；R→M 补证发起、部分/不可得返回及关闭 | 两条线同时保留材料已交范围、`request_id/question_id/analysis_round_id/origin_context` 和冻结前后版本；结果只返回原请求并解锁可消费部分 |
| 预期/数据/代码/参数版本变化，旧结果需复验 | 历史已接受结果原样保留；在**当前有效视图**中标记失效或待重验的具体范围与依据，不修改原回执、不无根据让全部工作重来 |
| 中断、效果未知、真实恢复回执 | 指出具体 `EFFECT_UNKNOWN` 动作、受影响工作与对账要求；不能因没有新文件就重发，独立合法工作仍可继续 |
| 问题结果正式接收、H3 结案或具名停止 | 逐问题核当前完成资格、剩余必需、未决和授权；严格区分 `complete`、`incomplete`、`stopped_with_unmet_requirements` |

在已有合格原始结果可以复用的情况下，不为“刷新状态”另外启动取数、重跑 R2/R4 或再叫一次 Pro。**同一事件/相同版本重复通知应幂等，不重复计数；更新范围只涵盖其实际影响的依赖。**

### 7.3 manager 如何实际消费和核验 `TaskProgressOverview`

在决定新的 D、审查跨 Workflow 交接、处理 Gate 缺环、恢复或建议 H3 前，读取从**受控业务事实**形成的当前全景（如果该功能实际可用）。最低核对四块：

1. **整体**：原目标和已明确范围、完成定义状态、当前是否有合法完结资格、仍未回答的必需问题、具名等待/决策。
2. **两条线及阶段实例**：M/R 并行分支、S/R 阶段实例对应问题和轮次、在途/已完成/需重验/合法跳过的适用范围，不使用“目前在 S3”一行覆盖全部工作。
3. **工作与材料**：`work_item_id/node_id`、已核实的原生产物、Gate 决定、原输入版本、复用/接受范围、仍缺什么；同一 M06 生成多份材料，只按一项实际运行登记其产出映射。
4. **问题与后继**：每个 `question_id` 的当前有效分析结论、`analysis_round_id/expectation_version`、补证和依赖、下一合法动作与恢复条件；能继续的工作不得被另一局部阻断全局停止。

核对 `as_of_control_version` 是否对应**最新有效控制事实**。若结果已提交但投影还没有刷新，必须把视图标成**陈旧/待重建**；依受控事件重建后再用于正式进度判断，不能拿旧 Markdown 推断“现在完成”。如果尚未有真实可查询投影，manager 可以提出需补的控制事实/投影缺口，并用原件形成**非权威的专业判断材料**，但不能自行写一个 `current_state` 文件来假装权威数据已更新。

### 7.4 一次变更该如何反馈：不生成独立的“进度报告工作流”

建议对一次新控制事实按 [06 协议 §5](../../control/06_业务完成全景与更新协议.md) 的顺序理解：

```text
原始事实/回交（可能仅候选）
  → 对齐 task / question / node / work / stage_instance / round / version
  → 核验实物、必要的 Gate/接收（未知则保持候选或阻断）
  → 当前工作实例是否有效、可供谁消费
  → 受影响阶段实例的必需工作和 Gate 是否满足
  → M/R 交付、等待、补证、限制变化
  → 业务问题完成资格与仍需动作
  → 父任务完成/未完/受阻与合法后继
  → TaskProgressOverview（受控事实的只读投影及来源版本）
```

manager 的实际产出是**专业问题、具名计划变更/验收建议、哪些已有结果可被消费、何处需重验及下一步条件**，并确保它们拥有精确来源/消费者；受保护记录、版本比较、派生视图计算和物理调度的执行者与接口仍待确认。没有必要仅为一条新回执新增一次 manager C 或专门的“生成完成进度报告”D。

**示例（只演示管理语义，不是运行结果）**：S5 已按 v1 完成材料交接，之后 R3 对 Q1 发出 REQ-1 要补一项 trace。manager 不应把历史 S5 v1 改回“当时未完成”，而应让当前全景同时表示“旧交付历史有效、M 有 REQ-1 定向补证、R/Q1 等原请求结果”。若补证只取得一部分，更新当前可使用子集及仍缺的 trace；若原数据版本又变更，历史结果保留，当前需要重验的受影响问题单列。**只有有据的新结果或合法决定，才改变当前有效完成范围。**

### 7.5 尚未授权/实现的部分明确留下

- [06 协议 §8](../../control/06_业务完成全景与更新协议.md) 的 P01～P06：候选何时变为有效完成、阶段范围/跳过条件、版本失效重算、GitHub 投影读写权和版本一致性、未知完成边界与有界停止等，尚待正式确认与测试。
- 当前 `TaskProgressOverview`、`as_of_control_version`、`current_view_status` 是**候选查询/呈现语义**，不能据此宣称 schema、受保护 GitHub 状态写入器或自动更新程序已实现。
- V2 的 `C/D/W` 属于**运行运输身份**，不能直接代替 `work_item_id/node_id/stage_instance_id/question_id` 的业务完成身份；主控核真实派发回执，manager 负责专业理解和提出有据后继，正式 Gate 与状态生效须由实际获授权的控制机制落实。

## 8. 一个只表示委派逻辑的业务例子（不声称实盘结果）

目标是观察“标准化高频是否既保留重要拐头附近的有用信号，又减少重复”。可以先签一项材料 D，要求执行 Pro 基于已有“密集与板块密集的简单标准化”完整 CAEGraph/数据入口核查大小转折、原始多参数组候选、select、apply、CloseGroup、merged 中哪些阶段和字段本轮需要真实取出；尽量复用同一图，交 `MaterialPlan`、真实材料与缺口。**不能预先写成数据已经齐全**。

随后将材料（连同实际限制）交给负责合理性分析的执行 Pro，按已有预期来源形成最小业务预期并在正式对照前冻结；对照可能给出 `SUPPORTS/COUNTERS/MISSING` 等任一有据结果。若发现“选中参数事件未进入 CloseGroup”的具体偏差，优先沿这一阶段查临近、同刻、超时与确认事实；缺中间 trace 时回原问题定向补证，不重做全部材料。只有诊断有据显示参数可修复/耦合待求解，并且本轮要求和操作资格允许，才调用标定 Skill。**这只是任务组织示例，不是要求每个用例照此强制走全链。**

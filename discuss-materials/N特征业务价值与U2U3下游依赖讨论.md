## 第 1 轮

### 问：

by: 樊月；原对话时间未提供。

我当前这个长程任务，从业务立场我觉得还不是很清晰，就是最终要达到什么状态和意图。
现在是观察迭代嘛，过程中可以不断从工作四回到工作一二三，发现问题去改。最终的产出拿不太准，比如可能会产出一组合理参数，是观察后大部分情况都成立的；或者发现一些设计问题，给出想法然后重新实现。
假设这些情况都有了，最终得到的是一个什么东西？整个最后的意图会怎么样。是观察到这个特征基本合理后就继续往后观察的它下游特征吗？如果是这样，那基本合理到底怎么确定，以及得到这个基本合理预期会经历大致上怎么一个时间预期的过程，我觉得当下还是不是很清晰。然后因为这个不是很清晰，我会担心说到最后会发现就是前面做的这些工作都白做。

### 回答：

我认为你现在提出的，其实是当前 BI-01 长程任务中一个比较根本的问题：我们已经有了“怎样持续观察和迭代”的工作方法，但还没有充分明确“观察迭代最终要使这个特征达到什么业务状态，以及达到什么程度就可以把主要精力转向下游”。

这个问题如果不解决，确实可能出现你担心的情况：四项专业工作都做了很多，参数调过、图画过、问题也发现过，但最后无法回答这个特征究竟怎么样了、为什么值得继续投入、下一步究竟该做什么。

我重新看了当前仓库的专业主干，发现这里确实存在一个值得补足的层次。

一、先区分三个层次的意图
我认为当前需要把三件事分开：

最终业务意图

使一组特征能够合理表达原本希望认识的市场现象，并能被下游特征可靠使用

当前单个特征的阶段目标

通过真实市场观察，明确它是否合理、在哪些条件下合理、怎样配置和使用，以及剩余局限

四项专业工作的作用

参数探索 → 展示与画通 → aidata 组织 → 观察分析 → 定向返回修改

你现在已经相对明确了第三层的工作内容，但第二层的终点比较模糊，因此第一层也就显得遥远。

目前仓库里的 00_PURPOSE_AND_FOUR_WORKS.md 把目标表述为：了解具体特征的含义、输入、输出与参数，在实际市场数据上探索如何展示和理解，检查正确性及其结果是否符合普通投资者对市场过程的正常解读。

这个定义作为观察工作的目的是成立的，但还不足以构成一个明确的阶段性业务完成目标。

尤其是它没有充分回答：

什么情况意味着特征已经基本合理？

参数合理和设计合理分别要证明什么？

发现问题后，哪些必须修改，哪些可以保留为已知局限？

观察到什么程度，值得停止当前特征的主要探索，转向下游？

哪些是必须先完成的前置条件，哪些可以伴随后续使用继续迭代？

这些不是继续把四项工作细化，就能自然得到答案的问题。

二、我建议把单个特征的最终产出定义为一种“有依据的可用状态”
单个特征观察迭代的最终产出，不应仅仅是合理参数、修改后的实现或一份观察报告。

更完整的产出应当是：

一个经过实际市场观察、适用范围和局限已经比较清楚，能够支持明确下游用途的特征版本，以及支撑这个判断的证据和使用知识。

这里至少包含三个方面。

方面

最终要知道什么

可能的实际产出

特征本身

它是否正确、合理地表达了想表达的市场现象

保留或修改后的特征设计与实现

使用方式

哪些参数、条件、品种、尺度下可以合理使用

推荐配置、适用范围、局限和反例

下游衔接

下游能够可靠地从它取得什么信息，哪些不能推断

明确的输出语义、时间边界和下游使用约束

这样，你提到的两种结果就不是两个互不相干的终点。

一种情况是：参数探索发现某一组参数比较合理，既有设计不用修改。

另一种情况是：发现原设计存在问题，提出并落实修改，再重新观察。

两者最终都应当走向同一个方向：使这个特征成为一个边界清楚、可被继续使用的业务能力。

还有第三种同样有价值的结果：观察后发现原设计思路不成立，或者其业务价值不足，决定暂缓、替代甚至放弃该特征。只要有足够的证据，这也不是白做。

关键并不是每个特征最终都必须通过，而是每个特征都要形成一个能够支持后续决策的结论。

三、“基本合理”到底应该怎么确定？
这里最重要的是：基本合理不是说观察了大部分历史情况都成立，也不是说特征已经没有明显问题，而是相对于它承担的业务职责，重要的正确性、合理性和使用边界已经获得足够支持。

我建议分成四个判断维度。

1. 计算正确
首先确认实际实现没有把预期处理逻辑做错。

例如目前观察的 U2NormalNodeBehaviorFrp，需要保证：

已完成过程、当前未完成过程没有混淆。

最近六段与此前六段的范围正确。

当前可知的信息没有使用后来才确认的信息。

关键统计、归一化和参数逻辑符合设计。

这一层主要验证特征有没有按照它宣称的方式工作，并不直接证明业务设计正确。

2. 业务表达合理
这一层更重要，也更难。

需要从这个特征原本想表达的市场现象出发，判断它的输出与实际行情能否形成合理对应。

例如，当前 N 特征大致在表达单品种、单尺度上的近期已完成过程和当前未完成过程的 Behavior。

那么观察时就应关心：在明显推进、推进减弱、反复折返、当前过程尚未走完等不同情况下，特征能不能把相关事实合理表达出来？

不能因为计算没有 Bug，就认为特征合理。

同时也不能因为特征没有提供完整的 U2/U3 市场认识，就说它不合理。它是一个上游特征，职责本来就有限。

3. 参数和适用边界合理
这里正好对应你提到的“一组合理参数”。

我认为最终不一定要得到一组放之四海皆准的参数，更可能得到下面几种情况：

观察结果

对参数的认识

一组参数在多种典型场景中均合理

可以形成优先采用的配置

不同品种或尺度明显需要不同参数

形成分类配置规则

一段范围内多组参数结果接近

存在相对稳健的参数区域，不必追求某个精确最优值

参数怎么调整都解决不了关键反例

很可能属于设计问题，而非参数问题

其中第三种很重要。

假设参数取 4、5、6 都能合理表达某个市场现象，那么往往不值得为了证明 5 比 4.8 更好，投入大量后续观察成本。

反过来，若从 5 改成 5.1，特征就产生完全不同的市场解释，这是需要关注的敏感性。

所以参数探索的终点更接近：

已明确可采用的参数配置或配置规则，并了解合理变化范围及重要敏感性。

并非找到数学意义上的全局最优。

4. 剩余问题不妨碍当前下游用途
这是我认为最适合确定阶段完成的标准。

例如 N 特征经过一轮观察之后：

计算正确性得到支持；

已完成过程的推进、幅度、效率等表达总体合理；

当前未完成过程的部分输出还存在较大波动；

但下游当前只需要已完成过程的统计信息。

那么就可能作出这样的结论：

N 特征的已完成过程相关输出，在明确的参数与适用范围内，可以供下游开始使用；当前未完成过程的某些输出仍需继续观察，不授权下游据此形成强业务判断。

这意味着，同一个特征完全可以部分达到可用状态，不必所有设计和所有市场情况全部研究透彻才允许继续。

这与你之前要求四项工作可以按实际依赖分批接收的思路也是一致的，不过这里进一步涉及业务层面的成熟度和下游资格，而不只是工作交付的管理接收。

四、我建议把最终阶段结论分为四种，而不是只有完成／未完成
A. 当前范围基本合理，可以继续下游

重要正确性及业务合理性获得支持，参数与使用边界清楚，没有阻断当前下游用途的问题。后续仍可根据新反馈迭代。

B. 部分合理，允许限定范围继续下游

哪些输出、参数和场景已经足够可靠，哪些还存在问题能够明确区分，下游只能消费有依据的部分。

C. 存在实质性问题，需要继续修改和验证

问题影响核心业务表达，尚不能安全地交给相关下游。需明确修复对象和再观察范围。

D. 现有思路不值得继续投入或暂时无法判断

可能是设计假设不成立、与已有能力重复、业务价值不足，或关键证据暂时无法获得。需要重新考虑特征的必要性或研究优先级。

这样的结论，比笼统说“工作4又发现一些问题，继续循环”更容易让你判断整体进度。

特别需要注意，A 或 B 也并不代表永久验收、生产就绪或者投资收益已经得到证明。它只代表在声明的业务范围内，具备进入下一层研究的依据。

五、那么是不是 N 基本合理以后，就继续观察它的下游特征？
我认为总体方向是的，但最好理解成沿特征依赖关系逐步形成可用的业务能力，而不是机械地把所有特征从上游到下游依次验收一遍。

当前 N 特征所在的位置，可以这样理解：

真实行情与上游过程数据

基础运动过程、已完成／未完成信息
当前 N 特征：U2NormalNodeBehaviorFrp

单品种、单尺度的近期过程 Behavior
后续 U2 组织与多品种关系能力

不同对象、不同尺度之间的关系与组织
U3 及进一步业务叙事

特征组合、角色、重点品种等更完整的业务判断
这是业务依赖的概念示意，不等于当前源码的完整依赖图，也不表示所有下游必须串行。
现在有一个容易混淆的问题：

你可能希望通过观察 N 特征，确定它能不能很好地解释“哪些品种会更强、哪些更弱”。

但 N 特征本身主要表达单品种的过程 Behavior，真正的强弱对比可能要到下游多个品种之间的关系和组织中才形成。

所以不能把下游应承担的业务能力提前变成 N 的验收标准，否则当前特征可能永远无法完成。

另一方面也不能只因为 N 自身描述得合理，就认为它必然对下游有用。

因此，这里实际存在两种不同判断：

第一种：特征自身的合理性。

它是否正确、合理地表达了自己应该表达的市场现象。

第二种：特征在下游的实际信息价值。

下游使用它以后，是否能产生有意义的新认识，是否存在冗余、缺失或错误解释。

这两种判断有联系，但不能混为一谈。

我的建议是：N 达到当前用途的基本合理之后，就让下游开始消费，并通过下游实际使用继续检验 N。没有必要等 N 的所有可能用途都研究完。

这样整体工作将从“一个特征内部反复循环”，发展为“多个特征之间沿真实业务依赖不断迭代”。

六、时间预期应该怎么形成？
这是目前最值得改进的另一个问题。

如果把目标定义为“直到观察不出问题”，那么确实几乎无法预估时间。因为市场情况太多，后面永远可能发现新的反例。

我建议不要按“要观察多少天历史、多少个 Case”直接推算，而是按认识逐步收敛的过程来估计。

一个合理的推进过程
形成第一版可观察对象

理解特征、参数、输出，并让真实数据与图能够正确对应。这一步解决的是能不能开展有效观察，不要求已经证明特征合理。

通过典型场景形成第一轮业务认识

优先观察最能暴露特征作用和问题的典型场景，包括正例、反例及边界情况。识别正常表现、明显问题和参数敏感性。

处理影响主要业务用途的问题

把发现的问题区分为实现错误、参数问题、表达问题、原设计问题。定向修改，并检查原问题是否解决、有无引入新的重要问题。

验证主要认识能否跨场景成立

在不同历史阶段、市场状态、必要的品种或尺度中核对，而不是只在最初发现问题的位置反复调参。使用未参与调整的案例检验，尤其需要保留反例。

形成阶段性使用结论，转向下游

明确能使用什么、不能使用什么、剩余问题是否阻断下游。把适用范围内的特征版本、参数及使用知识交给下游，后续再根据反馈迭代。

这里的第二、三、四步可能反复往返，但不应该无限循环。

关于具体工作量，我会这样做初始估计
下面只是用于项目规划的粗略量级，不是已经由当前 BI-01 实际运行数据验证的工期。

情况

特征实现和数据已有，展示路径也基本畅通

图是否真正画通，业务案例是否有代表性

这些时间并非要求长程任务持续运行相应天数，而是从发现问题到取得足够业务结论的日历时间量级。AI 的纯分析和执行耗时可能比它短，但外部实现、交付、人工确认和重新验证会增加时间。

对于当前 N 特征，我不会直接给出“还需三天”这样的结论，因为还缺少本轮真正完成的观察、关键反例数量、有效图形及下游依赖等证据。

更有用的是在第一轮典型案例之后，形成一个初步判断：

当前究竟主要是参数探索问题、几个可定位的局部错误，还是更根本的设计问题？

一旦性质明确，时间预期才可能明显收敛。

七、怎样避免最后发现前面工作都白做了？
我认为真正的风险不是发现特征设计错了，而是研究了很久，却没有留下可以继续使用的业务认识。

例如 N 最后发现“当前未完成过程的某种归一化设计不合理”，这本身不意味着之前的观察白做。

只要前面已经弄清楚了它在什么情况下失真、失真来自哪里、什么替代方案可以解决，研究就是有产出的。

相反，如果只是不断调参数、画图、生成报告，而没有形成明确的业务判断，即使最后找到了一组好参数，未来换一个品种或场景，也可能要重新做一遍。

因此，我建议每次实质观察，都要求推动下面三个问题中的至少一个：

对这个特征的业务含义或适用边界，获得了什么新认识？

某个具体问题是否已经被解决、反证或者缩小范围？

对这个特征是否能够进入下游使用，判断是否发生了变化？

不要求每轮都有正面成果，但要能够识别哪种探索方式已经没有明显信息增量，及时换方法或停止。

还有一个很重要的成本控制原则
不用为了证明一个上游特征“全面合理”，把所有可能的市场场景都观察一遍。

应该根据它当前承担的业务职责、可能造成的错误后果，以及下游实际依赖，决定需要投入多大观察成本。

如果某个细节只影响暂时不会被使用的输出，可能应当保留问题而继续其他工作；如果某个细节会造成严重的未来信息泄漏，即使只观察到一个反例，也必须先解决。

这里的优先级应该主要来自问题的业务影响，而不是反例出现的数量。

八、我认为当前 BI-01 真正应该补上的，是一层“特征成熟度与下游接续决策”
现在的四项专业工作不用推翻。

我重新核对的 01_OUTPUT_BASE_FORMAT.md 已经明确提出：不能因为四个栏目都填完，就认为专业观察完成；应由具体特征值得研究的问题、已得认识和接续方向决定。

这个方向是正确的，但我认为目前还缺少将这句话落实为明确业务判断的方法。

建议最终让管理 Pro 在适当时点，依据专业 Pro 的真实成果，能够回答下面五个问题：

管理需要回答的问题

对 Owner 的价值

当前特征主要希望解决什么市场认识问题？

确认工作有没有偏离原目的

我认为这里需要区分两种“为什么存在”。

第一种是工程上的存在理由：为什么要把 N 单独做成一个特征？

CYF 10 月 15 日的讨论很明确：完整 U2/U3 很大，需要从已经具备可靠输入的上游部分开始，逐项形成可以运行、可以读取、可以观察的具体特征。

N 适合沿着既有价格过程继续实现，而且能够作为具有历史状态的特征独立交付。

这是合理的实施理由，但不能替代投资业务上的存在理由。

第二种是业务上的存在理由：为什么需要这种近期行为描述？

这里的材料要弱一些。

在 10 月 21 日的讨论中，CYF 自己也明确担心：N 过于上游和平凡，交给投资业务人员观察，到底能产生什么有价值的认识？

当时形成的建议是，观察它能否有效表达单品种近期过程，以及哪些重要信息被统计压缩掉了，而非承诺它已经具有独立投资解释力。

我目前没有从核查材料中找到一项已经明确确立的、专属于 N 的投资场景，例如“为了判断某种明确的拐头风险，所以必须采用这两组六段统计”。

因此不能倒过来，凭 N 已有的六项指标和两组窗口，给它编造一个已经被确定的业务目标。

这意味着，现在的观察迭代其实还承担着一项更上游的研究任务：弄清楚这种近期过程 Behavior 是否值得独立成为一项业务表达，以及它应当承担哪些业务责任。

这与先假定 N 的设计目的完全正确，然后逐项找它实现得是否合理，是有本质区别的。

三、我建议暂时采用的核心业务锚点
结合现有设计，我认为可以先形成这样的候选业务目的：

对于一个品种在某一尺度上的价格运动，利用最近已经完成的一组运动过程，形成对近期运动表现及其变化的概括，并结合当前尚未完成的过程，帮助理解这个品种目前的运动与近期背景之间的关系。

重点检验这种概括能否保留值得认识的市场差异，而不是把关键差异压缩掉，或者把没有业务意义的统计变化误认为市场变化。

这里我刻意没有使用“预测拐头”“识别强势品种”这样的下游目标。

也没有把“趋势状态”作为唯一目的，因为 N 当前的六项指标并不完整表达趋势方向、发生顺序或不同品种之间的关系。

这个锚点目前应该是待业务观察验证的目的假设，而不是已经成立的 N 正式定义。

如果后面的观察发现它确实能够形成有用的近期运动画像，就可以进一步明确其独立业务用途。如果它主要只是方便下游取得一组统计事实，那么应当把它定位成描述性输入，不强求其独立解释力。

2. 当前未完成过程为什么要和已完成窗口放在一起？
这也是关键设计。

已完成窗口描述的是一批完整过程的统计表现；当前 Working 描述的则是一个仍在发展、其长度和内部路径会不断变化的过程。

现有实现并没有直接计算统一的“Working 相对完成窗口偏离程度”，而是把它们作为不同部分保留在同一 Behavior 中。

所以观察时不能默认两者已经可直接比较。

从业务角度真正值得研究的是：

已完成的历史过程为当前运动提供了什么参照？当前过程表现出来的不同，是有意义的变化，还是因为它还没有走完而产生的自然差别？

如果这个问题能够回答好，N 可能形成很有价值的持续过程描述。

如果很难回答，Working 与两个完成窗口放在同一个特征里，也许主要体现了数据组织上的方便，而不是已经形成了完整的业务解释。

另一个细节也很说明问题：六成员中位数的 LOO 绝对影响，在成员全部有效时会全部并列。这是偶数样本中位数的数学性质，不是一个能够直接指出哪个过程最重要的分析方法。此前 R33 已确认这个边界。它提示我们，某个字段即使计算正确，也不一定具有原本期待的区分能力。

五、用已经存在的真实 N 数据，把观察锚点落实到行情上
我认为可以先围绕下面几种真实情况展开。这里使用 CYF 之前已经计算并核对过的 N 结果，而不是凭空构造市场结论。

它们目前只能作为候选业务观察位置；正式工作4仍需相应平台交付获管理认可。

螺纹钢 rb 在 2016 年 5 月 30 日的一个真实样本中，最近完成窗口效率约为 0.0105，此前约为 0.190，而 Working 效率约为 0.842。

这里不需要要求 N 具有收益预测能力，但需要检验它表达的东西在市场过程中是否真的有可理解的意义。

六、这轮观察最终应该产生什么有价值的业务成果？
结合前面的分析，我现在认为，N 的观察结果最值得争取的并不是某一组最终参数，而是对下面这个问题形成有依据的答案：

这套近期过程描述，在市场认识中到底能够承担什么业务职责？

可能形成三种不同的结果：

观察后的认识

业务上的产出

N 确实能有效表现某些近期运动性质及其变化

明确这些业务概念、适用场景、使用方式以及相关参数

N 只适合表达基础统计事实，不足以独立形成重要市场解释

明确它作为描述性上游信息的职责，区分哪些进一步认识应交给下游

N 的部分统计组织无法保留其本应表达的重要差异

提出具体的结构或方法修改，而不仅是调整参数

这里还有一项很重要的判断：即使 N 不能独立产生有价值的投资认识，也不必立即认定它没有价值。

如果下游实际需要一种标准化的近期过程描述，那么它仍可能具有复用价值。但这种价值要通过具体消费者及其业务问题来证明。

反过来，如果下游既不需要这份概括，投资者看图也没有因为它获得更清楚的认识，那么就应该考虑减少 N 的业务责任，甚至简化这部分设计，而不是继续调出一组看起来更漂亮的参数。

我认为这才真正回答了你最初担心的“最后会不会白做”。

观察迭代不仅应该改进特征，还应该有能力发现：某项既有设计是否值得继续存在，以及应该以什么形式存在。

七、对当前 BI-01，我建议接下来怎样实际应用
我也核对了当前最新的 BI-01 管理 R0043。

截至这份 10 月 25 日的报告，N 的参数来源、图形设计、指定知识时点的回看与正式资料关联已经推进得比较多，但正常共享平台还没有完成实际接入和页面核验，所以正式工作4尚未签发。

已有的 rb 确认前后以及 i 缺价恢复等场景，主要解决的是时间、Life、数据可用性和展示正确性问题。它们很有必要，但还不能代替上述以业务目的为中心的市场观察。

因此，当前最好把两种工作区分开：

正在进行的专业任务继续处理已经确定的平台交付与真实依赖，不需要为了这次讨论推翻或重做已完成内容。

后续业务观察的核心方向则应明确为：先通过市场上重要且具有区分力的过程变化，检验 N 对近期运动背景及当前运动的表达价值，再决定具体要修改什么，以及哪些问题应由下游继续处理。

尤其值得在观察中同时保留一个对照：如果不使用 N，只看原始 K 线、尺度转折与单个过程的已有指标，我们已经能认识什么？加入 N 后，又让哪些认识更清楚、更稳定或更方便后续处理？

因为 N 本来就是对既有过程信息的再组织，它不必产生新的原始市场信息，但需要证明这种组织本身有什么业务用途。

八、这次分析后的阶段结论
我认为现在已经可以把 N 的讨论推进到一个比较清楚的位置：

可以确认的： N 的实际职责是描述单品种、单尺度的近期完成过程、近期相对变化及当前未完成过程。它属于 U2 的上游描述能力，不是独立的机会簇或重点品种判断。

目前最合理的目的假设： 为投资者和确有需要的下游提供一个持续更新的近期运动背景，让当前运动可以在这一背景下得到理解。

尚未得到证明的： 这种背景是否保留了投资者真正关心的市场差异、是否优于直接使用原有过程信息，以及哪些下游判断实际需要它。

下一轮观察最值得获得的结果： 不是笼统的“N 基本合理”，而是弄清楚“N 在什么样的市场情形下能够形成有用的运动认识，在什么情形下会造成误解，以及哪些认识根本不应由 N 负责”。

我认为这已经初步形成了你之前说的那个“大锚点”。

不过，当前最需要进一步深入的，不是全部六项指标的计算细节，而是“两组已完成过程如何代表市场近期背景”以及“这个背景与当前 Working 的关系”这两个关键设计。 它们决定了 N 作为一个整体，究竟是不是有意义的业务表达，而不仅仅是一些分别计算正确的统计量。

### 回答：

我认为你这次提出的思路，比前面直接猜测 N 有什么投资价值更加合理。对于 N，应该优先从下游实际要解决的业务问题，反向理解为什么需要 N、需要它提供什么信息，再判断它目前的设计是否能够承担这个作用。

你提出的两种特征价值来源，我认为可以作为当前观察迭代的基本分析立场：

直接业务价值： 特征本身就是为了解决某个投资业务问题，输出能够直接支持某种业务认识。

上游支撑价值： 特征为下游解决业务问题提供必要的信息、处理结果或可复用能力。它自身不必直接形成最终投资判断。

对 U2NormalNodeBehaviorFrp，我倾向于先按第二种定位展开分析，而不是要求它证明自己可以独立识别行情机会。

我查到了一个很关键的区别：U2 较早的关系设计确实包含使用 N 进行跨品种近期行为比较的逻辑；但当前已经接收的独立转折关系特征，并不要求运行或消费 N。也就是说，N 存在一个设计过的下游用途，但不能因此认为这个用途已经在当前主线中得到落实，更不能认为它的业务价值已经被验证。

这恰好说明，需要把“下游希望利用 N 做什么”和“下游现在实际上有没有使用 N”分别研究。

一、沿着 N 的下游，实际上能找到什么？
根据我查到的 U2 业务依赖图、原关系方法、当前关系特征和后续工作计划，可以先画出这样的关系：

真实价格、尺度转折、各段运动过程

在 Formation.hs 的原八类关系 中，有一类叫 NodeBehaviorComparison。

它把两个品种各自的 N 结果进行比较，比较的具体内容是各指标的：

这比单纯猜测 N 能不能描述市场，要具体得多。

而且源码中把 NodeBehaviorComparison 定位为 Descriptive（描述性证据），没有作为必须满足的 Required 或一票否决的 Veto。

因此，它原本主要承担的是补充对关系的理解，而非直接决定两个品种能否成为共同转折组。

还要注意，原比较方法并没有实际使用 N 的全部信息。至少在这条比较路径中，Working 和 LOO 没有参与上述三个坐标的比较。

2. 当前已经接收的关系特征，反而不依赖 N
这是另一个很有价值的发现。

当前 R39 第二特征管理接收 明确说明：

U2NormalTurnRelationsFrp 不恢复对 N 方法或 N 背景副本的强制依赖。

当前关系特征主要使用转折的时间、方向、类型、几何，以及转折后两过程的真实运动材料。这些信息已经能够形成其有限关系结果。

这意味着，目前不能说“因为下游关系特征要使用 N，所以 N 一定具有价值”。

更准确的现状是：

较早设计存在 N 的下游描述性用途。

当前独立关系特征不需要 N 也能完成自己的主要职责。

后续机会组织可能需要额外背景信息，但究竟需要 N 的哪些内容，目前还没有通过这条已接收的关系路径得到证明。

这并不意味着 N 没有价值，而是把真正需要研究的问题暴露出来了。

二、从下游业务问题出发，N 可能究竟增加了什么？
我们可以先从 U2 比较明确的业务问题开始：

几个品种在相近时间发生转折，并且随后都产生一定运动，它们之间究竟形成了什么关系？是否存在共同的机会组织？

现有转折关系与两过程比较主要能告诉我们：转折是否接近、方向是否相容，以及转折后的推进、效率、逆向运动等是否具有某种关系。

但我们可以进一步提出一个问题：

这几个品种虽然这一次的运动表现比较接近，但它们此前一段时间的运动背景是否相同？这种不同是否值得成为理解当前关系的依据？

例如，假设有两个品种 A 和 B，都在相近时间向上转折。

A 在此前一段时间的运动普遍比较顺畅，近期变化也不大；B 此前的运动经常折返，但最近几段明显改善。

这时，仅看当前转折和转折后的短期运动，可能觉得 A、B 很接近。

如果使用 N，理论上可以进一步表达：

A 当前的运动接近其近期既有表现，而 B 当前的运动发生在一个近期表现正在变化的背景之中。

这个差异是否具有投资业务意义？ 这才是我们应该研究的下游问题。

如果这种背景差异有助于解释两个品种为什么在后续组织中表现不同，N 就可能提供有价值的补充信息。

如果最终发现，当前转折及其后过程已经能够充分解释这种差别，N 所提供的背景并没有帮助，那就说明至少在这个业务用途下，不需要 N。

这里我并不预设“背景改善就意味着未来更强”。我们只是先明确下游需要辨识什么，再检验 N 是否提供有意义的材料。

三、这样反推以后，N 的设计问题会变得具体
例如，假设下游真的希望比较多个品种的近期运动背景，那么原本看起来很普通的“最近六段”参数，就会变成一个值得重视的设计问题。

因为两个品种即使都取最近六段，实际覆盖的市场时间也可能相差很大。

品种 A 的六段可能只覆盖几个交易日，品种 B 的六段可能覆盖很长一段市场历史。

如果下游希望比较的是它们在同一近期市场环境中的表现，就需要检验这两个背景是否真的可以相互比较。

但如果下游希望比较的是各品种最近六次独立运动的典型表现，那么这种时间跨度不一致可能本来就是合理的。

到底是否合理，要由下游需要怎样的业务比较来决定。

同样，当前部分指标还没有进行跨品种可比的归一化。如果下游只是看一个品种相对自身的变化，这和直接比较两个品种的绝对运动幅度，对归一化的要求并不一样。

因此，这种倒查会直接改变我们对 N 的观察重点：

不是先找一个最合理的六段参数，而是先确定下游希望使用怎样的“近期背景”，再检验现有选窗、统计和归一化是否能够提供它。

这里可以检验关系特征有没有抓住应当抓住的市场差异，还可以继续看相关差异是否影响候选、方向组织、机会簇和 U3 的运动质量比较。

这和 N 的处境不同。N 目前还需要先证明其历史统计背景对于哪个下游问题是有用的；关系特征则已经能直接连接到 U2 原本希望处理的市场现象。

2. 但关系特征也不等于已经打通下游计算
这是这次新核查中一个很值得重视的发现。

当前 U2 的 CommonPriceTurnGroupCandidatesFrp（共同价格转折候选组），其具体实现使用了 GroupCandidateSource.hs、GroupCandidatePairs.hs 等模块。

其中：

GroupCandidateSource.hs 明确不启动 Episode/N。

GroupCandidatePairs.hs 根据转折时间、方向、类型、几何等材料直接判断 Pair。

当前候选组形成过程并不是简单地读取 U2NormalTurnRelationsFrp 的正式结果，再从中筛出候选。

因此，当前独立关系特征与下游共同转折候选组，在业务语义上直接相关，但不能据此认为候选组计算已经把该关系特征的结果作为必需输入。

这不一定是设计错误。两个特征也可能合理地共享底层转折事实，分别进行不同范围的判断。例如，关系特征只保留每个品种最近两个合法确认端点，而候选组可能需要自己的完整候选范围。

但这意味着，在选它进行完整观察迭代之前，最好弄清楚：

它自己产生的关系结果，究竟是提供给哪个后续业务判断直接使用，还是主要作为可独立阅读的有限关系描述？

如果只是后者，它仍然可能有直接业务价值，但不能把“推进它的合理性”自动等同于“整个 U2 机会组织会随之改进”。

3. 它目前有可供真实观察的实物
第二特征 R39 正式接收 已经记录了 rb、hc、i 三个品种在 2013 年至 2024 年历史行情上的实际计算与正式读取。

其中还存在具体的业务例子：有的两过程差异落在灰区，有的在缺价恢复后进入反证状态；晚确认也会使同一关系的后续观点发生变化。

所以，它不是只有需求文档、没有真实数据的候选设计。

我的初步选择是：若在 N 与这个关系特征之间选一个，优先选 U2NormalTurnRelationsFrp。但观察目标应当围绕 U2 的共同转折与后续机会组织，而不是孤立地证明八类关系和七个坐标都正确。

所以，目前缺乏的不是 N 的合理性证明，而是它与 U2/U3 总体业务目标之间的实际贡献关系。

三、当前 BI-01 真正缺少的是总体业务目标与具体观察工作的联系
我认为现在至少需要把以下几件事联系起来：

层次

应当回答的问题

U2/U3 总体目的

想要解决市场中哪些具体问题，最终得到什么有价值的业务结果？

业务能力分解

后续接续

这样才能形成一个区别于现在“四项专业工作”的业务推进全景。

四项专业工作解决的是具体特征怎样观察；业务推进全景解决的是为什么要观察这个特征、这次观察应推动整体业务的什么部分，以及得到结果后沿什么方向继续。

两者是不同层次，不应互相替代。

四、这也意味着，单特征观察的完成不一定是最终业务成果的边界
例如，假设 U2/U3 希望处理这样的市场问题：

那么可能需要沿着以下业务关系不断推进：

U2 能不能合理识别这些转折之间的关系，形成有意义的候选与机会组织？

U3 能不能针对这些机会对应的实际运动，合理表达推进、摩擦、保留以及品种之间的差异？

这些认识能不能继续形成有依据的业务解释，并且通过后来结果检验和反馈？

这里仅是用来说明推进关系的业务例子，不是现在就把 U2/U3 全部目标缩成这一种场景。

实际推进时，可能先观察一个上游特征，发现它无法保留某些重要的市场差异；修改以后，要继续沿它影响的下游研究，而不一定在该特征上反复打转，直到它被单独判定为“完全合理”。

也可能在下游观察过程中，发现问题实际来自已经观察过的上游特征，再返回修改。

这样观察迭代的单位可以是单特征，但业务认识和迭代成果是沿着 U2/U3 的整体关系不断积累的。

五、我认为下一步应该先做什么
现在不应该继续讨论 N 和关系特征哪个更值得观察，也不急于制定新的单特征验收标准。

应该先从 U2/U3 整体出发，建立一份能够指导观察迭代的业务全景。

但这份全景不是把几十个特征及其输入输出重新罗列一遍。应该重点做三件事：

重新理解 U2/U3 总体业务意图。 从原始 Use Case 和业务设计材料中，梳理最终希望认识哪些市场现象、解决哪些业务问题、形成什么实际结果，而不只是列出现有 Feature。

建立业务目的到具体特征的依赖关系。 从最终业务问题向上游追溯，区分必要计算、条件性使用、描述性信息和仅在接口中携带的结果，并核对当前实际实现。

最后应该得到的是：当前 U2/U3 距离真正产生预期业务效果还差什么，观察迭代应该优先帮助解决其中什么，以及解决之后怎样继续向前推进。

它不要求一开始就把全部 U2/U3 细节设计重新研究透，也不要求等完整 U2/U3 都实现才能观察。关键是先对总体意图和主要业务关系有足够清楚的认识，再按实际可观察的部分逐步深入。

我认为这才是当前 BI-01 最需要补上的一层。此前我们主要在研究“怎样把特征观察迭代做好”，但现在需要先明确：怎样让观察迭代真正成为推进 U2/U3 落地、产生业务效果的一种有效工作方式。

三、总体观察思路与单特征观察的关系，应该怎样理解？
你提出“先有相对完整的 U2/U3 观察思路，执行到具体特征时再使用当前长程任务”，我认为有一定道理，但存在两种不同理解。

理解 A：预先制定一套覆盖 U2/U3 所有特征的观察计划
这种做法可能要求提前为大量特征确定观察目的、案例、顺序、参数和判断方式。

目前 U2/U3 有几十项后续特征或候选，许多内容还在实现和变化中。如果现在把它们全部展开到可执行的观察细节，投入会非常大，而且部分计划很可能随着业务认识变化而失效。

我不倾向于这种方式。

理解 B：先建立 U2/U3 的业务观察逻辑，再根据真实问题逐步展开具体观察
我更倾向于这个理解。

也就是说，先不需要穷尽所有特征的观察方案，而需要能够回答：

当前在推进 U2/U3 的哪一个业务问题？这个问题背后有哪些相关设计？为什么现在观察某个具体特征能够推进这个问题？

当这一关系成立时，再进入 BI-01 的具体特征观察。

例如，假设我们讨论的是：

几个黑色系品种在相近时间一起转折，但之后的运动明显分化。U2/U3 是否能够正确认识这种市场结构和表现差异？

这可以成为一个总体业务观察问题。

沿这个问题，可以先检查 U2 能否合理认识共同转折与机会组织，再看 U3 如何认识后续运动质量、相对关系等。

如果发现某个关键错误来自 U2NormalTurnRelationsFrp，就可以围绕这个具体特征使用 BI-01 的四项专业工作。

如果发现 U2 的关系描述合理，但后续机会组织不能合理使用它，那么问题不一定应回到关系特征，而可能要深入下游的候选、成立或组织设计。

如果发现 U2 的机会组织没问题，真正无法区分运动质量的原因来自 U3，那么观察重点就可能转向 U3。

这样，每次观察的执行对象可以是单特征，但观察问题属于更大的业务关系。

这就与你之前人工观察一组相连特征的方式比较接近，只是 U2/U3 现在需要显式地把原本隐含在脑子里的业务关系表达出来。

而且这里还有一个重要变化：

不应当把“一个特征是否迭代完成”天然当成业务推进的结束点。

结束点更可能是：某项业务问题已经取得了足够的认识，相关设计问题得到解决或明确了后续依赖，再沿总体目标继续推进。

### 回答：

我先看了 CYF 长程任务中 U2 Mission A 的汇总成果和当前任务入口，已经发现一个很重要的线索：

Mission A 的设计不是简单地把一个总体目标拆成若干特征，而是逐步形成了一套“业务对象—判断关系—正式结果—下游使用—历史反馈”的合同体系。

它不仅定义要计算什么，还定义哪些结果可以成立、怎样保持业务身份、什么时候正式提交、下游能读取什么，以及后来的信息怎样修订前面的判断。

这与我们现在讨论的观察迭代非常相关。因为观察一个特征时，真正值得检验的可能不只是其局部计算，而是它所承担的某一项业务判断在整条链里是否合理。

不过，当前读到的主要是 Mission A 后期整理过的成果，还不能把它直接当成设计最初形成的思考过程。接下来需要区分：哪些是最初的业务推导，哪些是长程任务运行时为了补齐合同、修复问题和支持工程交付而逐步增加的内容。

一、Mission A 最初要解决什么问题？
我找到了一个比较直接的原始目的表述。

在 CYF 的 U2/U3 长程任务 README §1 中，U2 Mission A 的目的大致是：

把哪些对象表达同一轮机会、机会簇怎样跨尺度保持、怎样识别重复暴露等完整业务形成方法、时间与回看、产品与消费者说清楚，形成基本合理、可修改的投资业务首版。

这有两点值得注意。

第一，Mission A 并不是从 N 或某个具体特征出发。

它是从几个具有明确投资业务意义的问题出发：

哪些品种的运动应该被认为表达同一轮机会？

多个品种怎样形成有业务意义的机会簇？

这种机会结构在不同尺度间怎样保持、变化或消失？

多个看起来有利的品种，是否只是同一机会的重复表达？

U2 怎样把这些认识交给 U3 继续处理？

第二，Mission A 的目标不是证明这些设计已经在真实市场中产生预期效果。

它主要是把解决这些问题的业务方法设计清楚，形成能够交给 Mission B 进行工程化解释的合同。

这也意味着，你现在希望开展的观察迭代，正好可以针对 Mission A 形成的这些业务方法进行实际市场检验。

二、Mission A 怎样把业务问题逐步展开成各层设计？
我认为可以初步还原出六层推导关系。

1. 同一轮机会的业务识别

哪些品种共同发生有意义的市场运动，而非仅仅时间接近
2. 从转折事实形成候选与过程关系

尺度转折、真实运动过程、节点 Behavior、跨品种关系、候选组
3. 判断机会组是否真正成立

转折后运动组织、成立资格、组外差距、身份仲裁
4. 理解机会之间的组织关系

跨尺度承接、重复机会、成员角色与差异
5. 形成能够交给 U3 的业务认识

结构化解释、证据、正式机会结果、H1
6. 通过 U3 结果和后续反馈继续修订

运动质量、活动转化、相对资金依据与后验结果
这个结构有真实材料支撑，最重要的来源是：

U2 Mission A Feature Narrative Stack §1–4

它明确提出：

Source → measurement → objective fact → Feature

再由具体 Feature 形成 Relation、Formation、Qualification、OpportunityCluster、CrossScale、Role、Assertion、H1。

这份文档尤其值得深入，因为它对每个设计节点不仅记录名称，还区分了：

正面市场含义；

向上游或下游的作用；

明确不允许据此声称什么；

正式产品与消费者；

当前方法与成熟度。

这比普通的“特征输入输出依赖图”更接近你要找的设计推导逻辑。

但这里不能把六层理解成 Mission A 历史上按这个顺序完成
这是当前需要保留的一个区分。

上述六层是从 Mission A 成果还原出的业务逻辑顺序。

实际长程任务形成设计时，还经历了大量业务合同修复。例如：

跨尺度承接不能只看成员重合，还需要实际转折与后续运动对应；

两个机会是否相同，不能只凭共同成员，必须区分共同部分与具有证据的独立剩余；

组的候选身份、正式机会身份、生命周期和修订不能混同；

下游不能凭最新状态拼凑历史上某时点的机会判断；

U3 的反馈不能直接无痕改写 U2 当时已经形成的结论。

这些不是完全独立的业务目标，而是在把最初目标细化成可执行方法时，暴露出来的关键设计问题。

三、一个具体例子：Mission A 怎样推导“重复机会”
这个例子能比较清楚地体现设计的深入方式。

最初的业务问题可以理解为：

几个品种可能都表现不错，但它们究竟表达了几个不同机会？如果实际上属于同一机会来源，就不能把它们简单看作多个独立机会。

第一层想到的是比较机会簇之间的成员重合。

但是，仅凭成员重合是不充分的。

例如两个机会簇包含同样几个品种，但对应的实际转折、运动时间和方向可能不同。

于是设计进一步提出：必须比较两个机会中实际形成运动的单元，寻找共同部分。

又出现第二个问题：有共同部分，并不意味着完全相同。

两个机会可能部分共享，但各自仍有明确的独立运动。

于是还要识别独立剩余。

再往下，设计要把关系区分为：

Same / Partial / Separate / Unknown

并且规定：

有明确共享和独立剩余，才可能形成 Partial；

缺少证据不能直接推成 Separate；

A 与 B 属于同一机会、B 与 C 属于同一机会，不代表 A 与 C 自动成立；

这些结果需要保留各自证据，并能在后续 U3 中消费。

这个推导过程可在 Mission A R23 的 GENERATION_METHODS.md §2–5 中直接看到。

它非常有启发性：

一个业务问题经过细化，不是机械地拆成多个计算特征，而是不断发现：要形成原本希望的业务判断，必须进一步区分哪些市场事实、哪些判断状态，以及怎样的证据才足够。

而这些新增设计，后续恰好都可以成为实际观察迭代的研究对象。

比如真实行情中两个机会明明具有独立运动，却被判断为 Same，那么就可以沿这套逻辑定位：共同单元怎么认定？独立剩余有没有被正确保留？是否是参数还是业务方法的问题？

这比对某个上游统计指标孤立地找问题，更直接地联系到 U2/U3 的业务目的。

二、P01–P13 与 23 项 Feature 究竟是什么关系？
这两者最准确的区别是：

四、§5 和 §6 为什么还要在 §3、§4 之后存在？
这两个章节的价值，在于进一步把业务过程和具体设计联系起来。

§5：把业务叙事展开成多种必须相互一致的设计关系
如果只有 §3 的 P01–P13，通常知道系统要做什么，但很多细节仍然无法决定。

例如 P06 写着“形成共同实际转折候选”，这还不足以实际实现。

继续设计时，需要回答：

WORK_MAP §5 视角

对 P06 实际要补清的问题

§5.1 业务身份与状态

什么才是一个独立 CandidateGroup？成员改变是否产生新 Life？

§5.2 Event、材料和业务时间

使用 actual 还是 confirm 时间？何时可知？候选如何持续、关闭和修订？

§5.3 方法位置

怎样比较实际临近、方向相容、几何关系？多个成员怎样形成 complete-link 组？

§5.4 正式产品与消费者

Candidate 最终是什么结果？P07 如何使用？

§5.5 历史与修订

迟确认、实际转折更正、候选退出怎样影响旧结果？

这些视图共同约束 P06 的设计。

并不是先完成身份，再完成时间，再完成方法，最后才允许考虑消费者。

相反，它们要相互校验：例如如果 P07 需要知道候选组形成时选中的实际转折，那么 P06 的输出就不能只保存一个品种列表。

这时需要回到 P06 的 LOCAL_CONTRACT，确保它形成的正式结果能够满足这个下游用途。

§6：把已经辨认出的 Feature 接入当前具体方法
§6 则更偏向具体使用。

例如：

WMF07–10：对应近期六段与此前六段、median、MAD、LOO、Working 独立处理；

WMF11–12：对应实际转折时间邻近、方向类型及几何语义；

WMF13–15：对应 Working 成熟度、Required 方向关系及辅助运动组织信息；

WMF16–18：对应 Formation 时间范围、最低组织支持和组外分离的具体条件；

WMF20–21：对应跨尺度承接和重复暴露中，两端运动证据的不同使用权限。

所以，§6 不是在 §5 的基础上再发明一次 Feature，而是把已存在的 Feature 定义与现行参数、方法合同及使用边界对上。

这也解释了为什么 WORK_MAP 与 LOCAL_CONTRACT 之间不是一次性的单向交接：LOCAL_CONTRACT 细化方法后，如果改变了实际用途或业务结构，必须反过来核对 §5、§6，必要时修订 WORK_MAP。

五、那么，观察迭代应该逐个特征从上游往下游做吗？
我的判断是：

沿真实依赖关系推进是合理的，但机械地从 WMF01 开始、逐个观察到 WMF23，不合理。

这里需要区分两种推进方式。

方式一：按特征顺序全面检查
WMF01 → WMF02 → WMF03 → …… → WMF23

这种方式有一个优点：组织比较简单，容易知道看过什么。

但也有很大的风险：

上游特征可能只是中间信息，并没有直接承担最终业务判断。

可能在验证某个字段时，就投入大量时间优化它的参数，却还不知道下游是否需要它。

即使单个 Feature 都被认为合理，组合起来仍可能不能形成预期 OpportunityCluster。

更下游的业务问题可能要求修改前面的 Feature 职责，而不是仅调整其计算方法。

N 的情况就已经暴露了第一、第二个风险。

方式二：从重要的业务判断出发，沿必要依赖观察，再向下游验证
我认为这种方式更符合当前 U2/U3 的总体意图。

例如，先以 WORK_MAP §2 的一个核心问题为锚点：

U2 能否从实际贴近转折及转折后运动中，正确识别一轮方向机会的成员和边界？

这时需要重点研究 P06–P08 这段业务设计，而不是自动把 P01–P05 的所有 Feature 都排在前面。

但观察 P06–P08 时，必须拥有足以解释结果的上游真实事实，例如实际转折、价格路径和 Episode。

于是可以采用这样的思考逻辑：

1. 先确认要检验的业务判断

例如：共同转折形成的几个品种，是否应被认定为同一个方向机会簇？

2. 反向找出这项判断所需的上游设计

Formation、PostTurnQualification、Validity、ExternalSeparation，以及各自需要的实际转折和 Episode 事实。

3. 用真实市场检验这段设计

看实际市场出现了什么，当前业务方法产生什么判断，它是否保留了重要差异。

4. 沿依赖关系定位问题并修改对应 LOCAL_CONTRACT

发现问题属于 Formation，就修改 Formation；属于 Qualification，就修改 Qualification；若业务定义本身不对，则可能需要修订 WORK_MAP。

5. 再检验修改对目标判断及下游结果的影响

不仅看单项计算是否变化，还要看是否改善了机会成员、簇边界或后续的业务认识。

这种方式既不是单纯的自上而下，也不是单纯的自下而上。

更准确地说，是：

从目标业务判断出发，向上游追溯必要设计；实际观察中定位问题；修改之后，再向下游检验效果。

当然，如果上游基本事实自身就不可靠，需要先处理它。这里不是跳过上游，而是不要求所有上游 Feature 都先完成独立业务观察。

如果 LOCAL_CONTRACT 有问题，应该改哪一层？

六、这对后续 WMF 与 Fao 的对应有什么影响？
我认为你提到的下一项核查是必要的，但前提不是先确定二十三个观察任务。

因为现在已经明确：

WMF 是 Mission A 的业务设计节点，Fao 则是后续实现和交付的具体特征单位，两者不能预设一一对应。

例如：

WMF01–06 可能作为 Episode 量测结果由同一计算主体提供，而不各自对应独立 Fao。

WMF07–10 描述单品种近期 Behavior 的几个业务方面，但不能据此认定存在四个独立 Fao。

WMF11–15 覆盖实际转折和后续运动的多个关系，但当前 U2NormalTurnRelationsFrp 只承担其已经授权和实现的有限关系职责。

WMF16–19 涉及候选、资格化、有效性、分离及机会簇边界，可能由多个相互关联的正式计算结果承担。

所以后续对应时，应核对的是：

一个 WMF 的业务意义，到底由哪个 Fao、哪个具体方法和哪个正式输出承担？该输出是否真的被它在 WORK_MAP 中声明的消费者使用？

这一步会把 Mission A 的业务设计与当前真实落地状态连接起来。

如果找不到对应 Fao，可能是设计还未实现；如果 Fao 已经实现但没有消费者，也可能暴露出业务设计与实现路线脱节。两种情况不能混同。

七、现在可以形成的阶段性认识
我认为这次已经可以明确三件事。

第一，WORK_MAP §3–§6 的确存在推导关系。

§4 解释重要总体方案的业务选择；§3 组织整个市场过程；Feature Narrative Stack 辨认各层 Feature；§5 用多视图保证设计完整和相互一致；§6 把 Feature 与现行方法、参数和业务边界对应起来。

它们不是四个按顺序执行、彼此独立的产物。

第二，P01–P13 和 WMF01–23 是同一套设计的两种视角。

P 描述过程，WMF 描述其中具有市场含义的 Feature。它们有多对多关系，也都不能直接当成二十三个或十三个独立 Fao。

第三，观察迭代不宜按 WMF 编号从头扫到尾。

更有价值的思路是：先明确 U2/U3 希望达成的某项具体业务判断，再结合 WORK_MAP 找到支撑它的必要业务关系，在真实行情中检验这段关系，并沿错误影响修改相应 LOCAL_CONTRACT。

不过，这里还有一个需要继续理解的地方：WORK_MAP 当前选用的 U2-C 方案，虽然是有业务理由的首选设计，但原始资料明确没有把它当作已经由真实数据证明的最优方案。

因此，未来观察不一定只是在旧 U2-C 方案内部修改细节。真实数据也可能暴露：这项总体方案本身相比 A、B 或更简单的分组方法，并没有形成原本希望的业务增量。

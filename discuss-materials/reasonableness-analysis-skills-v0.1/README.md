# 合理性分析 Skills V0.1

本包包含三个初版 Skill：

1. `business-expectation-derivation`：业务预期推导与可观察化
2. `business-evidence-comparison`：业务预期—真实证据对照
3. `business-discrepancy-diagnosis`：业务偏差诊断与 Owner 决策材料

README 不是第四个 Skill，只规定三者的协作方式。

---

## 1. 核心判断：不要把流程写成僵硬的“完整预期 → 全量证据 → 诊断”

人进行业务观察时，常常不是先把完整预期一次性想完，再开始看数据。真实过程更接近：

```text
已有业务意图
→ 形成少量最小预期
→ 看少量真实样本，理解输入和场景
→ 补充／修正候选预期
→ 冻结当前一轮预期
→ 做正式证据对照
→ 对偏差进行诊断
→ 必要时产生下一版预期
```

因此，三个 Skill 采用**渐进式预期—证据循环**，而不是瀑布式流程。

但“可以边看边想”不等于允许事后解释。必须保留：

- 当时已有的业务预期；
- 当时可见的证据；
- 证据出现后新产生的候选预期；
- 哪一版预期用于哪一轮正式对照；
- 后续为什么修订。

---

## 2. 两条并行轨道

### 2.1 事实准备轨道

可以在预期尚不完整时先做：

- 查字段定义；
- 查代码和处理链；
- 检查数据缺失、重复、错位；
- 抽取小样本；
- 找到具有明显差异的局部场景；
- 弄清 actualTime、confirmTime、参数版本和对象范围。

这条轨道只回答“数据和实现实际上是什么”，不提前判定“业务上就应该是什么”。

### 2.2 业务判断轨道

进入正式支持／反证判断前，至少要有一份**最小可检验预期包**：

```text
BusinessIntent
JudgmentTarget
ExpectationStatement
ExpectationOrigin
ApplicableConditions
FalsifierOrCounterEvidence
EvidenceNeeded
ExpectationVersion
```

不要求把所有场景、阈值和例外一次性写全。

## 3. 渐进式预期冻结协议

### 3.1 状态

```text
SEED
    刚从 Owner、业务目的或实现中提取，尚未充分细化

WORKING
    已能指导小样本探索，但仍允许补充适用条件

FROZEN_FOR_COMPARISON
    用于某一轮正式证据对照；本轮内不得无痕改写

REVISED
    根据新证据形成的新版本，保留 supersedes 和修订理由

RETIRED
    已被证据反驳、被 Owner 否定或不再适用于当前目的
```

### 3.2 何时可以开始看证据

满足下面四项即可，不必等待完整预期：

1. 已知要判断什么业务对象或处理阶段；
2. 至少有一条可被支持或反驳的候选陈述；
3. 已标明它来自 Owner、业务推导还是实现；
4. 已声明当前不知道什么。

### 3.3 何时必须冻结

以下情况必须先冻结本轮预期：

- 要给出“符合／不符合预期”的正式判断；
- 要做多个方案效果对照；
- 要建议改需求、改参数或改实现；
- 要把结论交给 Owner、叙事迭代或实现角色。

### 3.4 证据发现新模式时怎么办

不能把旧预期直接改成“原来就这样”。应当：

1. 保留旧预期与它对应的对照结果；
2. 新建 `BUSINESS_INFERRED` 候选预期；
3. 写明它由哪批证据诱发；
4. 使用新版本进行下一轮对照；
5. 若涉及真正的业务取舍，再提交 Owner。

## 4. 三个 Skill 的协作关系

```text
business-expectation-derivation
    形成 ExpectationRegister、InputSuitabilityAssessment、ScenarioExpectations
              ↓
business-evidence-comparison
    形成 EvidenceComparisonPackage、支持／反证／缺失证据和效果对照
              ↓
business-discrepancy-diagnosis
    沿处理链定位偏差、设计区分性实验、形成 OwnerDecisionPacket
              ↓
可能回到前两个 Skill 形成新版本
```

三者不是只能顺序调用：

- 只缺字段和代码事实时，可先做事实准备，再回到预期推导；
- 小样本观察发现新场景时，可从证据对照返回预期推导；
- 诊断发现原业务预期本身不充分时，可生成新的候选预期；
- 已有清晰 Owner 预期和干净数据时，可快速直达证据对照。

## 5. 快速路径与完整路径

### 快速路径

适用于：Owner 预期较明确、处理链较短、数据字段可靠、只需判断少量局部场景。

```text
最小预期包
→ 3～10 个代表性位置
→ 支持／反证／未决
→ 只对明显偏差做诊断
```

### 完整路径

适用于：预期含糊、处理链长、多个参数组、时间确认复杂、要提出改动或做效果统计。

```text
预期来源拆分
→ 输入三层检查
→ 场景矩阵
→ 证据清单与来源核验
→ 条件化对照
→ 偏差诊断
→ 低成本区分性实验
→ Owner 决策或后续改动请求
```

## 6. 本版中的来源与新增设计边界

### 由现有材料直接支持的部分

- 高频标准化中，“参数组选择”与“应用选择结果”是两个不同阶段；
- 紧密组具有更新、确认结束和持续身份；
- actualTime 与 confirmTime 需要分开；
- Pending、DataUnavailable、ValidEmpty、NoOccurrence 等不能混同；
- 候选关系或紧密组不自动等于业务上有意义的组；
- 不能用实现行为自动证明业务设计正确。

### 本次新增的 Skill 设计

- 预期三种来源的统一标签；
- 最小可检验预期包；
- 渐进式预期冻结；
- 事实准备轨道与业务判断轨道分开；
- 三种不确定性的路由规则；
- 三个 Skill 的输入输出合同和回环方式。

---

## 7. 首轮验证建议

先用高频标准化跑两个问题：

1. 原始候选高频是否适合承担“覆盖重要拐头”的目的；
2. 在输入可解释的位置，`select` 与 `merged` 分别造成了什么信息变化。

再选一个性质不同的用例（如跳空或贴近转折）检验这些 Skill 是否真正可迁移，而不是只会复述高频标准化的固定步骤。

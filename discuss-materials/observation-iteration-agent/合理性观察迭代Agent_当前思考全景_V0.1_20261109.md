# T03 合理性观察迭代 Agent：当前思考全景（V0.1）

> **性质**：2026-11-09 前序讨论中仍有效认识的整理；属于观察迭代 Agent 建设的候选讨论材料，尚非 Owner GO、正式 Agent harness/workflow、团队协议或已验证运行能力。
>
> **来源说明**：本篇把此前“合理性观察与迭代 Agent 当前思考全景”的聊天正文整理为独立 Markdown；该轮原本并没有生成同名独立附件。只保留后续讨论认可的认识，被修正或放弃的早期安排不作为规则重复列出。
>
> **对象范围**：T03 是“观察迭代 Agent 的设计与建设”；T03-UC01 为突破表现真实试点，T03-UC02 为高频标准化的跨用例验证。本文不为新的 Agent、Runner、运行实例或特征版本创造未经核实的正式技术身份。

## 一、目标和性质

### 1.1 观察迭代想完成什么

以已经经过现有特征生产流程的特征为对象，利用真实市场数据认识其现有业务表达；识别值得研究的不合理现象；追溯相关的原始业务意图、需求细化、实现准备、实现及运行环节，判断应在哪里、如何进行修订；把可以执行的方案交回相应生产工作；在新结果出现后继续观察，判断是否解决以及下一步是否值得推进。

观察迭代不等同于已有 ReqConform 的需求符合性验收。ReqConform 主要回答“实现是否符合冻结需求”；合理性观察还需要回答“即使符合现有需求，特征表达的业务含义是否合理”。但这不意味着在业务观察时可以跳过实现一致性问题：当具体问题指向实现时，需要沿相应层次核实。

### 1.2 建设目标与具体用例分开

- **T03**：获得可以用于其他特征的专业观察迭代能力，而非只完成某一版突破表现的修改。
- **T03-UC01（突破表现）**：让 Agent 独立重做此前的真实观察、问题研判工作，并继续推进尚未完成的后续迭代；运行本身也用来检验和修订 Agent 方法。
- **T03-UC02（高频标准化）**：在首版能力形成后检验能否迁移到不同性质的特征场景；不能先验认定它与突破表现的具体观察路径完全相同。

观察迭代成果与“Agent 是否真正具备可复用专业能力”的验证结论必须分别形成，不把业务用例做完自动等同于 Agent 建设完成。

## 二、与既有特征生产体系的关系

### 2.1 上游是什么

既有特征生产系统由需求细化、实现准备、实现三个专业团队承担不同生产阶段。它们的团队运行结果、正式采用的阶段档案、特征版本和具体运行实例是不同对象。观察迭代的输入在业务覆盖上包括这三个团队的相关完整成果；实际消费时，应首先定位目标特征及有效版本的正式档案，再按问题需要追溯原始运行产物与事实证据，避免混用不同版本和历史工作区。

主要需认识的上游内容：

| 来源 | 对观察迭代有意义的信息 |
|---|---|
| 需求细化团队 | 原始业务意图、特征外部边界、责任块关系、责任块内部判定和计算逻辑 |
| 实现准备团队 | 实现绑定、验收观测合同、已使用的特征运行实例及参数 |
| 实现团队 | 实际实现、输入输出与必要中间结果、ReqConform 验收与交付/集成事实 |

这里的“全部成果”表示完整的可追溯输入范围，不表示每次必须预先把三个阶段所有历史运行文件全部复制给 Agent。

### 2.2 与三个团队是反馈关系，而非代替关系

观察迭代 Agent 不承担现有三个团队各自正式需求修订、Haskell 实现、包装、编译、归档和集成。它判断哪里需要修订、应当怎样修订，并形成相应专业交付；具体修订由适当的既有生产团队在获得授权和正式输入以后完成。修改后的新结果再返回观察迭代工作。

因此，不宜直接把它看作现有实现团队末尾的一个新的符合性验收 Agent。它是以已生产特征为对象、可以反向触发多阶段修订的专业能力；是否建立独立 lane／团队及怎样接入 Runner，仍属于运行方案设计问题。

## 三、绘图、观察数据与完整运行数据的边界

这部分的具体工具对象、关系与文件夹对应，另见同目录《绘图与观察数据体系_核心对象关系与文件夹对应_初版_20261109.md》，此处只保留对专业工作安排的影响。

- AI Data 在 UPlot／CAEGraph 等基础上，组织观察图、定位时间窗、图对应特征切片及案例交付包。观察 Agent 是既有功能的**使用者**，不负责建设画图功能。
- 现有图与其对应数据已经可用于本次观察时，准备工作视为已完成；不能为了固定一个统一流程而要求重新画图。缺少必要工具能力时，应提出外部工具需求，不能自动归入观察 Agent 的开发职责。
- AI Data 图对应数据与完整特征运行结果是**不同对象**：前者服务于观察图上的市场过程；后者可包含输入特征、各责任块中间输出及最终输出，供具体问题的计算追查使用。二者可以重叠但不能替代。
- 图与图数据的一致性是工具自身应保证的性质，不另设观察 Agent 的独立工程验收任务。若实际发现工具缺陷，按其归属反馈处理。
- 平台 Sof、数据源、实际数据覆盖和日历应该有独立、可复用的说明来源；尚未证实存在完整统一的数据集目录，不能把每次补充数据知识都变成观察 Agent 的业务产物。
- 早期设想的概览到局部图的人机操作方式可以在实际使用时研究，不先强制规定成所有特征观察都必须经过的固定阶段。

## 四、当前成立的专业工作主线

### 4.1 第一步：取得可用的观察依据

从正式生产成果和已有工具取得当前特征的真实输出、相应市场数据以及可用图形。起始时原则上使用现有运行实例已经采用的特征计算参数，不在观察前单独进行参数合理性优化。使用不同品种、范围或必要的展示组织，不等于允许无记录地修改被观察特征本身。

若已具备相应观察图与数据，第一步无需重做；若需调用既有 AI Data/UPlot 能力，则使用已有功能；若工具本身需要新增功能，应作为外部工程需求处理。实际应怎样组织数据、图形与深入局部的顺序，在专业观察中可以逐步形成，不先固定为“AI 一定先看图”。

### 4.2 第二步：实际观察并识别值得深入的问题线索

观察的上层目的是判断“现有特征是否合理、充分地表达了原本希望表达的业务现象”。对于突破表现，原有业务意图包含对不同性质突破结果的区分；对实际输出分布和市场路径的观察，均应服务于这个更上层目的。

**不能把总体目的与具体发现方法并列成三种同层次技巧。** 例如“预期的四类表现是否得到有效表达”属于总体观察问题；“某些实际市场过程与其分类不符”“不同统计量呈现值得研究的差异”等属于其下可能展开的观察证据与线索。

“看图”只是沿用人类观察习惯的简称。对于 AI，当前较自然的做法可能是优先处理图对应的结构化数据，针对需要认识走势形态和上下文的情形再查看图；但这是**候选工作方式**，不是已经验证最好的统一操作顺序。Agent 应合理使用数据、统计、图形、具体案例及必要的进一步取数。

具体观察可以从整体结果进入案例，也可以从典型市场过程返回全量数据。此时形成的是有事实依据、值得继续追究的**问题线索**；不能把一个现象（例如某类别计数为零）自动等同于需求或实现错误。

### 4.3 第三步：研判需要修订什么以及怎样修订

这一步的目的不是独立完成一份“问题原因分析报告”，而是：

> 对观察发现的不合理现象，沿生产链调查，找到真正不合理的环节、判断应当修订的位置和范围，研究出适当的修改方案。

需要区分但不必机械固定检查顺序：原始业务目的本身需要修订、需求细化未合理表达业务意图、实现准备的实例或接口有问题、实际代码与需求不一致、数据/运行使用或图形工具出现问题。一个问题可能跨多个环节，应识别最早需要纠正的有权位置及后续受影响范围，而不能绕过需求直接在实现侧私改。

诊断计算和源码、研究候选改法、比较反例与相互依赖的方案，都是服务于修订决定的活动。问题认识与修改方案在成果中仍应区分，避免“指出某个阈值过严”便被当作已经给出可以实施的修订。

多个问题可以并行取证，但当它们共享分类边界或底层指标时，应联合考虑。例如此前的 P1（趋势持续被排除）、P2（明显回吐但最终盈利）、P3（结束价格没有充分进入路径回吐统计），分别涉及业务分类和路径计算，并非三个可以互不影响地独立改阈值的问题。先前提出的具体比例阈值只是候选试算，不属于已批准的最终修订方案。

### 4.4 修订由原有生产体系实施，之后继续观察

观察 Agent 形成有证据和作用范围的修订交付，外部有权团队按相应合同修订、验收、交付和归档。观察 Agent 本身不实施这些正式修改，但应能在新版本结果出现以后，沿用之前的观察线索、案例和方案，判断原问题是否改善、是否产生新问题，以及是否继续观察。

这构成“观察迭代”，而不只是一次性的观察诊断。是否可以由一次 Agent 调用涵盖全部环节，与外部长程协作如何持续驱动，应分开设计。

## 五、实质产物：目前只冻结语义，不提前定死文件数

根据现有共识，至少要保存以下**互不等价的专业内容**：

| 内容 | 应表达什么 | 关系 |
|---|---|---|
| 观察事实与问题线索 | 实际观察到什么、在哪些市场过程/特征结果中成立、有哪些具体证据和待核疑问 | 一个问题可由多个案例揭示 |
| 问题研判及修订方案 | 真正不合理之处在哪个环节、为什么需要修改、应怎样修订、影响哪些后继内容、怎样验证 | 一个方案可同时处理多个相关问题 |
| 新结果的迭代评价 | 旧问题的效果对比、保留的反例、新问题、尚未完成事项、继续或收束依据 | 可以跨多次修订累积有效认识 |

另有运行实例、图与关联数据、完整特征运行取数、原始日志等**证据和操作资产**。它们不应因存在而强行转写成重复的正式业务报告。

Agent 方法自身的验证和改进记录应与特征业务结果分开，原则上由能力建设与审查一侧负责，不让被验证的 Agent 只凭自评宣布能力已成熟。

这些内容将来如何组织为一份或多份正式工件、哪个有独立 template、何时原地更新，以及修订交接的 schema，尚未正式确定。现阶段不以早期 O1～O6 的文件编号作为已定的运行合同。

## 六、首次试点如何检验 Agent 的真实能力

T03-UC01 既是业务迭代，也是对 Agent 工作方法的压力测试。前期人类与 AI 对突破表现的分析可作为**独立复核资料**，不应完整预先注入 Agent 使其仅复述已知答案；但必要的原始需求、上游生产档案、真实数据和工具仍应作为正常输入。

已知检查方向包括：能否自己从实际结果发现重要现象；能否结合价格过程形成独立业务预期；能否定位到具体生产环节和规则；能否提出相互协调的修订方案；能否避免仅凭分类编码、最终盈亏或单个数值直接下强结论。

之前得到的观察事实、已经确认的业务解释、尚未确认的候选分类阈值，成熟度不同，不可全部当作“金标答案”。首轮Agent有效性需要从实际执行证据判断，而不是仅看最后文档是否提到已知P1～P3。

## 七、实际运行组织：方向已有，架构尚未定稿

当前已有两层不同的执行机制：

1. **现有三个专业团队及共享 Runner**：按各自 `team.yaml` 调用 Codex 专项 Agent，维护团队内 handoff、PASS/STOP 与修订；这不等于完整跨团队运行主控。
2. **外部长程体系**：Owner 授权，主控 Codex 负责调度/监控/回交，ChatGPT 专业 Pro 负责专业决定和签发工单，Worker Codex 负责操作仓库及运行团队。长程合同仍有需要在真实运行中验证的闭环与门禁。

初步倾向是让观察迭代专业能力独立于现有三个团队，先用 Codex 专项 Agent 开展 T03-UC01 真实试点，ChatGPT Pro 在重要判断与成果接收上发挥专业作用，Worker 和主控负责现有机制下的执行与接续；同时通过实际对照判断复杂业务思考是否需要不同运行载体。**这只是候选试点路径，不是已经作出的 Codex 优于 Web 的结论。**

应该先分清：一次专业调用的输入/输出与结束边界、修订方案交回生产团队的接口、修改后如何回到同一观察迭代任务的长程持续运行关系。不能只因为有一个长程主控，就默认它已经支持观察—修订—再观察全部自动闭环。

## 八、怎样落入 Agent 运行材料

需遵守 `feature-production-agent` 已有的《Agent运行材料分层规范》与《Agent运行材料内部结构规范》，但必须在专业对象和过程明确后再分层落档：

- **专属 harness**：稳定专业职责、随特征变化的业务输入和实质性业务输出；不重复执行步骤。
- **workflow**：观察、问题研判、修订交付、再观察的实际处理方式、结果更新和阻断/交接方法。
- **template**：确定需要结构化正式工件时，规定章节、字段及填写方式；不承担分析决策规则。
- **runner-facing prompt**：保持薄入口，引用正式材料而不是复制全部方法。
- **支撑合同及测试资产**：按实际需要另存，避免在四类主材料中重复展开。

本篇只是建设前的专业构想与讨论成果，不能据此直接宣称观察 Agent 已可运行或已通过跨用例验收。

## 九、当前已确定与仍待决定的边界

| 事项 | 当前认识 |
|---|---|
| Agent 的专业目的 | 已形成：对已生产特征做真实业务合理性观察、形成修订方案并参与迭代评价 |
| 上游输入 | 原则已形成：消费三团队的有效成果及所需实际特征/数据；具体输入入口和身份合同待定 |
| 图形和取数 | 现有能力与新 Agent 职责分开；图与其关联数据、完整运行数据必须区分 |
| 观察方法 | 有基本上层目的与线索/案例层次；如何高效、充分发现问题仍需通过试点研究 |
| 研判与修订 | 定位应修订环节并形成实施依据，不单设“只分析原因”的终点 |
| 实质工件 | 观察事实与线索、问题及方案、迭代评价等内容已辨识；最终文件结构待定 |
| 与生产团队交接 | 修订执行不归观察 Agent；准确合同、版本与反馈入口待定 |
| 执行载体 | Codex/ChatGPT Pro 不凭直觉定优劣；首版真实试点安排待正式选择和授权 |
| 长程循环 | 需明确单次调用、跨团队修订、同任务接续；不能假定现有协议已自动闭合 |
| 允许停止/结束的条件 | 已确定不能把一次运行 PASS 当作整个迭代完成；具体业务充分性与停止边界待研究 |

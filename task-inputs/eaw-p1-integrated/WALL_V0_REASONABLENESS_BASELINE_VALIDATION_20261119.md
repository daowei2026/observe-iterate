# Wall V0 合理性基础验收思路与遗漏

> 整理日期：2026-11-19  
> 性质：讨论稿／后续落地基线  
> 来源：围绕“当前 Wall 合理性任务是否达到曹总所说的分而治之与基础验收目标”的上一轮讨论回复。

## 一、总体判断

当前思路已经抓住曹总反馈的主干：

```text
不要求 Wall 在所有市场位置都正确；
先在清楚场景中验证它是否明显像那么回事；
既看正例，也看明确非例；
跨品种、跨时间检查；
基础 Wall 达到基本可信 Gate 后，再向 Build、AttackSegment、Absorb 推进。
```

更准确地说，本轮不是要证明：

```text
Wall 整体合理 / 整体不合理
```

而是先形成一个有边界的基础验收：

> 在当前 Wall 应该能够表达的清楚场景里，它能不能把真实盘口过程压成一个不过度泛滥、发生—维持—变化—结束基本讲得通的生命周期对象；在明确不属于 Wall 的场景里，它是否没有乱认；在不同品种、时期下，这个结论是否还能成立。

这与曹总所说的“不是要求处处都合理，而是在该合理的地方明显合理；中型、大型事件在该有的位置确实像那么回事”是一致的。

---

## 二、Wall 不是原始客观事实，但它没有直接涨跌预测承诺

Wall 是比较基础的业务对象，但不能称为原始客观事实。

原始事实是：

```text
某时刻买一／卖一的价和量
某时刻最新成交价
某时刻方向成交
```

Wall 则是经过一系列判断构造出来的：

```text
大挂单
→ 墙砖
→ 同一对象
→ 价带
→ Alive / Dormant / End
```

因此更准确的说法是：

> Wall 是一个基础业务事实对象，但不是原始客观事实；它是对可见流动性防守位置的业务化认知。

Wall 自身一般不承诺：

```text
出现 ask Wall 后价格一定下跌
出现 bid Wall 后价格一定上涨
```

但它仍然带有局部空间和受力方向的含义：

- ask Wall 是上方卖侧可见流动性；
- bid Wall 是下方买侧可见流动性；
- 它们可能成为向上或向下攻击的目标。

因此，后续价格可以作为辅助理解，但不能把：

```text
Wall 后没有反转
```

直接判成 Wall 错了。

Wall 可以被守住，也可以被打穿。真正的胜负需要 AttackSegment、Absorb 及后续价格共同判断。

## 三、当前基础验证框架是成立的

当前思路实际包含四项基础工作。

### 1. 看总体发生情况和密度

这用于判断特征有没有退化：

```text
是不是几乎处处都有 Wall
是不是 Wall.Start / End 反复发生
是不是大量 Wall 一闪而过
是不是 BandUpdate 密密麻麻
是不是某些状态永远不发生
```

这是必要的。

但密度是多少，本身不能告诉我们密度是否合理。例如：

```text
每小时 20 堵 Wall
```

单独看无法判断好坏，还需要继续看：

```text
这 20 堵是不是 20 个真正不同的明显对象？
还是同一个过程被错误切成 20 个 wall_id？
这些 Wall 是否大部分只有 1～2 Tick？
普通盘口时段是不是也一直有 Wall？
```

所以密度不能压成一个总数，至少应拆成：

| 密度类型 | 具体问题 |
|---|---|
| 候选密度 | LargeQuote、WallBrick 出现多少 |
| 对象密度 | 新建了多少个 `wall_id` |
| 事件密度 | 每堵 Wall 有多少 BandUpdate、StateChange |
| 活跃覆盖率 | 全市场时间中有多少比例处于 Alive / Dormant |
| 生命周期密度 | 短命 Wall、单砖 Wall、反复重建有多少 |

当前代码有稀疏化机制，但没有一个自动的“不过密判定器”。它只输出 Start、BandUpdate、StateChange、End 等稀疏事件，以及逐 Tick 状态轨迹。

### 2. 找几个真实发生的过程，看结果是否和人看到的一致

这是当前最核心的业务验证。

例如从原始盘口中独立选出一个清楚过程：

```text
一笔明显大挂单出现
→ 在相近价位持续存在
→ 价格多次接近
→ 挂单并未立刻消失
→ 价带有有限移动
→ 最后挂单衰弱、价格远离或被穿越
```

然后看 Wall 是否输出：

```text
LargeQuote
→ WallBrick
→ Wall.Start
→ Support
→ BandUpdate
→ 状态变化
→ Wall.End
```

这回答的是：

> 在一个人也会认为“这里有一段可见流动性对象”的位置上，特征是否讲出了同一过程。

这正对应“该有的地方，确实看起来是那么回事”。

### 3. 找几个没有这样发展的地方，看算法是否也没有误认

这个方向同样正确，但不能只从“算法没有输出 Wall 的地方”选负例。

否则只能证明：

```text
算法自己没选的地方，算法果然没选。
```

应从原始行情独立选出几类明显负例：

```text
单 Tick 大挂单闪现，下一 Tick 消失；
普通盘口量波动；
挂单虽大但相对当前环境明显偏薄；
价格快速跳档造成的瞬时大值；
同一价位没有持续存在证据；
明显属于另一种复杂现象，而不是持续 Wall。
```

然后检查：

```text
是否没形成 Wall；
若形成了，是否很快且合理地结束；
是否被错误拖成一个长生命周期。
```

### 4. 跨品种、跨时间做分层检查

“多个品种、多段时间”不应只随机多抽几个，而应有结构地覆盖：

```text
品种：
rb / hc / i 等不同盘口量级和流动性

时间：
不同年份、不同市场环境

Session：
日盘 / 夜盘 / 开盘附近 / 普通时段

行情状态：
平静 / 活跃 / 快速趋势 / 来回震荡

对象强度：
明显大过程 / 中型过程 / 边界过程 / 明确负例
```

这样才能发现：

```text
当前参数只在某个品种有效；
QT 在某时期失真；
固定 3 Tick 在高活跃和低活跃市场含义不同；
同一 Wall 逻辑在不同 Session 出现系统差异。
```

## 四、是不是只要大挂单就进入 Wall 生命周期

答案是：接近，但不完全是。

当前逻辑是：

```text
LargeQuote
AND not thin
→ WallBrick
```

因此 LargeQuote 本身还不一定进入 Wall。如果它同时被判为 thin，默认不会成为 WallBrick。

一旦成为 WallBrick：

### 当前该侧没有活 Wall

```text
直接创建新的 Wall
→ Wall.Start
```

### 当前该侧已有 Wall，且新 Brick 与 core 足够近

```text
并入当前 Wall
→ 维护同一个 wall_id
→ 更新 support / band / core
```

### 当前该侧已有 Wall，但新 Brick 与 core 太远

```text
旧 Wall 以 relocation 结束
→ 同一个 UTI 创建新 Wall
```

所以从当前实现看，可以近似说：

> 每一个 WallBrick 都会被放进某一个 Wall 生命周期：要么创建新 Wall，要么加入当前 Wall，要么结束旧 Wall 后创建新 Wall。

但不能说：

> 每个 LargeQuote 都一定进入 Wall。

因为还有：

```text
LargeQuote + thin
→ 不是 WallBrick
```

另外，Wall 创建以后，即使后续不再是 LargeQuote，也可能凭：

```text
near + not thin
→ Support
```

继续维持生命周期。

## 五、不能只看已输出的 Wall

如果所有 WallBrick 都会被放进某个 Wall，那么只观察：

```text
Wall.Start → Wall.End
```

很容易只看到算法“已经认为是 Wall”的样本。

为了形成相对完整的看法，必须同时有三组样本。

### A. 输出正例

```text
算法形成了 Wall；
人也觉得是一段清楚的 Wall 过程。
```

### B. 输出反例

```text
算法形成了 Wall；
人看原始数据后认为只是瞬时大挂单、普通波动或错误串联。
```

这用于检查误报。

### C. 潜在漏报

```text
原始盘口中，人认为存在持续、明显的流动性对象；
但算法没有形成 Wall，或被切得支离破碎。
```

这用于检查漏报。

C 组不能从 Wall 输出反推，必须从原始行情或独立候选方法中选。

这是当前方案最需要补上的地方之一。

## 六、当前方案仍缺的五项

### 1. 先给当前 Wall 一个明确的语义边界

本轮应先写清楚：

> 当前 Wall V0 只承诺表达：一档盘口中，由异常大挂单启动、在相近价带由局部存在证据延续、最终以远离、变薄、迁移或超时结束的可见流动性对象。

同时明确不承诺：

```text
预测未来一定反转；
覆盖多价位同时存在的复杂墙；
准确还原 L2/L3 真实委托；
单独判断守住还是打穿；
覆盖全部流动性防守形态。
```

没有这个边界，负例很容易选成“当前版本本来就没打算表达”的复杂情况。

### 2. 不只看最终生命周期，还要找第一次分歧层

例如发现一个假 Wall，不能只说：

```text
这个 Wall 不像。
```

要向前追：

```text
QT 是否太低
→ LargeQuote 是否误判
→ Thickness 是否没有否决
→ WallBrick 是否过松
→ Support 是否过度维持
→ identity 是否误合并
→ End 是否过晚
```

这正是“分而治之”落到执行上的意义。

### 3. 参数至少要有一个非退化基线

不需要先把参数调到最终最优，但要先排除：

```text
Dormant 和 End 完全同条件；
几乎所有 Tick 都是 Support；
大部分 Wall 只有一个 Tick；
BandUpdate 近乎逐 Tick 发生；
Wall 活跃覆盖接近全时段。
```

否则后面看到的大量异常会一直混杂“参数根本没给好”的影响。

### 4. 要有覆盖账本，而不是只积累案例

最终不能只是：

```text
看了 20 张图；
找到了 5 个问题。
```

应当能回答：

| 单元 | 已看什么 | 当前结论 |
|---|---|---|
| LargeQuote | 跨品种正反例 | 支持 / 部分支持 / 未决 |
| Thickness | thick / thin / neutral |  |
| WallBrick | 正例、误报、漏报 |  |
| Support | 持续性、过度延寿 |  |
| Identity | 合并、切分、relocation |  |
| Band / Core | 漂移、稳定 |  |
| Dormant / Revival | 可达性、时点 |  |
| End | 各 reason |  |

这样才能说当前 Wall 的基础验收到什么程度。

### 5. “通过这一关再看后三个 Feature”应是软 Gate，不是绝对串行

顺序总体合理：

```text
先把 Wall 基础对象弄到基本可信
→ 再看 Build / Attack / Absorb
```

但不必等到 Wall 完美才继续。

更合适的 Gate 是：

```text
Wall 在明确正例中能够稳定形成对象；
identity 和 band 基本可解释；
事件不退化；
关键已知问题的影响范围明确。
```

达到这些，就可以进入下游。

而且下游有时会反过来暴露 Wall 问题：

```text
Attack 总在 Wall 刚 Dormant 时被切断；
Build 经常因 wall_id 反复重建而断裂；
Absorb 绑定到了错误 Wall band。
```

所以实际应当是：

```text
Wall baseline
→ 下游验证
→ 反馈修正 Wall
```

而不是一次性的完全验收。

## 七、关于“带价格含义的特征看后续价格”

这个思路有价值，但需要区分两类特征。

### 直接结果型特征

如果特征语义本身就是：

```text
突破
反转
衰竭
阻挡
```

那么后续价格是主要验证对象。

### 基础对象型特征

Wall 更像：

```text
这里存在一个可见流动性对象。
```

后续价格只能做辅助验证。

例如：

```text
Wall 被明显攻击但价格未穿过
→ 支持“守住”的解释

Wall 被持续成交穿越且 presence 消失
→ 支持“打穿”的解释
```

但：

```text
Wall 后价格没有反转
```

不能单独反驳 Wall 的存在。

因此 Wall 的首轮验收优先级应是：

```text
对象是否真实
→ 生命周期是否合理
→ 作为攻击 / 吸收坐标是否可用
→ 最后才看完整价格结果
```

## 八、可执行的 Wall V0 验收步骤

### 第一步：全局非退化统计

检查：

```text
对象密度
事件密度
活跃覆盖率
生命周期长度
单砖 Wall 比例
短时间 Start-End 比例
BandUpdate 密度
各状态和 End reason 的可达性
```

目的不是直接给“合理分数”，而是找退化模式。

### 第二步：独立选案例

每个品种、时间层至少准备：

```text
明显正例
明确负例
潜在漏报
边界例
复杂未覆盖例
```

案例选择依据尽量来自原始盘口，而不是 Wall 输出。

### 第三步：逐过程对照

每个案例画出或整理：

```text
原始 best 价量
QT 与 LargeQuote
局部厚薄
WallBrick
Support / ThinTouch
wall_id、band、core
状态计数
Start / BandUpdate / StateChange / End
```

回答：

```text
第一次业务分歧出现在哪一层？
```

### 第四步：分类问题

```text
Bug
参数值
参数关系
标准化
方法设计
当前覆盖外
证据不足
```

### 第五步：形成基线结论

最终结论不应只写“Wall 合理／不合理”，而应类似：

> 在 rb、hc、i 的若干正常 Session 和清楚中大型可见流动性场景中，当前 Wall 能／不能稳定形成稀疏且连贯的生命周期；对瞬时大挂单和普通盘口波动的误识别情况如何；对潜在真实 Wall 的漏报情况如何；当前在多价位共存、快速迁移或复杂交战场景中不作承诺；Dormant 分支目前因参数关系退化。

这已经非常接近曹总要求的当前阶段成果。

## 九、当前判断

当前思路已经达到曹总反馈的主要方向：

```text
不要求处处正确；
先在清楚场景中验证它明显像那么回事；
有正例，也有明确非例；
跨品种、跨时间看；
基础 Wall 可信后再向下游推进。
```

仍需补上的关键点是：

1. **Wall 不是原始客观事实，而是无直接涨跌承诺的基础认知对象。**
2. **不能只从当前 Wall 输出选案例，必须独立寻找潜在漏报。**
3. **密度要拆成对象、事件、生命周期和活跃覆盖，而不是一个总数。**
4. **每个异常要定位到 LargeQuote、Thickness、Brick、Support、Identity、State 或 End 的最早分歧层。**
5. **Wall 通过的是一个“基本可信 Gate”，不是等到完美以后才看下游。**
6. **后续价格对 Wall 是辅助验证；完整的守住／打穿需要 Build、AttackSegment、Absorb 和价格结果共同判断。**

## 十、后续落地时建议形成的产物

为了把以上讨论转成实际任务，建议后续至少形成：

```text
1. Wall V0 当前语义承诺与不承诺范围
2. Wall 非退化统计规格
3. Wall 场景采样矩阵
4. WallAuditTape 字段规格
5. Wall 逐过程对照模板
6. Wall Reasonableness Coverage Ledger
7. Wall 基本可信 Gate
8. Wall → Build / Attack / Absorb 的软 Gate 与反馈协议
```

这些内容应当用于判断当前四个合理性 Skill 具体缺什么、需要修改什么，以及下一轮数据准备和实际 Run 应如何落地。

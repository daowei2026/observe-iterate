## 2. 两条线共同的业务目标

Owner 的主任务不是建立一套更大的工程体系，而是：

```text
取得指定实例的完整结果
→ 根据统计情况找明显不合理问题
→ 把问题分析清楚
→ 经 Owner 确认后处理具体修改
→ 修改后的正式实例重新运行、重新统计
→ 继续找不合理部分
→ 本特征达到当前深度后再进入下游
```

工作群中明确：当前“都还先只做了根据统计情况找明显不合理问题这部分”，预期是“把这种明显不合理的问题处理了，再根据观察继续找不合理的部分”；暂时不把主要精力放在偏复杂的改法上，主要还是找问题和分析问题。

WALL 与 F 两条基础线并行安排；当前采用联合基础 Barrier：两条基础线都达到本轮允许释放的状态后，再启动各自下游。

## 3. 对 Feature 理解的 Owner prompt

Owner 对 WALL、F 都要求获取：

1. 从输入到输出有哪些关键业务对象或业务概念；
2. 每个业务对象包含、依赖或围绕哪些属性／参数；
3. 上游对象到下游对象的业务处理逻辑；
4. 不只讲数据处理关系，还要讲时序逻辑；
5. 对应到正式 Feature、Event、occurrence 和输出字段。

来源消息：

- WALL：`01a1fc44-d378-7543-ae41-f024d2f65a74`；
- F：`01a1fc43-8cef-7043-8194-c18581490b0d`。

Owner 对“业务对象”的纠偏是：

> 业务对象至少应对应行情数据中的某种现象、某种位置或持续业务过程。实例编号、模块、配置或处理步骤本身不因为重要就成为业务对象。业务处理可能围绕对象的多种属性判断，这些属性也要列清楚。

来源消息：

- WALL：`01a1fc5d-bc31-7cb3-8db3-a4e1fa16bd6c`；
- F 对应引用：`01a1fc5f-f83b-7340-a61a-26dc2f26e805`。

F 还有一项明确关注：候选组属性很多，应按“围绕候选组进行什么业务处理”组织属性层次，而不是只给一张平铺字段表。来源消息：`01a1fcb3-7a3d-77d2-ab95-6643eb314275`。

## 4. 统计与合理性分析的 Owner prompt

Owner 对两条线共同要求：

> 统计每个业务对象的发生次数，比较它与上游对象的发生次数和发生位置，看有没有异常；目标是发现特征结果的合理性问题，即有没有不符合预期的点。若为此还需要其他统计，可以一并做，并给出统计和合理性分析结果。

来源消息：

- WALL：`01a1fc73-3905-7f81-99b3-9d8bd72e2309`；
- F：`01a1fcc5-688c-73e2-934c-d40c66ac485a`。

进一步明确：

- 有业务方向的对象需要按方向分别统计；WALL 中即 bid / ask 分开。来源：`01a1fcb7-2bdb-7fb0-b162-95b63510d91f`；
- 表格每一行需要有“含义／计数口径”解释，不能只给数字。来源：`01a1fcc3-a117-7cb2-9a1b-7d979ff6125c`；
- F 要能直接看懂每个品种原有多少贴近转折，最终形成多少候选组／多少次候选组，不能把不同口径的几行混在一起。来源：`01a1fcda-94c4-7cf0-b2df-a51a6815dc8a`；
- 统计只是发现入口。数量多或少不能自动代替业务判断，但显著比例异常需要继续沿业务链找首次阻断和设计原因。

这些是核心问题，不要求 AI 机械穷尽一张通用指标清单。AI 可以按业务对象链补充真正有助于判断的统计，但应说明为什么需要，不能把补充指标无痕变成新的 Owner 完成条件。

## 5. WALL 中已经形成的 Owner 判断与边界

### D1｜正式输出位置不一致

事件位置与 trace 对同一 Wall 的表达不一致，本身就是输出合同问题，不以某个下游是否消费其中一种输出为前提。当前远端修复已作为本轮输入。

### D2｜同拍 Dormant 与 End

Owner 的判断顺序：

1. 先定位两种输出各自的设计逻辑和参数；
2. 每个问题独立分析，不用 D3、D4 的联动替代 D2 的根因；
3. 已判断 End 的同拍不再输出 Dormant，因为对象已经结束，休眠没有业务意义。

来源消息：`01a1fda0-63a4-7d52-a5dc-e3e89950e43d`、`01a1fe18-f902-7461-9aa7-99ecf96ca823`。当前远端修复已作为本轮输入。

### D3｜同价短暂变薄后结束并重建身份

Owner 提出的业务对比是：价格远离后再回来并出现明显挂单，可以保留原身份；若价格没变，只是从薄挂恢复为厚挂，却被当成新 Wall，明显值得质疑。该问题当前改法复杂、边界还不够确定、发生比例不高，所以暂不作为本轮重点修改，但不得写成问题不存在。

来源消息：`01a1fdd9-9a2e-7cd1-b338-09640910bb22` 及工作群反馈。

### D4｜支撑恢复仍按 far 结束

Owner 要求先解释真正触发 End 的条件，而不是把 D4 混入 D2。最终确认的关键疑点是：有效支撑已经恢复，连续远离仍未被打断。Owner认可“支撑恢复应当被考虑进来”的修改方向。来源消息：`01a1fe18-f902-7461-9aa7-99ecf96ca823`、`01a1fe1e-e433-7833-8021-9613cfb51731`。当前远端修复已作为本轮输入。

本轮 WALL 要在最终版本上重新统计 D1、D2、D4 的状态，量化 D3 的当前范围，并继续发现新的明显合理性问题。

## 6. F 中已经形成的 Owner 判断与边界

1. 当前明确异常是：三年 5m 钢铁板块贴近转折数据上，候选组发生极少；问题单位是整体转化比例和识别范围，不是某一个 610 分钟案例是否应该通过。
2. 需要区分实际转折、首次可知／确认、尺度选择、候选组建立等时间；比较每两个实际转折之间的间隔，以及实际转折到确认的等待，理解比例关系和确认后可使用的时间。
3. 需要解释 Δ 是什么，为什么期限按 Δ 的倍数给；不能因为代码用了该形式就自动认为合理。
4. 当前同一个 Δ 的不同倍数承担不同作用。Owner指出“晚到期限的倍数”可以单独参数化，不能只因它当前写死就提前判为不可调。

## 7. 具体修改必须经过 Owner 确认

2026-11-22 Owner 新增明确要求：流程中的“具体修改”不能由 AI 在诊断后直接采用，必须先回 Owner 确认。

### AI 可直接做

- 读取代码、需求、历史 Chat 和已有结果；
- 在锁定正式范围上运行、导出、统计和分析；
- 编写分析脚本、报告和可复现检查；
- 做不改变正式版本的局部诊断或隔离实验；
- 形成具体修改方案、影响范围、备选方案、验证方法和拟修改 diff；
- 复用 Owner 已确认并已锁入任务输入的代码提交或参数实例。

### 必须先回 Owner 确认

- 修改正式 Feature 代码、业务规则或输出合同；
- 修改正式参数实例、硬编码业务常量或配置；
- 改变输入数据处理方式、正式品种、时间范围、尺度、用例或工作区；
- 把局部诊断 patch 提交、推送或采用为本 Run 的正式版本；
- 改变下游依赖或释放范围。

标准路由：

```text
诊断与证据完成
→ ModificationProposal
→ Owner 确认／修改／暂缓
→ 只有确认后才实施正式修改
→ 重新运行和重新统计
```

已由 Owner 在此前 Chat 中确认并已提交的 WALL D1、D2、D4 修复，不需要在本 Run 中重复确认；它们是当前锁定输入。Owner 后续提供并锁定的 F 新参数实例同理。

## 10. 不应被误写成 Owner prompt 的 AI 补充

以下内容可以作为控制实现，但不是 Owner 原话，不得反过来限制业务工作：

- `FeatureReleaseGate`、`PASS_WITH_ACCEPTED_LIMITATIONS` 等状态名称；
- `JOINT_BASE_BARRIER` 这个技术命名；
- AI 自行列出的某张固定统计大全；
- 固定抽样数量；
- 为每个工程动作新建 Skill、schema 或审批层；
- “必须先完整重做 FeatureUnderstandingPackage”之类的形式前置。

若这些实现选择与 Owner 当前 prompt 冲突，应以本文件中的直接意图和最新确认优先。

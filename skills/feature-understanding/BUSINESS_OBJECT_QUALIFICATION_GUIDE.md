# Feature 理解补充｜怎样判定业务对象

> 本文件是 `feature-understanding` 的轻量实践补充，不新增 Skill，也不要求所有 Feature 使用同一对象模型。

## 1. 为什么需要这份补充

理解 Feature 时最常见的偏差，是把运行实例、配置、算法模块、字段集合或处理步骤都列成“业务对象”。这会让后续统计失去业务单位：表里数了很多东西，却不知道它们在行情上代表什么。

业务对象应首先回答：

> 它对应行情、交易或业务处理中的什么现象、位置、持续过程或有身份的关系？

## 2. 业务对象的最低资格

一项内容通常至少满足下列一类，才进入 `BusinessObjectModel`：

1. **行情现象或位置**：某个可被业务识别的位置、片段、挂单、转折、关系或组；
2. **持续业务过程**：有形成、更新、延续、结束或修订过程；
3. **有身份的业务实体**：后续 occurrence 可以继续引用同一个对象；
4. **有业务意义的组合对象**：成员关系和组合方式本身影响后续处理；
5. **正式输出承诺的对象**：Feature 明确声称它输出或维护该业务结果。

不要求对象一定长期持续，也不要求一定有数据库 ID；一次性对象仍可通过来源、时间和组成获得身份。

## 3. 通常不是业务对象的内容

除非当前业务明确把它们结果化，否则以下内容通常只是工程或处理事实：

- Feature 实例、参数集和代码版本；
- 处理器、函数、类、模块和阶段编号；
- 日历、工作区、缓存和结果表；
- 阈值、基线、计数器、滚动窗口；
- 当前状态值、调试字段和显示图层；
- 为计算方便产生的临时数组或中间 DataFrame。

它们可以很重要，应进入实现来源、参数、中间判断或结果字段映射，但不因重要就成为业务对象。

## 4. 对象、属性、关系现象和参照量分开

### 对象

可被创建、引用、更新、结束或比较的业务单位。

### 属性

描述对象当前怎样，例如位置、方向、强度、状态、年龄和成员。

### 关系现象

对象与当前行情、其他对象或参照位置之间发生什么，例如靠近、远离、支撑、薄触、相容、覆盖。

关系现象可以升级为独立对象，但必须有自己的身份或生命周期；否则记录为对象的关系属性或中间判断。

### 参照量

为了判断对象而计算的阈值、基线、分位数或标准化量。参照量不是市场中又发生了一个对象。

## 5. 从处理链识别对象

沿真实代码问：

```text
原始输入中出现了什么业务单位？
哪一步给它增加了新的业务资格？
哪一步形成了新的身份？
后续是在更新原对象，还是创建另一个对象？
结束后能否恢复原身份？
同一拍多条 occurrence 是同一对象的多个变化，还是多个对象？
```

例如，一条观测先被判为异常，再被判为可以形成持续对象的证据：三者可能是同一输入在不同判断下获得不同业务含义，并不必然是三个彼此独立的对象。

## 6. 计数粒度同时登记

同一个业务链往往需要多个粒度：

```text
原始观测次数
连续现象片段数
唯一业务对象数
事件 occurrence 数
状态转换次数
生命周期数
```

`FeatureUnderstandingPackage` 应说明这些单位怎样互相映射。后续统计再根据问题选择，不把表行数当作对象数。

## 7. 时间语义

若对象存在多个时间，分别记录：

```text
actual_time      业务现象实际发生在哪里
observed_time    系统何时取得原始证据
confirm_time     何时具备确认资格
publish_time     何时正式输出
end_time         何时结束或确认结束
```

只有代码和结果确实存在这些区别时才建立；不为所有 Feature 强造五个时间字段。

## 8. 输出建议

除原 `BusinessObjectRecord` 外，可在包中增加一个简短判别表：

| 候选项 | 归类 | 理由 |
|---|---|---|
| 某行情位置或持续过程 | 业务对象 | 有业务现象、身份或生命周期 |
| 某状态码 | 对象属性／状态 | 描述对象，不另有身份 |
| 某门槛判断 | 中间判断 | 参与资格或结束判断 |
| 某历史分位数 | 参照量／参数事实 | 用于判断，不是行情对象 |
| 某执行实例 | 运行绑定 | 定位实现和参数 |

无法确定时保留为 `UNCONFIRMED`，不要为了填满对象清单作强行分类。

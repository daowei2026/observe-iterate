# E｜Worker 派单合同

> 本文件只规定 E 中哪些真实操作需要派给 Worker、在什么专业产物之后派、两类工单的边界以及回交关系。E 自己的专业判断和阶段推进见 [WORKFLOW.md](WORKFLOW.md)。通用 C/D/W 身份、授权、工作区和 Return 仍以 [longrun Worker 工单模板](../../../longrun/templates/WORKER_ORDER.md)及长程协议为准。

## 1. 与 E 专业 Workflow 的对应关系

E 的专业 Workflow 不把“派单”写成业务判断节点。本文件把专业产物与 Worker 工单单独映射：

| E 专业产物／位置 | 需要的真实操作 | 工单 | Worker 回报由哪个专业节点消费 |
|---|---|---|---|
| E1 `执行与核图基准` 已形成 | 在真实环境运行 D 定义，并做权限内机械修复 | **W1｜运行与有限修复** | E2 `消费候选运行事实并判断问题性质` |
| E2 判断仅剩机械执行问题，且 E1 基准未变 | 按新 revision 继续运行或修复 | **新的 W1 revision** | 仍回 E2 |
| E4 `正式取数准入记录` 已形成 | 对已经接受的脚本／HTML／运行正式导出图数据 | **W2｜正式取图数据** | E5 `消费正式数据事实并核对图与数据` |
| E5 判断只是导出动作错误，且取数准入未变 | 按新 revision 重做导出 | **新的 W2 revision** | 仍回 E5 |

Worker 工单只负责生产 E 需要消费的事实和实物；不能替代 E2、E3、E4、E5 的专业判断。

## 2. 为什么采用两份模板，而不是一张统一模板

E 中有两个时间上、权限上都不同的操作阶段：

```text
W1：运行 D 定义、在权限内做机械修复、产出候选最终图
    ↓
E2／E3：专业判断问题性质，核对并接受最终图
    ↓
E4：形成正式取数准入
    ↓
W2：只针对已接受图，导出正式 CAEGraph 图数据
```

W1 开始时，最终脚本和最终 HTML 尚未被 E 接受，因此不能同时授权“正式图数据导出”。若合并为一张工单，Worker 会在专业准入尚未形成时提前决定正式取数基准。

所以采用两份独立模板：

- [W1｜运行与有限修复工单模板](RUN_REPAIR_ORDER_TEMPLATE.md)
- [W2｜正式取图数据工单模板](DATA_EXPORT_ORDER_TEMPLATE.md)

两份模板分别是各自操作阶段的完整起点；不需要再造第三份统一大模板。共同的身份、授权和工作区字段由通用 `WORKER_ORDER.md / ORDER.json` 提供。

## 3. 两类工单的共同封面

每份实际工单都必须先满足通用长程合同，并至少包含：

```text
run_id / work_order_id / parent_delegation_id
issuer / issuer_call_id / worker / return_to
E 阶段当前专业工作身份
输入原件的精确 GitHub commit 与路径
实际工作区、仓库、分支、环境和数据根
允许执行的操作、允许写入的位置和 Owner authority_quote
预期交付物、验证方法、预算和停止条件
失败／部分／效果未知／重复执行时的回报
幂等／重跑条件和当前在途动作身份
```

阶段模板只补充 W1／W2 的专业内容，不替代通用 `ORDER.md / ORDER.json`。

## 4. W1｜CAEGraph 运行与有限修复

### 触发条件

E1 已完成 `执行与核图基准`，并固定：

- D 完整定义版本；
- C2 当前展示预期／当前预期 HTML；
- 外层特征实例、B 位置和运行环境；
- Worker 可自主修复范围；
- 候选脚本、候选 HTML、日志和 patch 输出位置。

### Worker 可以做

- 在真实环境运行 D 的完整 CAEGraph 定义；
- 收集标准输出、错误、运行环境和数据版本；
- 修复工单明确授权的语法、导入、路径、确定 API 差异、明确类型转换和输出目录问题；
- 反复运行以验证这些机械修复；
- 生成候选最终脚本、候选 HTML、日志、patch 和未决问题清单。

### Worker 不可以做

- 更换品种、时间、多尺度位置或特征实例；
- 删除／增加业务字段；
- 改变 C2 的页面、主图／附图、图元、时间表达、标准化或交互业务语义；
- 另算近似值替代特征输出；
- 判断最终图是否符合 C2／D；
- 正式导出并交付 CAEGraph 图数据；
- 因为脚本跑通就宣称 `DATA_READY`。

### 回交

Worker 必须把事实和实物交回签单的 E executor，包括：

```text
实际执行输入版本
实际环境和数据版本
运行状态与日志
候选脚本和候选 HTML
逐项 patch：前后、原因、权限依据和语义影响
无法在权限内解决的问题
是否存在重复执行／效果未知
```

E2 再根据专业 Workflow 接受、返修或路由 B／C／D。

## 5. W2｜CAEGraph 正式取图数据

### 触发条件

只有 E4 已形成正式取数准入，且至少冻结：

- 被接受的最终脚本版本／哈希；
- 被接受的最终 HTML 版本／哈希；
- 对应 D 定义、C2 当前展示预期和最终运行编号；
- 外层特征实例、品种、时间、环境和数据版本；
- 需要导出的数据阶段与完整性要求。

### Worker 可以做

- 按已接受脚本和运行环境重现或读取同一有效运行；
- 导出工单指定的源数据、后处理数据、构图 CDS、视窗最终显示值；
- 生成图层／Renderer／CDS／源表映射；
- 记录行数、对象、时间范围、数据阶段、原值／显示值关系、缺失含义；
- 计算文件哈希并生成数据 manifest；
- 报告无法取得、部分取得、浏览器回调未完成或数据阶段不明等事实。

### Worker 不可以做

- 修改已接受脚本、图定义、位置、字段或展示语义；
- 为了方便导出而换另一版图；
- 从图像素、clip 后数据或标准化显示值逆推缺失业务原值；
- 只导出前几行预览却声称完整；
- 判断数据包是否在业务上可接受。

如发现必须修改图或脚本才能取数，Worker 应停止并回 E；旧正式取数准入不能继续沿用。

### 回交

Worker 必须交回：

```text
所绑定的最终脚本／HTML／运行身份
数据文件和 manifest
每项数据阶段、行数、对象和时间范围
图层到数据源映射
原值／显示值／转换关系
缺失、有效空、无 occurrence、未确认等语义记录
文件哈希和日志
部分／失败／效果未知及停止原因
```

E5 再完成图与数据一致性核对。

## 6. 重跑与新工单

- W1 只要 D、C2、实例、位置或环境基准改变，就必须签新工单或明确新 revision，不能无痕续用旧输入；
- W2 只要最终脚本、HTML、运行身份或取数准入改变，就必须重新签发；
- W1 的候选 HTML 不能作为 W2 的授权依据，除非 E3 已经正式接受并由 E4 形成取数准入；
- Worker 回报效果未知时，先对账，不立即重复执行；
- W2 导出错误可在取数准入不变时重试；发现图本身有误则取数准入失效，返回 E 专业 Workflow。

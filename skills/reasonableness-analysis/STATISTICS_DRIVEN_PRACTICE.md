# 合理性分析补充｜统计驱动实践规则

> 本文件补充现有全量统计、偏差诊断和参数标定 Skills。它不新增 Skill，不替代各 Skill 的原生输出合同，也不把 WALL、F 或任何单一用例固化为通用方法。

## 1. 统计项从业务链推导

不要先列一张通用指标大全。先读取 `FeatureUnderstandingPackage` 和 `CurrentReviewTarget`，画出最小业务链：

```text
原始观测／输入对象
→ 上游业务对象或资格
→ 中间判断
→ 主业务对象
→ 状态／生命周期
→ 正式输出
→ 下游可消费结果
```

统计优先回答：

- 每一级发生多少；
- 上下游对象怎样对齐；
- 转化或阻断发生在哪里；
- 哪类身份、状态、时间或正式输出出现结构冲突；
- 当前对象与历史累计对象的口径是什么；
- 不同业务条件下是否稳定。

Feature 没有生命周期，就不机械做生命周期统计；没有方向，就不机械分买卖侧；没有 actual/confirm 区别，就不强造延迟统计。

## 2. 多种计数单位不要混用

根据当前 Feature 选择适用单位：

```text
观测次数
连续片段数
唯一对象数
当前／责任内对象数
成员关系数
事件 occurrence 数
状态转换数
生命周期数
```

每项正式统计都说明：

```text
统计对象
计数单位
对象键
时间基础
是否去重
分母
同刻多 occurrence 规则
业务含义
能否仅凭该数判异常
```

表格或 HTML 中应给“含义与计数口径”，避免数字存在但业务上无法阅读。

## 3. 分层由业务维度决定

优先考虑：

- 对象或品种；
- 业务方向；
- 时间段、年份或市场阶段；
- Session；
- 参数实例；
- 由共享理解明确给出的环境条件。

只有当分层字段可靠、且它可能改变业务解释时才使用。具体品种、方向名称和时间范围属于任务输入，不写进通用 Skill。

## 4. 从原始或上游过程找潜在漏报

只看 Feature 已有输出，只能检查已识别对象。当前目标涉及覆盖时，还应从原始市场过程或上游业务对象中建立独立候选，再追踪它为什么没有进入主输出。

独立候选是筛查工具，不是真值。报告必须区分：

```text
潜在漏报候选
已确认漏报
因上游门槛被合理排除
证据不足
```

## 5. 抽样方法：没有固定万能数量

全量统计先覆盖全部数据；抽样用于理解、诊断和展示，不用于替代全量计数。

针对一个 finding，先选最小区分集：

1. 一个最清楚的代表位置；
2. 一个能够反驳最强竞争解释的对照位置；
3. 如 finding 跨分层，再选一个关键分层位置；
4. 如靠近参数门槛，再选边界内外各一个；
5. 如担心漏报，从原始／上游候选中选未输出位置。

随后按证据饱和扩展：新样本仍改变根因判断、适用边界或副作用认识时继续；连续新增样本只重复既有结论时停止。

不存在对所有 Feature 都有效的“固定抽 10 个”或“每类固定 3 个”。样本量必须写明选择理由和还不能代表什么。

## 6. 发现阶段：覆盖面与高置信度并重

发现阶段不是只追求广度，也不是看到一个异常就立即深挖。正确顺序是：

```text
在当前正式结果上完成适用业务面的统计与检查
→ 把执行者判断为明确值得处理的高置信候选先登记出来
→ 记录未升级观察和未覆盖范围
→ 形成当前结果绑定的候选队列快照
→ 再逐个进入责任逻辑定位和根因诊断
```

高置信判断由执行者结合以下内容作专业判断：

- 当前 Feature 的业务对象与身份；
- 状态、生命周期和正式输出合同；
- 上下游转化与业务分母；
- 全量／分层结果；
- 业务常识与当前 ReviewTarget；
- 可复现程度及替代解释。

以下仅为参考视角，包括但不限于：

- 对象、身份、状态或生命周期出现明显矛盾；
- 与明确业务语义发生强冲突；
- 核心转化或当前对象数量出现有业务基准支持的数量级异常；
- 多对象、多时期重复出现的结构异常；
- 正式输出之间不自洽。

这些不是穷尽清单、固定阈值或自动判错规则。执行者可以提出清单外候选；也可以在证据不足时不把清单内现象升级。每个升级候选都要说明：

```text
为什么不是普通波动
与什么对象语义、合同或数量关系冲突
现有证据支持到什么程度
仍需 D 阶段确认什么
```

Owner 明确提出的候选必须完成评估，但不预设它最终是实现问题、业务规则问题、统计口径问题还是非问题。

“队列冻结”表示对当前正式结果形成可追溯快照，不表示后续禁止新增候选。

## 7. 统计发现与业务判错分开

部分硬结构矛盾可以直接形成高置信候选，例如正式输出互相冲突、终结后继续更新或非法状态转换。

对象数多或少、生命周期偏短、某品种明显不同、某分支很少发生、参数变化后输出增加等，通常不能仅凭数值自动判错；但当它们与明确对象语义、业务分母和数量关系形成强冲突时，可以由执行者升级为高置信候选。

未升级的观察应说明“为什么暂不升级”和返回条件，而不是无痕丢弃。

## 8. 输出自洽不以使用方式为前提

同一 Feature 的正式事件、trace、对象表或当前状态若声称表达同一对象和同一时点，就应当自洽。

不能以“下游可能只读其中一张表”降低问题性质。若两个载体本来承诺的时间语义不同，应把差异写进输出合同；不能事后用“使用限制”解释未声明的不一致。

## 9. 代码符合性与业务合理性分开

诊断至少分别回答：

```text
ImplementationConformance:
  当前代码是否按现有规则执行？

BusinessReasonableness:
  该规则与业务对象、上游节奏和当前用途是否相容？
```

“没有代码 bug”不能关闭业务规则问题；“业务结果不合理”也不能在未定位前直接说成实现错误。

## 10. 参数能力审计包括硬编码常量

参数可修复性检查不能只看配置文件中已经暴露的字段。还要检查：

- 参与判断的固定倍数；
- 多个期限共享的派生常量；
- preset 中未暴露但具有业务作用的值；
- 同一量被多个阶段共同消费的耦合。

结论要区分：

```text
只改当前已暴露参数无解
当前实现能力完全无解
将某个业务常量独立参数化后可能可调
需要改变业务规则而非参数
```

不要把第一种扩大成第二种。

## 11. 诊断性干预不等于标定

在少量位置把参数改大、让一个反例通过，只能说明过滤机制或参数方向。

正式参数结论至少需要：

```text
TargetInclusionSet     明确应该保留的场景
TargetExclusionSet     明确应该排除的场景
HoldoutSet             未参与求值的场景
ConstraintPurpose      参数或期限承担什么业务作用
FullInstanceRun        完整实例重跑
GlobalProfile          修改后的全量统计
```

输出组数增加、覆盖某个延迟分位数或恢复一个案例，都不能单独作为成功目标。

## 12. 多 finding 的联合处理边界

每个 finding 先独立定位直接责任点。只有在以下事实成立时才联合求解：

- 共用同一状态变量；
- 共用同一参数且不能独立暴露；
- 修改一个规则必然改变另一个 finding 的输入；
- 业务上本来就是同一个联合约束。

否则分别处理，再做交叉回归。这样避免一个问题的验收目标掩盖另一个问题的真实原因。

## 13. 当前轻量闭环的停止条件

当 `CurrentReviewTarget` 明确只要求发现并处理明显问题时，可以在以下条件下结束本轮：

- 最新代码和参数已完整运行；
- 当前 ReviewTarget 内的已确认问题已经关闭；仅初始 ReviewTarget 明确为不阻断的范围外限制可保留并传递，AI 不得为释放而自行暂缓本轮高置信问题；
- 已完成当前正式结果上的高置信发现 pass，并形成 `FindingDiscoverySummary` 和候选队列快照；
- Owner 指定候选已有判断；
- 最新全量统计没有尚未进入处理的高置信 finding；
- 剩余观察需要复杂业务定义、证据不足或超出本轮范围；
- 已知限制、影响和返回条件已经传给下游。

这不是“Feature 已被全面证明合理”，而是当前业务深度下可以继续推进。

# 一、两个 Chat 背后真正形成的思考方法

这两个 Chat 最重要的并不只是最后找到了哪几个问题，而是你多次纠正 AI 后形成了一套更准确的分析方法。

## 1. 先找真正的业务对象，不能把工程模块当业务对象

WALL Chat 里，AI 最初把实例配置、计算模块等当成业务对象，你明确纠正了：

> 业务对象至少要对应行情中的某种现象、某个位置，或者一个持续维护的业务过程。

因此 WALL 的业务主链最终被还原为：

```text
一档挂单观测
→ 大挂单
→ 墙砖
→ Wall
→ Wall 的形成、延续、位置变化、休眠、恢复、结束
```

F 也一样。它的业务对象不是配置和处理器，而是：

```text
实际转折
→ 尺度选中的转折
→ 两两相容关系
→ 候选组合
→ 候选组
→ 候选组后续修订
```

这里还必须区分：

- 设计中的业务概念；
- 运行时产生的具体对象；
- 对象的成员关系；
- 对象的一次修订；
- 事件 occurrence；
- 同一个业务现象在半秒或五分钟数据上的重复观测。

这说明当前 `feature-understanding` Skill 的方向是对的，但还需要加入更强的“业务对象资格判断”和反例，防止执行者再次把实例、配置、模块、当前状态等机械地当成业务对象。现有 Skill 已要求还原业务对象、状态、事件和参数，但还缺少这次 Chat 中形成的判别力度。

---

## 2. 统计不能只是数输出条数，而要沿业务链逐级比较

两个 Chat 都不是从“最终 Feature 有多少条结果”停下来，而是继续比较：

```text
上游对象发生了多少
→ 其中多少进入下一阶段
→ 在什么位置进入
→ 哪一道门排除了它
→ 被排除的对象与被保留的对象有什么业务差别
```

WALL 中进一步区分了：

- 半秒观测次数；
- 同侧同价连续片段；
- Wall 身份数；
- 状态转换次数；
- 生命周期事件次数；
- 同拍多个 occurrence；
- 买侧与卖侧；
- 已识别对象和从原始盘口独立筛出的潜在漏报候选。

F 中则区分了：

- actual 转折位置；
- 首次知道该转折的 confirm 时间；
- 尺度选中时间；
- 两两相容关系；
- 候选组创建；
- 候选组修订。

这意味着新的统计 Skill 不能只规定“统计对象、状态、事件和生命周期”，还需要明确要求：

1. 每一行统计的业务含义；
2. 计数单位；
3. 是否去重；
4. 分母；
5. 对象身份键；
6. 方向、品种、时期等必要分层；
7. actual time 与 knowledge/confirm time；
8. 上游到下游的转化与首次阻断位置；
9. 从原始市场过程独立寻找潜在漏报候选。

当前 `feature-global-behavior-profiling` 可以继续使用，不需要推翻，但要把这些要求补进去。

---

## 3. “代码按自己的规则执行了”不等于业务合理

这是两个 Chat 的共同核心。

### WALL

问题 4 中，代码确实按照“成交价连续远离”结束 Wall，但当拍墙位上仍有 6196 手有效支撑。代码一致并不能证明业务合理。

### F

F 确实按照“actual 位置之后 6Δ 内必须完成首次准入”执行，但上游正常转折确认通常远远晚于 6Δ。代码没有违背合同，仍然可能让 Feature 的实际识别范围偏离原来的业务对象。

因此诊断必须分开：

```text
实现有没有按当前规则执行
≠
当前规则有没有合理表达业务目标
```

这条必须补进 `business-discrepancy-diagnosis` 的硬约束。现有 Skill 已要求定位最早责任阶段、区分事实和解释，并判断参数可修复性，基础是可用的；但这两个 Chat 说明还要再加强“实现符合性”和“业务合理性”的显式分离。

---

## 4. 输出错误不以“下游是否使用它”为前提

WALL 问题 1 是你非常明确的一次纠偏。

AI 一开始说：

> 如果下游只依赖事件恢复位置，这会造成问题。

你纠正为：

> 无论下游怎么使用，同一个 Feature 的事件输出和 trace 表达不同，本身就是不合理。

这个原则应该直接固化进 Skill：

```text
Feature 对同一对象、同一时点发布的多个正式输出必须自洽；
不能因为某个下游暂时不用其中一种输出，就把不一致降级成“使用限制”。
```

这不是展示问题，也不是下游适配问题，而是 Feature 输出合同问题。

---

## 5. 不能过早宣布“现有参数无解”，要先检查哪些常量其实可以参数化

F 中 AI 最初只看到了同一个 Δ 同时控制：

- `2Δ`：两个 actual 转折允许相距多远；
- `6Δ`：首次确认晚到多久还允许建组。

于是得出“保持 10 分钟共同性，同时接纳很晚确认，只改 Δ 无解”。

你随后指出：

> 6 这个倍数本身不能单独调大吗？

这才发现：

- “仅调 Δ 无解”是对的；
- “现有设计不能调”是过早结论；
- `6` 当前虽然是硬编码常量，但可以成为独立参数；
- 同时还要审查它与 `12Δ` 修订终点等其他期限的关系。

因此参数诊断前必须有一张完整的参数作用图：

```text
参数或常量
→ 定义位置
→ 是否暴露为实例参数
→ 所有消费位置
→ 派生关系
→ 与其他期限或状态的耦合
```

不能只检查配置文件里已经暴露出来的参数。

---

## 6. 敏感性实验不等于参数标定

F Chat 中第二次重要纠偏，是 AI 根据一个 610 分钟迟到案例推了 `K=122/128`。

你指出：这个位置本身还没有被证明应该纳入目标现象，不能为了让它通过而反推出参数。

于是结论被撤回。正确顺序应是：

```text
先说明 F 要覆盖什么共同转折
→ 哪些迟确认属于正常目标损失
→ 哪些迟确认确实因为业务时效不再有价值
→ 哪些只是为了有限维护责任而必须收口
→ 再看参数如何区分这些类别
```

不能把以下指标直接当标定目标：

- 输出组数变多；
- 恢复某个反例；
- 覆盖延迟分位数；
- 找到一个能让异常样本通过的 K。

当前 `feature-instance-calibration` 已经写了“不先枚举参数再按输出数量选值”“不把局部复算当完整实例证明”等原则，但这次执行仍发生了偏差，说明输入合同还需要更强：必须先有明确的 `ConstraintPurpose`、目标纳入类别、目标排除类别和未参与调参的留出场景。

# 二、WALL 到底要不要在修改后重新统计

## 结论：需要，而且不是可选项

但要区分两类工作：

1. **针对问题 1、2、4 的定向修复验收**；
2. **对修改后最终版本重新做完整全局统计和合理性发现**。

第一类已经在修代码 Chat 中做得比较充分；第二类还没有被它替代。

## WALL 当前四项状态

| 问题 | 当前状态 | 对新统计的影响 |
|---|---|---|
| 1. 事件位置与 trace 不一致 | TIS 分支中已修；补发位置更新并统一事件载荷 | 改变事件流数量与载荷，旧事件统计失效 |
| 2. 同拍 Dormant 后立即 End | 已改为先仲裁 End，不结束时才发 Dormant | 删除大量瞬时 Dormant occurrence，旧状态事件统计失效 |
| 3. 同价短暂变薄后反复 End、重建身份 | **未修改** | 仍是明确的已知未决问题 |
| 4. 有有效支撑时仍因 far_price 结束 | 已让 `support_flag` 清零远离计数 | 会改变结束时点、寿命、身份延续及后续新建，旧生命周期统计失效 |

问题 1、2、4 的实现过程记录在[修代码 Chat](https://github.com/daowei2026/observe-iterate/blob/feat/reasonableness-analysis-v0.2-20261120/ai_chat/%E6%A0%B9%E6%8D%AE%E7%BB%9F%E8%AE%A1%E6%89%BE%E4%B8%8D%E5%90%88%E7%90%86%E7%82%B9/wall%E7%89%B9%E5%BE%81%EF%BC%8C%E4%BF%AEfrp%E4%BB%A3%E7%A0%81.md)中，对应短提交为：

```text
19e6b15  问题1：位置事件一致性
4d06ec2  问题2：同拍 End / Dormant 仲裁
6618d4d  问题4：支撑恢复清零 far 计数
```

其中问题 4 使“有支撑当拍仍 far End”从 1,482 次降为 0，但它确实改变了 Wall 生命周期。问题 1、2 即使没有改变最终 trace，也改变了正式事件输出。

因此，旧统计只能解释旧版本，不能作为新版本进入下游的 Gate 证据。

## 为什么已有全年对照不能代替重新统计

已有对照主要证明：

- 指定缺陷消失；
- 允许变化范围符合预期；
- 某些不应变化的字段没有被多改；
- 回归测试通过。

它没有重新执行原来的开放式发现工作，例如：

- Wall 总数是否明显变化；
- 同价位反复重建是否变多或变少；
- End 原因分布是否转移；
- 薄触结束是否成为新的主导机制；
- Wall 寿命、单砖墙、短命墙分布是否改变；
- 新的状态序列是否出现；
- 问题 4 延后结束后，是否让问题 3 更集中；
- 新增 BandUpdate 是否造成新的同拍 occurrence 表达问题；
- 独立筛查出的原始盘口候选覆盖率是否发生变化。

所以正确流程是：

```text
最终修复版本
→ 先跑问题1/2/4的定向回归检查
→ 再做完整全局统计
→ 从新统计中重新寻找结构疑点
→ 新疑点继续诊断/修复
→ 行为再变化则重新统计
```

当前 V0.2 控制面本身也规定：实现、参数、设计或数据修改改变行为后，旧运行和旧全量统计失效，必须回到 Feature 运行和全量统计。

### 一个执行上的细节

WALL 是否必须重新计算全部 Feature 数据，可以留一个“正式接收现有最终产物”的入口：

- 若最终 D4 结果包仍在；
- 能校验输入范围、参数、源码 SHA、最终提交；
- 能被新 Run 正式登记为当前版本产物；

则可以复用结果并直接重新做完整统计。

否则就重新运行。无论是否复用已有结果，**完整全局统计必须重新做**。

# 三、WALL 的问题 3 不能在新 Gate 里消失

当前反馈说“问题 1、2、4 已改，问题 3 复杂，暂未改”。

但问题 3 不是已经被证明不存在，而是：

- 现象已确认；
- 同价、同侧、持续盘口过程中出现 23 个 Wall 身份；
- 原位短暂变薄会直接 End；
- 恢复后只能重建；
- 是否应保留身份仍需业务边界和规则处理。

所以新控制流程不能写成：

```text
问题1、2、4修好
→ WALL没有问题
→ 进入下游
```

必须显式保存问题 3 的状态。严格口径下，它应阻断 `WALL_BASE_STABLE`。若你决定当前阶段允许暂缓，则要形成：

```text
ACCEPTED_KNOWN_LIMITATION
```

并明确：

- 为什么暂缓；
- 影响哪些统计；
- 下游可能继承什么偏差；
- 在什么条件下必须返回处理。

“没有找到新的问题”不能覆盖“仍有一个已知问题尚未关闭”。

# 四、F 当前真正到哪一步了

F 的现状也不是“已经确定一个新参数，只差重跑”。

## 已经确定的部分

1. 最终候选组数量异常少只是一个入口信号，不是单凭数量判错。
2. 大量上游 M 尺度转折在真正进入两两相容和候选组判断前，就因 actual 起算的准入期限被排除。
3. 原始业务对象关注 actual 转折是否共同，confirm 时间是系统何时知道它，不天然构成共同性的反证。
4. 当前 `6Δ` 的原始设计动机主要是：
   - 让在线观察和历史处理有终点；
   - 避免对象一直开放、一直处理旧材料；
   - 早期还带有“三个 `2Δ` 邻域宽度”的结构解释。
5. 没有找到充分证据表明：
   - F 就是要识别“快速确认的共同转折”；
   - 正常转折应当大多在 `6Δ` 内确认；
   - 排除当前这么大比例是设计上预计并接受的。
6. 本批确认等待中位数达到 `22—56Δ`，而不是接近 `6Δ`。rb、hc、i 的 actual→首次收到确认中位数分别约为 280、270、110 个交易分钟。

## 还没有完成的部分

- `6` 应不应该参数化：方向上已经明确，可以参数化。
- 参数化后是否只影响首次准入，还是还要同步处理观察关闭、修订责任等期限：尚需形成准确合同。
- 新参数值究竟是多少：**没有确定**。
- 哪些迟确认样本应该纳入、哪些应该排除：尚未形成正式分类。
- 修改应落在 FRP、TIS 配置或两者之间怎样接线：还需要按现役代码精确落实。
- 修改后的 F 实例尚未形成可锁定的代码版本和参数实例。

所以 F 的正确前置不是直接写：

```text
把 K 改大
→ 重跑
```

而是：

```text
明确时间限制的业务作用
→ 分开“共同性、发现时效、有限维护责任”
→ 定义目标纳入/排除类别
→ 将 K 及相关期限合法参数化
→ 固定一版有依据的参数实例
→ 全量运行 F
→ 重新做上游—下游转化统计
→ 再找合理性问题
```

这仍然符合你说的“改了参数之后再统计”，但仓库里不能假装参数值已经从 Chat 中得到。

# 五、两条线应该怎样并行

我按你后半段更具体的表达，暂时理解为采用 **联合释放 Gate**：

```text
WALL 基础闭环 ──┐
                 ├─ 两边都达到 BASE_STABLE
F 基础闭环 ─────┘
                       ↓
                 才启动各自下游
```

也就是说，不是 WALL 先完成就立即单独释放，而是等 WALL 与 F 都通过基础特征 Gate，再启动下游批次。

这不是技术上唯一的方式。两条线没有业务依赖时，也可以各自通过就各自释放；但你现在说的是“WALL 和 F 都没有找出新的合理性问题之后，再跑它们下游”，所以新计划应把它写成：

```yaml
release_policy: JOINT_BASE_BARRIER
```

而不是靠主控临场理解。

## 两条基础线内部仍应串行

```text
WALL：
最终代码版本
→ 实例运行或正式接收现有结果
→ 定向修复回归
→ 全局统计
→ 发现/诊断/修改循环
→ WALL_BASE_STABLE

F：
规则目的与参数合同
→ 参数化实现
→ 固定实例
→ 全量运行
→ 全局统计
→ 发现/诊断/修改循环
→ F_BASE_STABLE
```

跨线并行，线内闭环串行。这与当前“合理性分析内部严格串行”并不冲突；现在缺的是明确写出“多个独立特征闭环可以在多 Run 层并行”。

# 六、下游不是全部同时启动

## F 的下游关系已经比较明确

当前任务输入明确写了：

```text
F = CommonPriceTurnGroupCandidatesFrp
Q = PostTurnGroupDirectionalOrganizationFrp
V = CommonTurnGroupValidityFrp
```

Q 需要准确的 F 实例，V 又需要准确的 Q，而 Q 由 F 构造。 

因此正确依赖是：

```text
F stable
→ Q 运行和合理性闭环
→ Q stable
→ V 运行和合理性闭环
```

Q、V 不应该因为同一个构造入口会返回 `f, q, v`，就被当成可以同时独立放行。

当前 F 输入文件还明确排除了 Q、V，并且绑定的是旧 FRP/TIS 提交，因此不能直接把它当成新 F 闭环的输入原件。

## WALL 下游范围现在还不够精确

现有 EAW P1 集成输入中可以看到 Wall、Build、Attack、Absorb、方向大成交等证据，但文件自己也明确说，不能据此自动认定它已经冻结了完整 P1 Feature 范围。

所以 WALL 下游正式启动前，需要单独形成：

```text
WALL_DOWNSTREAM_SCOPE
WALL_DOWNSTREAM_DEPENDENCY_GRAPH
```

明确：

- 哪些 Feature 是本轮下游；
- 它们分别直接依赖 Wall 的哪些输出；
- 哪些可以并行；
- 哪些必须先后；
- 修改后的 Wall event/trace/lifecycle 哪些版本进入下游；
- 旧 CAEGraph 和旧下游缓存哪些已经失效。

不能仅凭“EAW P1 整体”让执行 Chat 自行扩范围。

# 七、仓库不能只增加一个新 control 文件夹

新 control 版本是必要的，但单独增加它不够。当前需求至少涉及四层：

| 层次 | 应解决的问题 |
|---|---|
| 专业 Control | 单个 Feature 的统计—诊断—修改—重跑闭环，以及基础特征向下游释放的 Gate |
| Campaign / 任务输入 | WALL、F 两条线的并行关系、联合 Gate、下游依赖和具体版本 |
| Skills | 把两个 Chat 中形成的方法固化下来 |
| Longrun 运行层 | manager/executor 都在 Codex、直接操作 Linux、零 Worker、多 Run 并行和跨 Run 汇合 |

比较合适的目录形态是：

```text
control_v0.3/
├── README.md
├── 01_L0_统计驱动的特征合理性闭环与下游释放.md
├── 02_L1_本特征运行与全量行为统计.md
├── 03_L1_疑点诊断_实现修正_参数标定与回流.md
├── 04_L1_基础特征稳定Gate与下游版本释放.md
├── 05_多特征并行与联合释放Gate.md
└── 06_节点输入输出和完成状态.md

task-inputs/wall-f-parallel-20261121/
├── OWNER_INTENT.md
├── CAMPAIGN_RUN_GRAPH.md
├── WALL_BASE_RUN_INPUT.md
├── F_BASE_RUN_INPUT.md
├── WALL_DOWNSTREAM_SCOPE.md
├── F_Q_V_DEPENDENCY.md
├── VERSION_LOCKS.md
├── WORKSPACE_BINDINGS.md
└── KNOWN_ISSUES_AND_RELEASE_POLICY.md

longrun/profiles/
└── CODEX_NATIVE_DIRECT_EXECUTION.md
```

这里的分工是：

- `control_v0.3/` 写通用方法，不写死 WALL 和 F；
- `task-inputs/wall-f-parallel-20261121/` 写这次具体任务；
- `longrun/runs/<run_id>/` 仍保存真实运行状态；
- Codex/Web/Worker 的物理运行方式放 `longrun`，不塞进专业 Control。

旧 `control/` 应保留，作为 V0.2 历史来源，不应直接覆盖。当前根 README 明确把它定义为“严格串行的合理性分析候选 V0.2”。

# 八、现有 Skill 哪些能复用，哪些需要更新或新增

## 现有 Skill：复用并升级

| Skill | 判断 | 需要补的内容 |
|---|---|---|
| `feature-understanding` | 可复用 | 业务对象资格判定；对象与属性归属；设计概念与运行实例区分；形成/更新/修订/替代关系 |
| `feature-global-behavior-profiling` | 可复用 | 观测/片段/身份/事件/修订多种计数口径；方向分层；上游转化；发生位置；actual/confirm 时间；独立漏报候选 |
| `business-discrepancy-diagnosis` | 可复用 | 输出自洽不依赖下游使用；代码符合性与业务合理性分离；约束原始设计意图追溯 |
| `feature-instance-calibration` | 可复用 | 先冻结约束用途和目标类别；硬编码常量参数化审计；禁止用单案例反推值；敏感性实验与正式标定分开 |

## 当前明显缺的能力

### 1. Feature 实例真实运行 Skill

现有 Control 写了“运行 Feature”，但仓库里没有一个足够明确、通用的 Feature 实例运行 Skill。需要负责：

- 锁定代码、参数、数据、日历、品种和时间；
- 真实运行；
- 缓存与旧结果处理；
- 输出完整性和读取验证；
- 形成可被全量统计消费的 `FeatureRunPackage`；
- 允许正式接收已有结果，但必须验证版本和哈希。

这与 CAEGraph 的 E Skill 不同。

### 2. 实现修正与回归验证 Skill

WALL 修代码 Chat 已经实际形成了一套很好的方法：

```text
定位最小责任层
→ 建独立分支
→ 新测试能在旧代码复现失败
→ 做最小修改
→ 定向反例通过
→ 全量同输入比较
→ 明确允许变化与禁止变化
→ 独立读回验证
→ 提交代码和结果包
```

当前 Control 只是把实现问题路由到“外部实现修正”，但没有把这套过程变成 Skill。新闭环里如果再次发现实现问题，这个缺口会再次依赖临场发挥。

### 3. 业务规则目的与设计沿革还原 Skill

F Chat 中“为什么存在这个期限、它究竟想筛选什么”不是普通参数标定，也不完全是场景选择。

需要一个专门产物，例如：

```text
ConstraintPurposeRecord
├── 原始业务目标
├── 规则首次出现的原因
├── 后续修改的原因
├── 明确规定的后果
├── 能推断但未明说的内容
├── 完全缺少证据的内容
├── 约束承担的多个作用
└── 哪些作用不应再由同一个参数混合承担
```

它可以新增为独立 Skill，也可以扩展到 `business-expectation-derivation`，但不能继续隐含在诊断 Chat 的自由分析中。

# 九、Codex 执行、不要 Worker：我理解的正确改法

你的意思不是取消角色区分，而是取消不必要的物理中转层。

仍然保留逻辑角色：

```text
controller
manager
executor
```

但物理运行改为：

```text
manager  → Codex thread
executor → Codex thread，直接拥有本 Run 的 Linux 工作区
worker   → 不创建
```

每条线可以是：

```text
WALL Run
├── Codex manager thread
└── Codex executor thread
    └── /独立的 WALL workspace

F Run
├── Codex manager thread
└── Codex executor thread
    └── /独立的 F workspace
```

这样：

- 不需要 Web Chat；
- 不需要 ChatGPT executor 再给 Worker 写工单；
- 不需要在 Web、Codex、Linux 附件之间反复搬运；
- Skill executor 自己在其工作区运行、检查、产出并回 manager；
- manager 仍只维护 Workflow 和状态，不替 executor 做专业工作。

现有长程协议已经支持多 Run 交错运行、每个 Run 独立 manager/executor，也允许 executor 直接执行且 `workers` 为空，但现在主要只把这一点写给 E Skill。

现有 schema 事实上也允许：

```json
"workers": []
```

只是 `workers`、`accepted_worker_refs` 等字段仍保留在兼容合同里。

所以最稳妥的做法不是立即破坏性删除所有 Worker 合同，而是增加：

```text
CODEX_NATIVE_DIRECT_EXECUTION profile
```

规定：

- 所有 Skill 都允许直接交给 Codex executor，不仅是 E；
- `workers=[]`；
- 不签发 W；
- executor delegation 直接携带工作区、允许写面和操作授权；
- manager 与 executor 都新建于本 Run，不能复用其他 Run 的线程；
- 旧 Run 和旧 Worker 路径继续作为历史兼容。

等这套方式稳定后，再考虑真正的 V3 schema 删除 Worker 字段。

# 十、现有多 Run 支持还差一个“联合 Gate”

当前 `MULTI_RUN_CONTROLLER` 已支持：

- 一个主控交错管理多个独立 Run；
- Run A 等待时 Run B 继续；
- 不同 Run 使用独立工作区；
- 各自独立 manager 和 executor；
- 零 Worker 的 Codex executor。

但它把各 Run 当成独立运行单元，还没有正式表达：

```text
WALL_BASE_STABLE
AND
F_BASE_STABLE
→ 才释放下游批次
```

所以需要新增一个很薄的 Campaign 层，而不是再创建一个“跨 Run 专业 manager”。

例如：

```yaml
campaign_id: OI-WALL-F-CLOSURE-20261121

base_runs:
  - wall_base_run
  - f_base_run

release_policy: JOINT_BASE_BARRIER

release_requires:
  - wall_base_run.feature_release_gate == PASS
  - f_base_run.feature_release_gate == PASS

downstream:
  - wall_downstream_graph
  - q_run
```

这个 Campaign Gate 只检查各 Run 已经产生的专业 Gate，不替两个 manager 判断业务问题。

## 1. WALL 修复分支目前还没有可远端锁定的版本

修代码 Chat 记录的是 TIS：

codex/wall-output-consistency-20261121
19e6b15
4d06ec2
6618d4d

启动前必须完成以下一种：

```text
推送该分支到 daowei2026/tis
```

或：

```text
合并到一个专门的新 Run 分支
```

然后在任务输入中锁定完整 40 位 commit。

## 2. F 还没有“可运行的新实例版本”

当前 F 任务输入仍锁定旧版：

```text
FRP @ 67711c...

```

而且当前修改方向尚未形成：

- 代码提交；
- 参数化合同；
- 完整参数实例；
- 适用范围；
- 相关期限的一致性约束。

# 十二、我目前形成的最终判断

1. **WALL 必须对最终修改版本重新做完整全局统计和合理性发现。**已有定向回归不能替代这一步。

2. **WALL 问题 3 必须作为已知未决问题显式处理。**严格口径下它阻断基础特征稳定 Gate；要暂缓则必须形成明确接受记录。

3. **F 必须在规则目的、参数化方式和具体实例确定后全量重跑。**当前 Chat 没有产生可直接采用的新 K 值。

4. **WALL 与 F 两条基础闭环可以并行；每条线内部仍按运行—统计—诊断—修改—重跑顺序执行。**

5. **按你现在的表达，采用联合基础 Gate。**两边都稳定后才释放下游。

6. **F 的下游是有顺序的 F→Q→V，不能把 Q、V 当作无依赖并行任务。**

7. **WALL 的下游 Feature 集合和依赖关系仍需单独冻结，不能由“EAW P1”这个名字自动扩出来。**

8. **新 control 目录是必要的，但还要同步修改 Skills、具体 task-input 和 longrun 执行配置。**

9. **manager 和 executor 都迁到 Codex，直接操作各自工作区；新 Run 使用零 Worker profile。**旧 Worker 合同先保留兼容，不让它继续出现在新流程的正常路径中。

10. **下一步不应直接开 Run。**应先形成文件级改造清单，并优先解决 WALL 远端版本和 F 新参数实例这两个启动阻断。

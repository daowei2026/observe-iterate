# 管理接收与实际接续：工具参考

执行修订：`2026-09-22-coordinator-dispatch-v3`。协调者日常操作统一[08](08_自然语言运行提示_v0.3.md)；本页提供既有工具和v3消息命令。Python标准库/本地Git；不自动接受业务，不内置手机/调度。

## 1. 既有地图与接收保持

workmap-binding/v1指纹和资格保持，旧接收不因升级自动生效。v2仅在原管理接收中明确迁移，先核在途，不重做业务或另开审核轮。保留overview、streams/map/task、owner_sources、rule_paths、watch_roots、receipt_path和manager_role。

v2的shared_overview_anchors与各scope overview_anchors需覆盖每个唯一锚点，共同目的和约束不得隐藏在兄弟区。reader_output_roots只允许在watch_roots内专用窄目录，不能排除整个业务面。阅读输入和结果分别处理；reader_fingerprint不含被验证后产生的读图报告，fingerprint仍反映管理接收变更，task_payload_sha256是原任务字节。

## 2. 原snapshot/check/dispatch

```sh
O=runtime/overlay
python "$O/tools/workmap_gate.py" snapshot --repo . --ref "$EXACT_COMMIT" --binding "$BINDING" --scope "$SCOPE" --output /tmp/input.json
python "$O/tools/workmap_gate.py" check --repo . --ref "$EXACT_COMMIT" --base-ref "$PREVIOUS_ACCEPTED_COMMIT" --binding "$BINDING" --scope "$SCOPE"
python "$O/tools/workmap_gate.py" dispatch --repo . --ref "$EXACT_COMMIT" --base-ref "$PREVIOUS_ACCEPTED_COMMIT" --binding "$BINDING" --scope "$SCOPE" --delivery "$ACTUAL_DELIVERY_JSON"
```

ref是实际40位Git commit，base是前次接受基线；不能用HEAD替换。check核引用/区域/投入/版本，dispatch还核原任务和实际在途。executor检查保护写面不阻止保存专业成果。必要方法path在rule_paths内且可读，方法存在不证明实际使用。

## 3. 阅读与交付证据

workmap-intake/v1及原intakes保持。manager/decision_report/effort/scope_dispositions/validation_claims都需真实依据。reader_check=RECORDED必须有实际独立上下文、报告path/blob、input_commit和该版reader_fingerprint；旧输入不能标成当前通过。

新阶段/重要意图变化需适当新读者；普通低风险增量可由管理有据定ROUTINE_RESULT/EXISTING_AUTHORIZED_REPAIR，不以布尔值跳过必要独立性。实际delivery保留observed_commit/task_id/task_blob/state/evidence/载荷摘要；仅NOT_SENT或已确认失败可新发送，RUNNING/COMPLETED/UNKNOWN先对账。

## 4. 原文取得与信号

```sh
python "$O/tools/execution_handoff.py" prepare --repo . --ref "$EXACT_COMMIT" --task "$TASK_PATH" --method "$METHOD_PATH" --output /tmp/task.json
python "$O/tools/execution_handoff.py" notice --observations /tmp/runner-observations.json --output /tmp/notice.json
```

prepare只取得内层原文/方法身份，不能作为整条新管理消息已验证的证明。新消息统一用下节；普通任务默认准确引用，不自行摘要，不强迫把长全文全贴手机。notice依已有events/handled/inflight去重，不把POLL当管理、不写业务状态、不实际派发。无新commit仍按原绑定核到期管理；业务重要性由Pro/原条件给出。

已有主续作、独立接收、管理复看和交付补齐先投影为分别具名的issued actions，再用下列纯函数分类；它不会发送或改状态。不能因为主续作可发，就把同work的独立接收从待办中覆盖掉；IN_FLIGHT只收取，不重发，UNKNOWN先对账。

```sh
python "$O/tools/execution_handoff.py" reconcile-actions --actions "$ISSUED_ACTIONS_JSON" --output /tmp/actions.json
```

## 5. 新消息：配置取源、组装、核验

固定结构配置为`runtime/config/COORDINATOR_DISPATCH.json`（候选，未采用）；只有实际管理/Owner形成本轮授权BOOTSTRAP或Binding，才可由运行端据此准备消息。POLICY_COMMIT须为实际采用本次规则和配置的提交；它只固定规则、Owner目标、阶段及机器mode到实际工作名称的映射，不能代替现场采用的当前任务或在途动作。DISPATCH_JSON由当前真实绑定、管理决定和运行记录投影，不成为新状态源。

共同必需字段：work_id、invocation_id、assignment_token、binding_ref、route、send_state、dispatch_kind。binding_ref用原repo/commit/path/selector（`full`或`全文`），route用既有routes键或`trigger:原trigger_id`，dispatch_kind只取`NORMAL`或`DELIVERY_REPAIR`。不得提供goal/text/request/role/stage等自行改写固定要求；未知字段/重复键报错。目标阶段和mode映射取配置，接收角色与聊天取原route；新阶段先由实际任务变更处理，配置不授新权限。

首次没有计划时，`binding_ref` 可定位 DR14 的 `question-work/v2`、`kind=BOOTSTRAP` 原始管理输入；仍用同一 `dispatch prepare/verify`。配置中模式为 `M-START`，`route=same_work`，接收者仅取 BOOTSTRAP 的真实管理 `recipient_ref`，不要求或生成 plan/budget。固定 Owner 目标须与该输入的 goal_ref 完全一致；完整来源、父合同适用说明、M-START 题面和当前任务/采用依据均须可核。该入口不接受专业、接收、trigger 或交付修复路线；专业工作待真实管理输出的 BINDING 另派。

`NORMAL`还必须给`current_task_ref`全文及`task_adoption_ref`：前者是当前生效任务的exact Git版本，后者是采用它的管理决定或直接要求。二者不得默认用POLICY_COMMIT或moving main。历史binding仍作为“上一轮实际采用的任务绑定”保留，检查旧回交按旧派发，不拿新任务反判旧回答。机器RETURN用`latest_return_ref`解析时，必须同时给同一blob的`latest_response_ref`全文；显示给目标聊天的是完整回答，continuation另列。可选evidence_refs、observed_at（带时区）、effective_calls、elapsed_hours。

任何BI-01专业新签任务都使用已采用的`current_task_ref`全文，不再依赖CYF `CURRENT_C_WORK` 标记；合法同工作续作按当前任务／采用依据核对后优先使用。`source_reads` 只列所选来源的位置、版本、用途及读取要求，不把其正文自动嵌入；Owner要求实际消息带全文时须由当前任务提供。`--message-output` 保存真正待发全文，prepared JSON 不含消息全文，也不证明已发送或语义审查通过。dry-run 不调用 sender、不改在途状态、不恢复任务；新正常消息采用新规则，原消息运输恢复严格保持旧字节。

`DELIVERY_REPAIR`不得装入当前完整任务，必须给`repair_context.original_dispatch_ref`、`issue_ref`和非空`missing_output_refs`。脚本从原调用取work/role/recipient，所选路线不一致就明确拒绝；因此管理缺件不能发给专业聊天。业务finding返修仍用NORMAL及实际业务任务，不能因路线名含repair误当交付补齐。

BI-01 候选 Dispatch 提供 `M-START/M-REASSESS/M-CLOSE`、统一 `FEATURE_OBSERVATION` 与 `INDEPENDENT_REVIEW` 模式，**只识别真实有权 Binding 的 mode 并选择固定角色正文**；四项工作不是四个 Gate，不自动生成专业任务、授权或审查通过。旧 BI-01-V2-02 的 Workmap、旧 U2/U3 任务和 CYF 历史执行只是来源事实，不能继承为新任务的工作、在途或触发。正式消息仍须具备新 run 真实签发的 Binding、当前任务全文和接收者；配置本身不授权派发。

```sh
CONFIG=runtime/config/COORDINATOR_DISPATCH.json
python "$O/tools/execution_handoff.py" dispatch prepare --repo . --ref "$POLICY_COMMIT" --config "$CONFIG" --dispatch "$DISPATCH_JSON" --message-output "$ACTUAL_MESSAGE_MD" --output "$PREPARED_JSON" &&
python "$O/tools/execution_handoff.py" dispatch verify --repo . --ref "$POLICY_COMMIT" --config "$CONFIG" --dispatch "$DISPATCH_JSON" --payload "$ACTUAL_MESSAGE_MD" --recipient "$RECIPIENT_REF"
```

正常 GitHub 派发分两段，不能把第一段完整文件发进手机：先运行`dispatch prepare`（不带`--github-message-ref`）生成完整 `FULL_ASSIGNMENT.md`，在有权现用分支普通提交并远端回读。将其准确 `repo/commit/path/selector=full` 写入`FULL_MESSAGE_REF.json`；再调用相同dispatch JSON及锁定策略：

```bash
python "$O/tools/execution_handoff.py" dispatch prepare --repo . --ref "$POLICY_COMMIT" --config "$CONFIG" --dispatch "$DISPATCH_JSON" --github-message-ref "$FULL_MESSAGE_REF_JSON" --message-output "$ACTUAL_MESSAGE_MD" --output "$PREPARED_JSON"
python "$O/tools/execution_handoff.py" dispatch verify --repo . --ref "$POLICY_COMMIT" --config "$CONFIG" --dispatch "$DISPATCH_JSON" --github-message-ref "$FULL_MESSAGE_REF_JSON" --payload "$ACTUAL_MESSAGE_MD" --recipient "$RECIPIENT_REF"
```

两个 digest（归档全文和手机短指引）分别保留；短指引逐字回指GitHub归档原文，校验失败不得手写跳过。原本本节不带`--github-message-ref`的命令仅作为**归档全文的prepare**示例，不能作为正常手机verify/发送；新版本verify默认拒绝未指明短指引的直接全文。Owner明确同意直接正文运输的例外才在verify中加`--direct-body-authorized`。已发送历史恢复仍以`replay`原字节处理。

回交使用GitHub报告全文及独立有效`QUESTION_WORK_RETURN.json`、`ROLE_RETURN.json`时，`latest_response_ref`指完整报告，`latest_return_ref`指独立问题回交JSON，新增`latest_role_return_ref`指独立角色回交JSON，三者须是固定Git来源。Role Return的`question_work_ref`必须直接指向真实Q-Return的`repo@commit:path::full`（可带`github:`前缀）；角色最终提交树必须仍有完全相同的报告和Q-Return blob。程序只做原文/身份/仓库一致性检查；完整Schema、原invocation/token、资格及业务接收依现有Gate另核。旧单一Markdown同blob的Return保持兼容，不补造旧记录。

两步成功后只发送ACTUAL_MESSAGE_MD原字节，不再让模型润色。失败不得改用手写短消息绕过。policy/config固定源与动态bindings都来自exact Git，固定目标不接受现场自由文本。计划/预算/完整scope和最新回交以精确引用进入；对应角色实际阅读，工具不冒称读懂。

现有发送器可调用`management_prompt.checked_send(prepared, payload, actual_recipient, sender)`：它同时核完整字节和实际接收者，再调用sender，无自动重试。载荷或接收者任一改变都拒绝。手机包携recipient/work/role/invocation；进入目标聊天后还须用新鲜可见标题和当前轮锚点确认同一聊天，不能凭相似旧标题发送。实际权限、撤销、在途和已采用绑定仍须发送前由原可信入口检查。该模块不认证输入记录身份，也不能证明手机端标题；控制只覆盖真正经过它的路径。

## 6. 旧原文恢复

```sh
python "$O/tools/execution_handoff.py" replay --repo . --repository daowei2026/feature-refinement-implementation-agent-evolution --original-ref "$ORIGINAL_REF_JSON" --expected-digest "$ORIGINAL_SHA256" --message-output "$REPLAY_MD"
```

ORIGINAL_REF_JSON直接定位当时实际完整提示，SHA来自原发送记录；原文恢复不叠新提醒。效果未知先按原协议对账，此命令不产生重发授权。新Owner消息原样沿既有CHANGE处理，未归档不能假装已经Git核验；固定材料缺口交材料维护，不要求Owner整理新表。

复用既有派发记录关联policy/config/binding、完整载荷摘要、退出状态及真实发送回执。sent=false与semantic_review_passed=false保持准确，不改一项“已采用=true”自证。提示由协调者归档一次，目标聊天不再抄同一原文。

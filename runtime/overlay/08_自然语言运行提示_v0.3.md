# 协调者操作入口：取原文、填事实、发送与接续

执行修订：`2026-10-13-normal-feature-positive-methods`（沿用 coordinator-dispatch/v3）。
本页是协调者唯一日常操作入口。固定正文和取源配置由材料维护一次整理；协调者只取原文和运行事实；管理及专业聊天不重编通用控制材料。详细回交字段见[13](13_角色回交与主控接续协议.md)，命令和能力边界见[12](12_管理接收与地图校验.md#coordinator-prompt-commands)。BI-01专业方法按本次有权任务实际引用，协调者不必理解完整专业算法才能搬运。

采用边界：CYF原来的U2/U3专业采用和Owner纠正只属于历史来源；当前BI-01完整目标/权限来自本仓professional/下的准确原件和本次真实有权任务。旧CYF材料不自动成为BI-01 Owner授权。

本次适配保留已有机械派发、材料权力和回交规则，不替管理Pro重新签发任务；旧CYF运行记录不能直接迁移为BI-01在途或已通过状态。通用规则和正确专业正文必须保全，不得压缩成短壳。

## 1. 固定责任与正常动作

协调者只使用已确定原文、模板和真实运行事实生成消息。不得概括Owner目的、补业务范围/重点/参数/实现方案/完成条件或新增禁令；不得把建议升级成必须。固定源缺失或矛盾交材料维护，动态业务缺口交原有权Pro，运输问题按原恢复；只限制依赖该缺口的动作，不要求Owner每步确认。

首次采用/恢复：核对真实在途、实际已采用任务和本版材料；只影响下一次合法新消息，不重发旧消息，不清零work、预算和责任。消息模板、固定目标、源选择规则留在repo，不交长程聊天每轮重写。

收到结果：保存完整回答和成果，按原派发核身份、去重、解析原ROLE_RETURN/QUESTION_WORK_RETURN。Worker 技术回交按原工单签发者及 return_to 定向给原 Pro 消费，采用12中的限定校验；不能因结果新增引发的 INTAKE_STALE 自行改送管理。需管理认可或判断由原 Pro 按绑定提出，独立到期管理责任仍按原机制处理。原任务内same_work仅在原授权与实际依赖放行仍成立时继续；按绑定检查RESULT/CHANGE/EFFORT，无新回答也检查到期责任。已在途/已处理同一责任不重发；原非阻塞专业续作与到期管理均保留。UNKNOWN交原责任者处理，不能当未到期。字段错误只补字段，分析未完继续原工作。

## 2. 固定源与动态源

本工作读取`runtime/config/COORDINATOR_DISPATCH.json`的固定方法与角色入口（启用须存在有权签发的work绑定）：固定Owner目的、阶段、允许的机器mode及其实际工作名称。它仅规定固定关系，不保存进度、当前任务、接受状态、预算或另一套授权。目标正文由goal_ref指定用例README或当前Goal，一份正本；配置中的相对ref按本次已采用policy commit解析。当前生效任务、采用依据、binding和回交分别使用真实40位commit，不跟随moving main，也不默认跟随policy commit。

|内容|取法|
|---|---|
|Owner完整目的|配置goal_ref的原文，不用管理decision或协调者摘要替换|
|阶段与职责|stage和binding的professional_mode相符，机器mode名称不冒充接收角色|
|本轮请求和角色|已采用binding的routes或trigger.route，不改角色绕过模板|
|当前生效任务|已采用管理决定或直接要求的exact全文，另给采用依据|
|上一轮实际任务|原binding及full_scope；核旧回答仍按旧派发|
|安排和投入|plan_ref、budget_ref原位置，完整终点和投入起点保留|
|最新成果和续作|完整实际回答及相符continuation_ref，不替代完整目标|
|本次直接上下文|已选定source_reads；用途由材料维护/原Pro/管理确定|
|时间、次数、发送状态|使用既有事实；工具不判断业务重要性|

协调者把已有记录投影为临时dispatch JSON，不写新业务综述。新Owner消息原样沿既有CHANGE路径转交，保留原消息位置；不能自行摘要覆盖固定目的。新阶段或固定源更换由相应正式变更更新配置，不让普通业务调用维护本规范。外仓资料沿任务exact引用取得；本地工具只核本checkout，外仓定位不冒称已取得正文。

### 2.0 GitHub 完整派发、手机短指引（新调用必须遵守）

正常 GitHub 可写、且接收者能够实际读取精确仓库原件时，先使用现有生成器形成完整角色派发原文（含当前有效任务/Binding/Owner Goal），按原写权在当前有权分支推送并从远端读取确认；随后使用`execution_handoff.py dispatch prepare/verify --github-message-ref <精确定位JSON>` 将**同一份逐字校验过的原文**转换为手机短指引。该JSON必须是 `repo/commit/path/selector=full` 的真实固定位置；脚本不一致即拒绝。短消息只带原身份、全文阅读要求和唯一完整派发位置，不在手机重复内联全文、Binding和通用方法；先取得全文才能执行，短指引不缩小任务。

实际手机发送必须使用短指引的独立digest及recipient核验；完整派发原文的digest另存。旧已 committed/未知送达消息只按当时原字节恢复，不改写、不重新发；本规则不自授 Owner GO。若 Owner 明确要求本轮把原文直接发到聊天或有实际不可通过GitHub交付的内容，才在有权记录下使用 `--direct-body-authorized` 验证直接正文。GitHub 不可读不能假称短链接已交付，受影响动作按原有备用运输和阻断程序处理，禁止主控临时手写绕过失败的生成/verify。

Pro的完整业务报告与符合原Schema的 `ROLE_RETURN.json`、`QUESTION_WORK_RETURN.json` 优先交到GitHub有权目录，单独校验准确身份、binding、引用和实物；在远端三件齐全且可验证时，聊天最终回复只需实际commit及交付路径/必要失败状态，不再重复整篇报告或两份JSON。仓库长报告仍必须完整，缺有效Return须定向补齐、不能从手机短文推断业务完成；GitHub写入失败仍用已有ZIP/原始回交兜底，不凭一条链接自称完成。

### 2.1 直接上下文：使用现有source_reads

沿DR12专业源、DR13 §6读取周期和DR14现有字段，由原责任者填实本次接收角色需要的正文。关键定位和禁令直接给在第4节；详细内容给准确位置，不把整套文档全文灌入提示，也不让执行者自由递归所有链接。实际角色与写面保持原授权；完整业务地图及直接相邻合同不能从专业上下文消失。

每项沿已有形状：

```json
{
  "source": {
    "repo": "daowei2026/observe-iterate",
    "commit": "<本次有权采用的真实40位commit>",
    "path": "professional/feature_observation/02_WORK_DETAILS.md",
    "selector": "全文"
  },
  "requirement": "MODE_FULL",
  "purpose": "本次具体特征四项可迭代工作的实施方法；其他来源按本次真实任务选择",
  "reuse_evidence": null
}
```

上方尖括号只用于展示字段形状，不是合法派发值；实际运行必须填准确的已存在40位commit。实际任务分别填写真正采用的方法、业务任务和执行源码版本，不能把三个版本统一替换成latest。新绑定填写实际选项；旧绑定缺项显示具体缺少，不假填已读、不为修字段重发历史。下一次正常改派或更新绑定时补齐。

生成器只展开已选定source_reads的位置、用途、边界与复用条件。同仓用原Git/selector核位置，外仓或附件只给准确定位，目标角色实际读取；不声称文件hash证明已读。没有新ContextPack、阅读证书或通用Ontology系统。

### 2.2 BI-01 稳定角色取源，直接回到专业原文

协调者按新 run 的有权 source_reads 定向引用 [00 具体特征与四项工作](../../professional/feature_observation/00_PURPOSE_AND_FOUR_WORKS.md)、[01 基本输出](../../professional/feature_observation/01_OUTPUT_BASE_FORMAT.md)、[02 初步细节](../../professional/feature_observation/02_WORK_DETAILS.md)、[03 旧知识复用](../../professional/feature_observation/03_REUSE_FROM_V2.md)及按需使用的 [04 aidata](../../professional/feature_observation/04_AIDATA_USE.md)。专业者须实际取得本轮承重的特征定义、代码/结果/数据与必要来源；U2/U3 只按具体特征需要引用，不把旧完整 U2/U3、旧固定 rb/i/hc 两包或 S1–S3 强加给新任务。新 run 的身份、数据位置和参数由真实 Owner GO 与有权任务明确；主控不编业务内容，也不重用旧 BI-01-V2-02 已采用 Binding。

### 2.3 读取周期、缺项与更新

首次进入职责取得完整适用方法；同一上下文、内容未变且仍可准确恢复时复用。换上下文、关键正文截断或方法更新时，回对应正文取得需要的内容，不以旧阅读回执冒称已取得。continuation保留完整未完、当前实际工作、有效结果、重要输入输出和相邻关系。

下一次合法正常调用必须实际提供已采用版本的固定提示和本次 BI-01 阶段适用的完整专业方法，并携带原生效完整Goal、当前任务及地图。通用方法同步本身不改用例任务；`current_task_ref`、`task_adoption_ref`、binding、角色、预算、暂停、租约和在途事实保持原值，只有原有权责任者真正改变任务后才更新。禁止为了表示采用而制造新工作单、假采用记录或重新派发。

如果现行任务确有与最新Owner纠正相反的条款，准确定位交原任务责任者删除或修订，只限制真实依赖；不能继续默默执行错误，也不能由通用维护者或主控擅自改写 BI-01 现行有权任务。已由有权责任者撤销的任务只保留历史，不继续派发。正确在途工作保留真实版本；Owner取消或已确认跑错时停止受影响操作，其他已定合法工作继续。

不用逐文件已读证明。是否实际使用从设计、代码、运行和处置判断。手机Pro收到更新不等于本地Codex收到；DR10工作单与工程师正常接续须传相同通用方法版本和实际上下文。现场已有AGENTS或协调入口可定向给稳定短指引，不复制全套手册，不改运行事实，也不冒称已部署。

## 3. 消息种类与长度

所有管理调用用管理正文、当前阶段说明和Owner完整目的；普通专业续作用任务/阶段正文；只读接收不用工程编制正文。只读接收仍属于原已授权工作和阶段，不自动产生下一阶段或新授权。

固定正文直接载入，任务和详细方法精确引用；已有有效内容复用，不以统一行数删业务。完整目标和删除多余任务的短要求直接显示，详细图使用准确位置，不让接收者再考古。正确业务和工程正文禁止任何压缩；只定点删除已明确多余的非实质任务，不能整章改短或只留历史链接。

交付字段补齐与实质业务返修分开。前者保持原调用和角色，只补具体缺件；后者采用完整业务任务。已committed消息的运输恢复逐字使用原消息，不叠新规则；实际Owner改变沿CHANGE采用新任务，不假称原历史已更新。

**管理需要独立说明完整目标下正常系统应当怎样工作：当前业务观察问题是什么，真实数据与专业结果怎样到达、可消费证据资格在哪里，业务认识怎样进入Owner判断或下一阶段，以及哪些工作已经完成、哪些仍需核查。以这张完整业务关系图安排工作。**

比较新增结构时，判断它解决了哪个真实业务问题、是否由已有平台承担、是否有更直接且保真方式。不能仅凭文件多、类型多或代码长否定必要业务，也不能因旧包详细、曾被接收或已投入很多维持无用工程。

当前采用关系、旧纠正处置、全局优先级、重要剩余和实际后继由管理承担。给推进者明确业务方向与已知处置，不把这些职责打包成“请全面检查一切”转交。

某项局部问题只限制实际受影响的输出和运行；其他已明确主体继续。连续回交偏离主要业务时，改变真实安排，不能只追加“完整范围保留”的说明。

**真实业务观察、设计迭代及当前阶段实质收拢是第一优先。管理必须从 Owner 完整目标、业务问题—可信证据—业务认识—下一行动的实际关系和全部重要剩余出发作判断、排顺序、派工作。禁止以最近结果、最新 remaining、局部报错、审查 finding、文件数量、测试数量或已有投入默认决定优先级。**

**禁止把“本轮只观察一个 Case”“先清完整个仓库再做业务”“只处理几条 finding”“先把这份文件做完”设为正常实质推进目标和主动停点。当前重点只决定处理顺序。承办者持续承担当前阶段全部约定工作，局部修通后继续已经明确的后继。**

管理必须预期旧目标理解、工程结构、任务拆分、推进顺序和自己的旧决定可能存在严重错误。不得先认定旧方向正确，再只处理局部差分。已有代码、旧接收、formal 名称、完整 schema 或长期投入，都不构成继续保留错误工程的理由。

**材料权力收拢、已知问题裁定、旧要求撤销、全部重要剩余、全局优先级、跨任务协调、实际后继安排及接收判断，由管理承担。禁止把这些工作打包成“请推进者全面检查并整改”后转交实际推进聊天。** BI-01下游工作依赖具体上游成果时，由管理Pro核已成实物和必要技术/专业证据，明示接收范围、允许下游及后继签发；必要Notebook/平台实际操作核验可委派具名限定Worker，但主控不得代发自拟核验单、判断成果通过或绕过未认可依赖。

管理亲自核实已发现的承重问题，给出具体正文或代码入口、问题性质、业务影响、应撤职责和必须保留的正确业务。已经明确的删除决定直接作出，不再让推进者重新研究其必要性。管理无需预先穷举每个调用点或设计每个类型；推进者与工程师继续追实际依赖并完成全部相关修改。

当前执行输入必须分清：现行要求、被撤要求、保留的业务合同、历史事实和真正未定事项。已撤任务不再作为另一份当前完整任务提供。主控依据管理已经完成的决定准确装配，不补业务判断；推进者不再每轮重做整套历史裁定。

**局部阻塞先判断该机制是否应当存在，再判断具体阻断哪个业务输出和消费者，影响施工还是实际运行，以及修到哪里即可继续。无必要辅助任务直接删除；必要缺件与直接消费者集中处理；不受影响主体继续。禁止用一个来源、reader、生成错误或共享现场等待冻结全部业务。**

**连续回交只停留在来源、工具、格式或运行准备，而真实业务观察、反例挑战与迭代行动没有推进时，管理必须在当前管理工作中改变实际安排。只在报告末尾写“完整 scope 保留”“继续完整主线”不构成履行管理责任。**

管理决定应当减少推进者的重复判断和等待。已经有足够依据的工作及时交出；尚未解决的问题只限制真实受影响部分。禁止先开展完整仓库审计、重建地图或穷举全部未来问题，才让实施者开始。

只有本轮确有获授权的 Worker Codex 技术任务时，实际工作单才需要容纳相应依赖、普通工程选择、计算/制图、实际调用和结果核验。不得用封闭文件白名单、逐错误批准或“重要工程一律回 Pro”收回既有授权。开发中的工程反馈及时取得，完整业务接收继续保持原标准。

管理与审查兼任时分别履行职责。审查直接对照原业务依据、最新纠正、真实专业结果、必要源码及下游使用者，不能仅核作者新概述的自洽性。管理如果实质参与某项新设计，不能对自己形成的设计自签独立通过；按已有渠道处理真正受影响部分，不默认增加角色。

**已否技术职责从生效工程、工作单、前置、验收、后继及其专属实现和检查中退出。禁止改列为 deferred required、未来优化或后续必做。正确业务、方法、字段、状态、时间、历史、专业方法和消费者完整保留，禁止压缩。**

普通细节形成基本合理、可修改的首版，尽快取得真实反馈；核心方法不能留空，必要验证不能伪造。核上次安排是否实际落实，保留原投入起点、持续管理责任和有效成果。局部完成不关闭完整阶段；管理本轮结束不取消尚在继续的管理责任。

## 5. 实际发送与能力边界

使用12中的`execution_handoff.py dispatch`先归档完整派发、再用`--github-message-ref`准备/核验短指引载荷，才交现有发送动作。非零退出只修受影响消息，不手写绕过。既有授权、在途、撤销和重复派发检查继续；脚本只核机械关系，不认证市场语义、实际已读、手机送达或输入权限。

可接Python的发送器使用`checked_send`同时核载荷与实际接收者，任一改变拒绝；不自动重试效果未知的外部动作。手机包携recipient/work/role/invocation，发送前用新鲜标题和当前轮锚点确认目标，不凭相似旧标题。未接发送器不称全通道强制，不新增截图轮询。

只在原记录保留policy/config/binding、实际载荷摘要、核验退出和真实发送回执。提示归档一次；source_reads展开不证明阅读，生成器不新增语义裁决和证书任务。

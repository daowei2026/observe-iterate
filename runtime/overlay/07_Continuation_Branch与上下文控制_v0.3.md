# Continuation、Branch 与上下文控制

执行修订：2026-09-14-management-repair。

采用GitHub工作面时，共同README、各线推进地图、当前任务和完整正文是接续入口，不另写平行Continuation真源。推进图由管理／审查端维护，普通执行者只读定位后完成自己的实质任务；BI-01 专业证据/观察由获授权的执行 Pro 形成，长程推进地图及当前任务由管理 Pro 维护，不能继承 CYF A/B/C 的地图作者职责。

换聊天提供任务目录、已存在输入commit、任务卡、必要完整正文／审查／Owner来源、未处理反馈和当前执行修订。管理端还恢复上次接收范围、实际发送现场与已知投入；不能只搬一页总结，也不复制全部历史。Builder下一步仅提案，不随换聊天获得权力。

无GitHub写能力或明确离线运行时，给真实未发布状态、完整实物或差分以及薄Continuation：实际成果、变化、未决、审查、Owner、受影响下游和必读材料。不得谎称同步；恢复后只补缺失交付，不重做已完成业务。

上下文按“全图导航＋本轮完整专业方法与承重正文＋必要相邻依赖”控制，不缩方法、不拒绝未列出但实际承重的材料。原始问答按具体歧义回查；代码事实重新比较live并锁exact。新规则或Owner纠正也要对旧成果和地图作定向回查，即使没有新业务文件。

独立写面可并行；共享README／推进图／任务签发由指定管理者顺序更新，共同业务接口仍保持正式单写者。聊天分支只继承分叉前，后续决定不自动回写父线兄弟线；Git分支隔离代码，聊天分支隔离上下文，两者不互相替代。

接收与投递用12核exact输入和在途状态；新聊天、重命名、分包不清零实际投入与审查循环，重复收取不算新工作。没有实际发送证据不声称任务已经运行，没有fresh上下文不声称独立审查已完成。

管理／审查继承同阶段专业方法，不只管理覆层。实际发送保留签发正文和方法身份，不能在接续总结中新增“最小问题”或“任意返修全停”等限制；新工具prepare与notice见12。未变且有效内容可复用，不要求每轮重读全历史；更新方法不清零原业务与真实投入。

# GitHub 持续工作面：建图、接续与版本管理

执行修订：`2026-09-08`。适用于 A／B／C 的跨用例长程，不定义任何具体用例的对象、算法、里程碑数量或仓库路径。

## 1. 工作面是什么

任务正文直接在获授权的 GitHub 目录持续修改；日常不再以“每轮一个 ZIP”作为唯一交付。Git 保存旧版本，地图保存全局问题和可核对进展，审查保存判断依据。ZIP 只在明确需要离线交付、阶段冻结或外部移交时由指定提交导出。

**推进地图不是 Mission A 的业务工作地图，也不是另一份缩写任务包。** 前者回答“还要解决什么、现在在哪、下一步为什么做”；后者回答“市场过程、特征和方法怎样构成”。地图指向正文，不能替正文裁业务；不能把它写成打勾表而省略仍未回答的问题。

## 2. 开始前只补真正缺少的输入

新任务或中途接续均需要：目标仓库、获授权分支或建分支范围、目标目录或已有地图路径、完整任务目标、当前材料和 Owner 授权。先用已连接工具读取，能从指定入口查出的不再问人。

只给目录但未给分支：遵循该仓现行写权规则；若获准建工作分支，可从核准基线创建。**授权写某仓不等于永久允许直写 main**。Owner 本轮明确授权的目标分支优先；不改保护规则、不 force push、不代推他人改动。未获写权时只提出修改，不声称已经接入。

核对活动分支，选定 exact commit；重要材料在该提交上读取。无法取得必要正文时，具名报告缺项、受影响部分和仍可继续工作，不拿旧摘要或代码现状补业务。

## 3. 新建与中途接续使用同一办法

### 已有地图：先对账，原位维护

读取已有地图、当前任务、实际正文、最近独立审查和 Owner 决定；沿受影响依赖看必要上游与下游。先检验地图声称的进度是否有正文和证据支撑，再选本轮问题。原地图够用就保留文件名和编号，不为套模板再造一张平行地图。

### 没有地图：从真实材料恢复，不从聊天轮数编造进度

先读完整目标与最高影响的当前正文，形成初步理解；据此列出少量可交付的业务／工程结果及依赖。把已有内容接上去，清楚区分“正文存在”“待审”“审后可用”“待真实验证”。其余范围在图上保持可见，不为填满地图一次性通读全部历史。

第一次建图可以和第一段实质分析同轮完成；不要先花若干轮建设调度基础设施。确需恢复的当前关键包未齐时，先做好不依赖它的部分。

### 中途补机制：恢复状态，不重跑整个 Mission

保留当前有效的决定、正文、审查和放权。旧任务中没有独立审查证据的地方标“审查未核实”，不要虚构循环次数或一律打回零起点。若当前任务过大，提出有业务理由的拆分，并保留原任务的未完范围与已花循环，不能换编号抹掉欠账。

导入 ZIP 时，先锁 Owner 指定 parent／当前版本及 hash；解包保留完整有效正文后建立一次导入提交。不能按最大版本号或修改时间自行选真源。已丢失且原始字节仍有证据价值的附件保留缺失状态，不从清单重造。已有 Git 正本则直接采用 exact repo/commit/path，不再强求生成 ZIP 才能继续。

需要集中补齐既有材料时采用 [11 的 MATERIAL_CATCHUP](O11_TURN_AND_MATERIAL_PUBLICATION.md)：核对有效后继后实际导入正文，默认以 2–3 轮完成必要范围，允许提前结束；不补历史问答，不重做整个用例。

## 4. 最小文件形态，已有等价文件不重复建

```text
<Owner 指定的任务目录>/
  00_长程推进地图.md
  01_当前任务.md
  artifacts/       # 按业务主题组织的完整正文，稳定路径
  reviews/         # 审查与路线判断；已有记录系统可直接引用
```

输入锁、Owner 决定、交接信息先放地图对应节或引用已有正式文件；内容确实足量才拆文件。自本执行修订起，Pro 每次交付自行保存本轮实际提示全文与完整回答正文；不等待外部抓取器，不负责补录历史问答。必要实质文件完整入库、相同成员只存一次，详见 [11](O11_TURN_AND_MATERIAL_PUBLICATION.md)。本轮问答保存、任务材料齐全和业务审查通过分别报告，不能互相替代。

一个完整任务可跨 A／B／C，不能每换 Mission 就换地图。并行任务确有独立问题与写面时可有各自子图；共享依赖在上层薄索引可见。每张共享地图由一个指定维护者顺序写，子任务只交进展，不同时覆盖总图。不要强制所有用例先建总图再建两张子图。

## 5. 地图里必须看得见什么

开头用业务语言写完整目标、目前最关键的未解决问题和本轮进展；人不应读完身份表才知道在干什么。主体按结果而非文件或聊天轮次列里程碑，可用短段落或表格，不规定固定数量。

每个里程碑应能找到：

- 要回答的业务／工程问题、完成后谁拿它做什么；当前边界与依赖。
- 当前完整正文的位置；已形成的具体结论、最重要的剩余未知及其后果。
- 内容进展、独立审查进展、使用资格分别是什么，分别由哪份证据支持。
- 当前完整审查循环数及对应候选／审查／返修版本；无法核实的旧循环写未知。
- 离站条件、对相邻部分的影响；未开始的部分仍在完整范围内。

另保留少量最高损失风险、真正待 Owner 的问题、可并行的未阻断工作、下游正在使用的冻结版本，以及最新已裁定路线。**路线理由必须比较当前实质价值：先解决哪个问题能减少错误解释或下游返工，不以“完成文件更多”作理由。**

地图可以概括，承重内容不能被摘要替代。图变大就按真实子问题分层，不能靠删未完事项或把所有正文复制进地图控制篇幅。每轮只修改受影响条目，不重新生成全图。

## 6. 谁能更新哪一种进度

Builder 可更新自己实际修改的正文定位、已完成动作和仍有问题的事实；“写出第一版”不得自行升成“通过独立审查／允许下一阶段”。独立审查者核正文后，记录判断和路线；详见 `10_独立审查与下一轮问题选择.md`。Owner 决定保持原话来源，Agent 的概括不是新 Owner 授权。

`01_当前任务.md` 是当前已签发问题，不是 Builder 建议池。Builder 交付后将本任务标为“已交付，待独立审查／路线判断”，不得自己替换成下一业务任务。建议可放本轮交接末尾并明确“未签发”，审查者先独立判断后再按需读。Codex／routine 只能传送和机械核对，不能把建议变成命令。

授权中的初始任务可由主 Pro 结合材料形成；已在执行的任务接入地图时可保持不变。但第一份承重候选离站、进入新里程碑或改路线，必须有独立判断；不能以“初始化地图”绕过它。

## 7. 活动正文只留一份，版本靠提交

建议稳定路径如 `artifacts/<业务主题>.md`，不要日常复制 `v1/`、`v2/`、`final2/` 全套目录。文件头可保留合同语义版本，但 Git commit 标识确切字节，二者作用不同。

**“只有一个活动目录”不等于“所有人都读最新分支”。** 下游使用 `(repo, commit, path/section, 使用资格)` 指定的冻结版本；上游继续修改同一路径不自动改变下游。发生语义不兼容时，精确标记受影响下游并重新交接，不要求全部重跑。

同一提交内相对链接指向同一快照；引用历史审查对象或另一仓必须写 exact commit，不能写 latest。提交前文件不能写入“包含自身的提交号”：地图保存已存在的输入／被审提交，提交成功后的输出 SHA 写在最终回执，或由外部投递记录指明。commit SHA 与 tree SHA 不得混用。

Git 能保留历史，但不能替代语义连续性：修订正文必须说明 KEEP、修改、完整移动、明确删除及理由。发现冲突要改掉旧正文，不能仅追加“新版优先”。不以管理机制为由清理现有归档、删除旧证据或整体改名；旧活动副本的收拢要另做有定位证明的迁移。

并行试验或破坏性改动用分支隔离，不用多套版本目录冒充隔离。候选提交、审查通过、Owner 接受和真实运行验证仍是不同状态。

## 8. 一次提交与下一轮读取

一次工作交付尽量在同一提交包含正文变化及相应地图事实；审查提交可同时包含 review、路线和新的当前任务。这样下一轮不会看见“地图已完成、正文尚未推送”的半截状态。本轮问答记录也纳入该交付；正文被多次讲解只引用一个落点。没有任何新记录或实质变化不要求造空提交。

投递时绑定已经存在的输入提交；写入前核对 live head。若已变动，检查是否影响任务、正文或授权；不静默覆盖，不凭新版地图摘要重定任务。必要时重基线或暂停受影响写面。使用可检测并发的提交方式，最终更新 ref 不强制改写历史；成功后按 [11 的交付检查](O11_TURN_AND_MATERIAL_PUBLICATION.md) 重新读取远端确切提交上的入口、问答、本轮必要文件与引用，不能只确认 commit 存在。

只有远端回读成功才说“已提交”。失败或中断时说明实际停点、是否有未发布修改、可恢复输入；不得仍更新地图为完成，也不得自动退回 ZIP 当成同等已发布事实。

新聊天读取该投递提交的地图、当前任务和列出的必读正文／审查，做完这一块再按触发深入。未列出的关联材料若成为承重依赖，应主动补读并说明；“必读清单”是最低要求，不是禁止推理的围栏。

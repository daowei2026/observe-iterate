# 1. 为什么它是正常实施主干

执行修订2026-09-29：完整业务逻辑和正式接通优先；源码尽量由Pro编写，Codex承担工作区编译、测试执行、真实运行和现场调查，有具体理由才委派编码。当前不默认同时写测试程序，场景矩阵、fixture、proof和工业化加厚放到真实反馈后按实际需要安排。DR10/DR11规定具体分工，正常构建单预授有界编译小修；重要工程／业务修订仍回Pro，详细边界见DR10/DR11。

Host Builder 的难点不只在出现 bug 后怎样修。真实实施中更常见的是：

```text
业务主体尚未实现，却先做周边 proof；
一个简单 Action 被仪式化成很多层；
多个独立业务 Action 又被压进大函数／WholeState；
当前 method asset 有，但参数没有真正到达；
production root 存在，但 writer／readback 不可达；
实施过程中发现工程包或业务合同仍有空缺；
性能困难开始诱导删除 history、缩 scope 或降频；
局部测试绿被误报为完整 campaign 完成。
```

normal mode持续完成已定主体，按实际反馈或具体反证处理偏差；无反证不每轮重选研究方向。已具条件的正式路径尽早真实运行，同时继续其余完整责任。

# 2. 四个必须维护的前沿

Goal 决定当前焦点，不删除完整 campaign scope。

## 2.4 预计工作形态

```text

```

预计形态不固化为永久计划。RepoFact或实现证据改变时再判断；直接用现有工作面，不另建焦点指针、测试预算表或初始化机制。

# 3. 正常实施主线

## 3.1 共同约定

Mission C 沿“主体施工、编译修通、正式实跑与读回、业务结果检查与定向修订、完整范围接收”推进。工作段描述当前主要要取得的结果，不对应固定聊天、固定轮次或新的权限。

按已接受工程中的业务结果和依赖组织工作批。一条链具备条件就向实际运行和结果检查推进，其余约定主体继续施工；不能等待全用例源码和全量测试全部完成，也不能反复打磨一条小路径而停止其余主体。

Pro 主要承担源码编写和业务／重要工程分析；Codex 工程师承担现场调查、应用与生成、编译、实际运行、授权小修和结果回交；独立审查者检查实际实现与证据；管理者判断完整剩余、轻重缓急与接收；主控执行已有派发和接续。每方既完成自己的责任，也把足够下一方继续工作的实物交出去。

已接受的业务含义、两路表达、平台边界及有效经验在各段持续适用。业务理解和早期审查不推迟到结果阶段；缺少真实依据的效果深挖、场景穷举和工业化加厚后移。必要编译、日志、内存保护、正式保存／读回和结果解释继续做，不能随测试扩张一起后移。

已完成且未受影响的工作和证据复用。新方法发布、上下文切换或工作重点改变，不要求从第一段重新做起。四前沿继续保存在现有工作面；不增加阶段状态机、五类新任务或审批表。

<a id="c-source"></a>
## 3.2 主体施工：写出本批要形成的业务和正式连接

Pro 从已接受业务与工程恢复本批的输入、方法、状态、正式结果和直接消费者，沿指定方法路线编写实际程序。需要使用已有特征时，先读清其业务含义、参数、实际输出和本次采用方式，按平台复用方法 §2.4 实施，不能只依据名称、类型或配置存在判断。

方法、必要分支、事件状态、正式调用、注册和手写包装都属于主体。不能以纯内核、类型、外部传入的已判答案或测试替身代替尚未实现的生产过程；也不为统一外观把普通函数／Reflex 强制改成复杂 CEPS。方法仓、实现仓、结果工作面及两路完整 Feature／父组合责任保持。

一批相连源码能够进入实际构建时就交工程师，不等全部特征写完。交接说明本批补上了哪段业务、采用哪份源码、需要哪些已给出的应用或生成操作，以及后续运行还缺什么。缺少的主体仍由原责任者继续实现。工作区板块、完整成员、日历、输入与预热由工程师定向取得，Pro 在已有合同和权限内形成首个具体运行安排，不让 Owner 重讲已有信息。

本段交出源码只取得相应源码交付资格，不自动证明能够构建、运行或满足完整业务。正常后继是编译修通；已有有效且未受本批修改影响的构建证据直接复用。不要求每批同时配齐新的测试程序。

<a id="c-build"></a>
## 3.3 编译修通：连续处理实际源码错误

工程师使用工作单指定的源码与现有工程环境执行标准构建。TIS／FRP 的编译严格在 `edh-universe` 目录执行 `stack install`，禁止添加其他参数。正常使用已保证的环境，不默认调查二进制位置、导入路径或重建构建配置。

先读完本次已有错误，按共同原因归并。在工作单预先授予的小修范围内，能够依据现有类型、函数体和调用确定的语法、局部类型及明确引用错误，自行集中修复，检查直接相关同类位置后继续编译。正常构建单应预先给清这一范围；只读单保持只读。

需要业务或重要工程判断的修法，带实际错误、相关位置和已查明部分交 Pro；Pro 按原因处理相关代码，不能只修日志第一处。工程师继续不冲突的已授权工作。差分随原回交复核，不把每个小修 hunk 的事前独立放行作为再次编译的前置。共享写面仍保持一个活动写者。

不为编译问题扩写全场景测试、清理全仓警告或建立测试框架。已有适用测试和当前问题所需的定向检查按工作单执行，未执行不记通过。

指定源码通过正常构建后，正式路径和运行安排已具备就继续实跑；尚缺生产者、调用或必要包装，则明确返回该项主体施工。编译成功不能代替正式运行，构建失败也不自动结束整个工作单、归还现场或重新等待手机派发。

<a id="c-run"></a>
## 3.4 正式实跑与读回：取得可信、可分析的真实结果

工程师沿当前正式入口，使用工作区实际取得且满足本次业务要求的数据、完整对象范围、频率、预热和配置运行特征。Pro 负责在已有合同和权限内形成具体运行安排，普通实例选择不逐项交 Owner。

实际输入、业务计算、必要保存、正式读取及消费者所需输出连起来检查。内部计算完成、缓存存在或退出码为零，不能单独证明整条链成立。输出采用便于理解的正式可读形式，可以是 DataFrame、具名子表、结构化对象或事件记录；不为统一展示另建工程，也不取消原合同要求的正式接口和消费者。

开跑前设置内存保护，运行中保留必要进度和主要开销。额度及已有保护工具由现场落实；确实未知且影响本次运行时作小验证。异常增长或危险运行先停止受影响操作并调查，不能通过删历史、减对象、降频或静默调阈值制造成功。

当前规模能够安全取得可信结果时，及时交 Pro 分析；扩大范围的性能问题另行定向处理，不要求先做完所有性能优化。小范围成功不提升为目标规模或长历史开销已经合理。运行失败保留版本、阶段和增长事实，静态风险与实际事故分开。

无结果时分清输入、预热、调用、方法激活、读取故障、正在形成和合法业务空。解决接入故障后，继续取得原任务要求的结果；不能把排障完成当成特征结果已经检查。必要中间值来自真链，不另算旁路。

正常后继是业务结果分析。技术链不可信时先修对应环节；可信且未受影响的结果继续分析。回交给 Pro 足够的输入、对象过程、配置和必要样本，不只给退出码、行数或其不可访问的本机路径。

<a id="c-meaning"></a>
## 3.5 业务结果检查：解释实际形成的对象、过程和关系

Pro 结合真实输入和正式结果，说明主要业务对象、过程、关系或数值／事件为何形成、怎样变化、为何不存在。合同承诺持续对象时，检查形成、延续、变化、结束及其材料依据；其他特征检查实际承诺的行为，不强加统一生命周期。直接上下游还应核其对象、可见材料、版本和消费关系能否同时成立。

关键参数按业务含义检查。需要对照时，在已有方法允许范围和运行授权内保留基线、说明变化，选择能回答当前问题的真实配置；不默认全参数搜索或固定宽中严三档。参数产生了数值差异，不自动证明差异符合业务含义。形成、延续、结束和尺度参数分别理解；有状态系统更宽的配置可能合并对象，不能只按对象数量推断效果。

结果全空、状态顺序合法或字段齐全，只支持相应有限结论。核心对象从未形成时，不能宣称其生命周期已验证；根据真实输入选择能补足证据的合法数据或配置，确缺材料则保留具体未验证。观察窗口结束时仍存活，也不能直接判成结束逻辑缺失。

明确违反现有合同的问题继续修复。程序忠实运行但首版方法表现可疑时，围绕实际疑点取输入、中间结果和必要对照，取得新信息后决定修订或保留，不在无新证据时无限深化。改变已接受业务含义或主要工程决定时，定向回相应专业责任，不静默改合同。

工程师执行定向调查、对照和修后复验，Pro 必须消费结果，独立审查者复核重要解释与修订。排障途中解决一个技术问题后，仍返回本轮尚未回答的业务问题；结果上传失败只补上传，不重跑昂贵实验。

需要后续综合图审或进一步研究的内容，保留具体结果与问题并限制结论；当前能够查清的明显语义问题不得推给 Owner 或后续看图。如果尚未判断的内容直接影响本阶段最低业务正确性，对应接收继续待证，不能改称可选优化。

<a id="c-close"></a>
## 3.6 完整范围接收：回到原完整目标判断是否结束

管理者对照原完整范围，检查全部约定主体、正式连接、适用运行和业务结果分析是否实际完成；独立审查结论只覆盖真实审查范围，不能由局部通过推得整项完成。

确认的问题已有实质处置和必要复验，运行结果没有无人消费，重要修订已进入实际使用的源码与结果。已实现、已构建、已运行、已解释和已接收分别说明，不能用统一的“完成”互相替代。

本阶段所需的主要业务行为有输入、结果和分析支持。未覆盖市场状态及后续图审／成熟化内容如实列明，不要求证明所有未知场景，也不允许用这些限制掩盖核心行为仍无证据。

一轮回答、一次源码提交、一张工程师工作单和一条短路径结束，不自动结束完整 Goal。达到本 Goal 的完整条件后由获授权管理责任者接收，主控据此结算；未达到则从具体欠项继续。运行因保护／权限／外部材料暂停只限制受影响操作，与局部交回及完整完成分开。

# 4. 问题返回、审查与正常接续

|实际问题|处理与后继|
|---|---|
|授权范围内可确定的语法、局部类型、唯一引用错误|工程师集中修相关同类位置并复编，差分随原回交复核，不重开业务设计或逐 hunk 等放行|
|正式生产者、调用、注册或手写包装尚缺|原 Pro 继续相应主体，工程师执行生成和实际验证；不以 fixture 冒充上游|
|需要事件状态、重要接口或布局／结构修法|工程师调查并集中交事实，Pro 判断和主要编写，修后重跑受影响链|
|异常耗时／内存增长|先保护机器并定位实际阶段；重要修法交 Pro，可信结果与不冲突主体继续|
|生命周期、来源含义、参数作用或关系不合|Pro 对照有效业务／工程处理对应方法及直接消费者，工程师复验，独立审查复核|
|授权内只改运行参数或观察范围|保留基线，按配置机制对照；无源码变化不制造源码提交或无关重编|
|超出现有业务／工程／平台权力|具名回 A／B／窄平台问题／必要 Owner 决定，只暂停真实依赖，不削完整范围|
|确需后续综合图审|保留可继续使用的实际结果、问题与限制；影响当前最低正确性的部分不签接收|

修复后接回原任务尚未回答的业务问题，不让临时排障取代原目的；只重跑、重审实际受影响部分。已定普通步骤写进工作单连续执行，不以每次工作段转换触发重新审批、独立读图或固定新轮次。

管理同时看完整主体和已成源码到真实反馈的转化：不让未跑代码持续积累，也不让一条小链的打磨掩盖其余主体。早期独立审查及时核承重实现与重要结构，结果出现后核实际业务解释；作者自查不替独立审查。finding按依据、影响与当前价值处理，不自动全局阻断。

共享写面遵守现有单写安排。编译／运行中不修改同一源码，后继保留工程师已完成的有效小修；是否隔离按既有现场，不默认新建 worktree。Owner 明确暂停与未知现场仍按 recovery，正常已知写者的未提交施工和一次编译失败不自动成为中断。

# 5. Feature→Action→symbol 的忠实实现

每个承重 Feature 保留一条代码 trace：

```yaml
feature_trace:
  business_feature:
  positive_meaning:
  source_or_objective_facts:
  action_chain:
  host_symbols:
  state_owner:
  method_binding:
  formal_outputs:
  production_entry:
  writer:
  official_readback:
  consumer:
  current_evidence:
```

多个Action可进入同一module，但业务步骤必须有真实可定位symbol；不要求每个Action在当前施工前先配一组测试。简单Action可为纯函数，多个业务问题不能压成一个大reducer。方法路线不由执笔者决定，Pro编写普通Feature仍保留其完整任务和普通表达。

# 6. 最低充分实现的二次核对

Mission B已经给出realization decision。Mission C核对当前repo能否忠实承载，不自行重新裁业务。

## 降级到更简单形态

只有当：

```text
业务语义完全保持；
没有独立 state owner；
没有独立 occurrence／history；
没有多 Action 拓扑；
consumer commitment不变；
Mission B 的复杂形态只是错误 repo 假设。
```

才可形成 RepoFact delta 并请求 B 重编，不能静默简化。

## 升级到更复杂形态

发现：

```text
同一大函数里有多个独立Action；
多个owner需要read-old统一commit；
反馈／采样／并行关系不能由当前形态表达；
方法需要独立版本和失败可见性；
公共product需要独立writer／history。
```

先判断RepoFact遗漏、工程缺口或A合同缺口；不得自行创造新owner、Book或平台。

# 7. bounded-state 的忠实实现

从工程包读取：

```text
business lookback；start/end anchor；eligible material；
current sufficient state；working summary；formal history；
eviction；rebuild；replay/correction；growth invariant。
```

物理分开：

```text
ACTIVE_RUNTIME_STATE：未来判断仍需的活跃状态。
FORMAL_DURABLE_HISTORY：业务必须保留的append-only历史。
REBUILDABLE_OR_DIAGNOSTIC_MATERIAL：可重建、切片或外置，不能永远常驻。
```

Codex测量并定位增长，Pro判断及尽量写源码修正，有具体理由再委派。等价不自动授Codex改Map/索引权；既有平台继续用，不把存储转换/编码解码列成默认任务，不静默改变回看、历史、scope、频率和对象义务。

# 8. current／provisional method 的有效激活

不能只有一个RulePack/CFIS文件，须核：

```text
method id/version由正式配置或输入进入；
参数identity与业务合同一致；host加载预期asset；
输入来自正确business cut；knownness/failure不当0；
方法输出由外层Action消费；deterministic envelope执行；
方法不私取commit资格；版本进入必要正式product/history；
适用的定向变化或实际结果能证明参数生效。
```

参数实际进入计算之后，还应根据真实结果检查其作用是否符合业务含义。必要参数对照属于本阶段业务检查，不等于最终调优。

对照在现有方法允许范围和运行授权内进行，保留原配置和结果，说明调整目的。改变参数语义、方法或已接受业务承诺时返回相应专业责任；禁止静默改值追求非空，再将新结果冒称原配置正确。

不要求全参数矩阵。对形成、延续、结束或尺度有不同作用的参数，按实际作用解释，不能只比较结果数量或数值大小。核心方法 SOURCE_BLOCKED 或确需 Owner 决定时不以 fallback 制造正式结果。

# 9. production／writer／readback 主链

每个业务结果的最低诚实路径：

```text
真实或正式fixture输入
→ production entry → 实际caller → Action/state/method
→ formal occurrence/current → writer firing
→ store/transport → official readback → consumer-readable result。
```

fixture只证明其范围，真实数据资格必须来自真实输入。局部测试绕过production root只能证明局部；writer不可达、ADT未导出、读取吞错返回空表，都不能称业务空或正式成功。给实际输入和正式可读结果，形式以解释对象／过程／关系方便为准，不取消正式接口。按§3.5解释业务、参数差异和空值；技术排障后接回原问题，不只交行数／退出码。

# 10. 四类实施再判断点

## 10.1 比例再判断

触发：基础设施明显多于主体；简单Feature引出异常多Book/processor/schema；工作集或历史随总时间无界增长；为过Harness写大量周边而主链不动。

判断复杂度是否与业务跨度相称、是否可在保语义下更简单、是否隐藏了业务Action、是否需B重编。不是按行数或分钟裁决，不另增审批表。

## 10.2 主链再判断

触发：连续工作未推进production/readback；proof多而核心无symbol；反复修测试壳/fixture/manifest；本批不再对应可观察业务结果。

立即停止无必要测试和加厚，回最近未闭合的Feature→Action→symbol→product链，安排原责任者完成实际未完或具体接通问题。不要仅记录注意轻重缓急；必要时调整工作批，不缩完整scope。已确认错误仍处理，不以早期运行之名跳过安全限制。

## 10.3 权力再判断

触发：想改Feature/scope/owner/time/history、method/RulePack问题、公共产品、跨仓责任或平台，或为性能删业务。

返回B RepoFact/recompile、A Local Contract/MapRevision、窄平台问题或Owner决定；暂停受影响路径，继续不受影响可逆工作。

## 10.4 完成再判断

准备报checkpoint/完成，或因某层测试绿、文件/writer存在而作完成主张时，对账：完整scope、Goal、Feature trace、方法激活、状态历史、production/writer/readback/consumer、未执行proof、具体blocker和下游可用范围。

局部PASS不冒充完整完成。早期审查不以完整场景/proof阻挡首次真实运行；完整接收仍需当前目标的必要实际证据，不将后移项目签成已通过。

完整接收按§3.6，核主要业务行为正面依据、重要问题处置与复验。局部工作单通过、运行暂停和完整Goal完成分开，后续图审不掩盖当前能查清的问题。

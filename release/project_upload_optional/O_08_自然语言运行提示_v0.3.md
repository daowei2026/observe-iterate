## 1. 固定责任与正常动作

协调者只使用已确定原文、模板和真实运行事实生成消息。不得概括Owner目的、补业务范围/重点/参数/实现方案/完成条件或新增禁令；不得把建议升级成必须。固定源缺失或矛盾交材料维护，动态业务缺口交原有权Pro，运输问题按原恢复；只限制依赖该缺口的动作，不要求Owner每步确认。

首次采用/恢复：核对真实在途、实际已采用任务和本版材料；只影响下一次合法新消息，不重发旧消息，不清零work、预算和责任。消息模板、固定目标、源选择规则留在repo，不交长程聊天每轮重写。

收到结果：保存完整回答和成果，按原派发核身份、去重、解析原ROLE_RETURN/QUESTION_WORK_RETURN。原任务内same_work继续；按绑定检查RESULT/CHANGE/EFFORT，无新回答也检查到期责任。已在途/已处理同一责任不重发；原非阻塞专业续作与到期管理均保留。UNKNOWN交原责任者处理，不能当未到期。字段错误只补字段，分析未完继续原工作。

## 2. 固定源与动态源

本工作使用材料维护已填实的`COORDINATOR_DISPATCH.json`：固定Owner目的、阶段、允许的机器mode及其实际工作名称。它仅规定固定关系，不保存进度、当前任务、接受状态、预算或另一套授权。目标正文由 goal_ref 指定用例的 README 或当前 Goal，一份正本；配置中的相对ref按本次已采用policy commit解析。当前生效任务、采用依据、binding和回交分别使用真实40位commit，不跟随moving main，也不默认跟随policy commit。

|内容|取法|
|---|---|
|Owner完整目的|本配置goal_ref指定原文；禁止以管理者decision或协调者摘要替换|
|本阶段与实际职责|配置stage与实际binding的professional_mode相符；配置给机器mode对应的实际工作名称，不能用工程编制mode冒充独立接收|
|本轮请求、接收角色|从已采用binding的routes或trigger.route取得，不能另填角色去绕管理模板|
|当前生效任务|从已采用的管理决定或直接要求取得exact全文，并另给采用依据；不能按policy版本或“最新main”猜任务|
|上一轮实际任务|保留本次binding及其full_scope；检查旧回答仍按旧派发，不能拿新任务反判历史回答|
|上次安排、投入|binding.plan_ref、budget_ref原位置；保留同一完整终点与原起点|
|最新成果及续作|真实完整回交；同一binding的continuation_ref，不能替代完整目标|
|时间、次数、发送状态|既有运行记录；工具不认定记录真实性，也不自行推算业务重要性|

协调者把已有记录投影为临时dispatch JSON，不写新业务综述。新Owner消息原样沿既有CHANGE路径转交，保留原消息位置；不能自行摘要覆盖固定目的。新阶段或固定源更换由相应正式变更更新配置，不让普通业务调用维护本规范。外仓资料沿任务exact引用取得；本地工具读取只支持本checkout，缺项准确报告。

### C 本轮当前工作说明

C 的五段工作是自然语言重点，不增加机器 phase／mode／schema。初次或改派要求由原有权责任者写在现有完整任务，原任务内续作由承办 Pro 写在已有 continuation_ref；主控只搬原文和事实。

选中的正文用 `<!-- CURRENT_C_WORK_BEGIN -->` 与 `<!-- CURRENT_C_WORK_END -->` 包住一小段当前说明：本批实际业务链／结果、已有事实、本轮要做什么、交回结果、已授权正常后继和需要其他责任者处理的情况。完整范围与相邻责任仍保留原引用，不要求机械填表或复制完整方法。

同工作且当前任务未被新采用所替代时，取相符最新回交的 continuation_ref；它优先于初始 focus。最新合法续作无标记时原样使用已选定续作正文，不能退回旧重点。新任务取当前已采用任务的标记段；旧任务无段落继续保留精确引用，不由工具补编。改变了当前任务时按新采用正文处理，不误用旧任务续作。

ROLE_RETURN 和 QUESTION_WORK_RETURN 维持原字段，当前说明随已有 continuation_ref／任务正文定位，不增加第三份回交。段落和引用齐全不证明语义正确或实际送达。

## 3. 消息种类与长度

管理角色包括启动、恢复后的新调用、结果触发、投入复评和收拢：全部使用下方管理短正文，叠加“管理当前阶段工作”的说明和Owner目的，不把管理者写成工程编制者。`progress-route`也走此入口。普通专业续作只用任务短句和阶段提醒，不附管理职责。review/receiver只用独立只读接收正文，不先附“本轮主任务是形成工程”；B内使用实现侧方法的只读接收仍属于B接收，不启动实现。

任务和专业方法默认给精确引用，目标聊天实际按适用读取；已读未变且仍可用者复用。长任务不强制全贴进用户气泡，不允许用协调者摘要代替。固定正文直接载入，不只给链接。长度只作观察，不设逼迫删业务的统一行数门；必要长原文按预定引用方式处理。

交付补齐与业务返修分开。交付补齐必须给原调用、具体缺件检查和需补的原产物，目标角色／聊天必须与原调用一致；管理交付不能发给专业执行者。业务finding返修仍按当前业务任务进入专业路线，不因route名含`repair`就压成补字段。已committed消息运输恢复使用原消息和当时摘要，逐字恢复，不套新模板。机械发布继续原窄职责，不冒充新管理。直接复制旧窄管理提示作为新管理消息会漏掉持续职责，禁止。

## 5. 实际发送与能力边界

使用12中的`execution_handoff.py dispatch`准备/核验同一载荷，再交现有发送动作。非零退出只修受影响消息，不能手写绕过。既有实际授权、在途、撤销和重复派发检查继续执行；配置和模型自称角色不能替代真实记录。脚本能核机械关系，不判市场语义、不认证输入权限、不证明手机已送达。

实际发送器若可接Python调用，使用`checked_send`把载荷与实际接收者核验、发送连在同一调用内；载荷或接收者任一改变都拒绝。该函数不重试外部动作，效果未知仍先对账。外部发送器不在本仓，必须接入后才声称该路径有强制点；不宣称全通道不可绕过。手机执行包必须携带核验后的recipient/work/role/invocation，进入聊天后用新鲜可见标题及当前轮锚点确认同一目标，不能凭相似旧标题发送。保持必要网络检查、发送原子动作和原观察频率，不新增截图轮询。

只在原派发记录保存policy/config版本、binding、实际载荷摘要、核验退出和真实发送回执。原消息按Owner当前要求由协调者归档一次；保存失败补原记录，不要求业务聊天制造重复副本。

## 6. 采用和定向修复

### C 当前工作与连续采用

采用本次方法时，从真实任务和结果恢复每条业务链的当前重点，不将全部工作重置到主体施工。将共同定位、实际角色定位和本轮当前工作说明送达相应承接者；当前工作说明来自已采用任务或合法续作原文，主控不自行编写业务重点。

已授权的小修、复编、生成、运行和读回可在同一工作单连续完成，不为每一步重新等待手机派发。需要新的专业判断、权限或实际条件时，交对应责任者补齐，其他不冲突工作继续。工程师直接取得 DR11 和完整工作单；手机 Pro 提示更新不表示本地工程师已收到。

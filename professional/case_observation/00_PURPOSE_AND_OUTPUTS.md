# 多品种差异用例研究：目标、产出与边界

## 1. 最外层意图

让 AI 逐渐能够像投资者一样观察多个品种，研究如何依据此前信息，提前区分哪些品种的后续运动可能相对较好、哪些可能较差。事后识别差异和回看历史是为这一目的服务的；不能以已经发生的路径描述替代辨别依据与逻辑的研究。

当前从偏单边走式的品种选择角度开始，例如持续推进与反复回吐、小尺度反复是否破坏主方向、成员先强后弱等。这些是帮助理解意图的例子，不是固定分类、必选题目或预先指定赢家。

U2/U3 为这一业务范围提供已有抽象、词汇和设计参考，不是所有观察必须依次走完的处理流水线。当前目标不是验收完整 U2/U3，也不是直接形成交易指令、盈利策略或普遍预测结论。

## 2. 本批范围

一次研究 **3–5 个有差别的用例**，每例从开始就是多个品种共同观察。优先选择在相近或可合理对照的市场情境中有明显好坏分化的位置，而不是先选单品种赢家再补陪衬。

“有差别”意味着本批能给 Owner 多一些实际观察信息；不能把同一段行情稍微移动边界就凑成多例。不要求先建立分类学、每类配额、统一评分或用例间依赖关系。几个都好或几个都差不是本批主要研究对象，暂不扩成另一套验证工程。

数据 **必须通过 aidata 的正式接口及交付取得**。起步用完整可用历史范围的多品种 1d 数据找位置；选中用例后提供 1d 概览与各例 30min 大尺度图及对应数据。实际品种、历史范围、数据上下文在真实任务与调用中明确；不得把讨论中的示例日期或旧 ZIP 自动当作本批输入。

## 3. 产出一：具体多品种差异用例

每例须交出以下能被下一步直接使用的实物内容，不以“已扫描”“已发现”代替：

| 内容 | 要回答的问题 |
| --- | --- |
| 位置与对象 | 具体品种、主要差异时段、必要的关键日期/位置在哪里？ |
| 对照事实 | 每个品种怎样运动，彼此共同点和差别是什么，差别怎样发展？ |
| 业务价值 | 为什么这一差别值得从品种选择、有利/不利条件角度研究？不能只列最终涨跌幅。 |
| 图数定位 | 用例 ID、aidata run/node、数据文件和统一平台页面内的图标题/位置怎样对应？ |
| 研究问题 | 希望向此前追问哪一项具体差异？哪些只是事后已知结果？ |

用例的核心差异区间、展示的前后留量范围、实际回看的信息范围分别记录。三者不必相同，也不由统一固定长度代替。

产出一成立，不意味着已经证明当时应当选择某品种；它只是准确交出了值得研究的市场对照。

## 4. 产出二：该例的提前辨别逻辑研究

从投资者视角自主研究与该例有关的此前信息，尝试形成一个**基本完整、合理、可在图上核对的辨别故事**，回答如何在所判断的后续结果尚未知时，对各品种后续运动的好坏作出有依据的不同倾向判断。暂不要求讲得很细或形成可执行算法，但不能只交零散观察、好坏标签、历史路径复述或限制声明。

这里规定成果质量，不预设某种解释必然成立，也不指定研究角度、指标、阈值、参照位置、统一时点、回看长度或固定步骤。可以看更早历史、不同运动阶段、品种关系和确有必要的其他尺度；需要扩展正式数据时仍通过 aidata。

每例的研究正文须交出：

| 内容 | 具体要求 |
| --- | --- |
| 回看选择 | 实际看了哪些位置、品种、尺度与信息，为何看这些；范围选择可以在研究中修订。 |
| 基本完整的辨别故事 | 连贯讲清本例要辨别的后续好坏是什么、此前哪些事实构成依据、怎样支持不同判断，以及判断的适用条件和可能改变判断的情况；这些是内容要求，不是固定叙事模板或指定市场模式。 |
| 合理性与检验 | 事实与推断能对应，推理没有以结果证明结果；说明实际考虑过的支持、疑问、反证、竞争解释及后续检验怎样影响原判断，不为凑完整故事补写无依据的原因。 |
| 提前辨别的含义 | 说明判断针对哪段尚未知的后续表现、使用的信息当时是否可知；不要求给出最早 T 或成功预测，也不能等整段结果已经形成后才把识别结果称为提前辨别。 |
| 图上可核对 | 主要依据及其相互关系在所交图的合适范围和缩放下相对明确，正文能够对应到具体位置；仅靠表格数字或图上难以分辨的细微差异不能冒充清楚可见。非图上直接可见的信息注明来源和作用。 |
| 当前所得与反馈 | 哪些辨别逻辑已形成、哪些仍只是候选、哪些未能成立或仍讲不清楚，对本例比较有什么影响；Owner能直接指出故事中的具体判断或图中位置反馈。 |

认真研究后仍不能区分、只能部分解释或有多个解释，均可以成为诚实成果；须交代实际尝试过的依据、判断及未能成立的原因，不把“没有证明预测有效”作为省略辨别研究的理由，也不能用一句“不确定”代替已经能够继续完成的研究。图形相关、同步或先后本身不证明驱动因果；过去质量好也不自动证明未来风险小。

## 5. 批次交付

按 [02_OWNER_DELIVERY.md](02_OWNER_DELIVERY.md) 提供一个 Owner 入口，含整批 3–5 例摘要、逐例正文、一个真实统一平台图链接及 aidata 实际输入/调用记录。每例的两个产出可以放在同一份正文中，不机械要求两套重复文件。

批次完成不是只找齐位置、只把图画通、只调用成功或填满表格；需要每例都实际完成上述辨别研究，已有故事的完整性、合理性和图上可核对性能够接受检查，不能形成的如实说明实际研究及不足。图数和节点范围阴影按 02/03 核对，技术 PASS 不替代业务接收。无法凑足有价值的 3 例时保留实际成果并说明具体原因，不能虚构、复制近邻窗口凑数或自称整批完成。

这批是 Owner 先一次性查看的范围。交齐后沿既有管理机制接收并等待真实反馈/后继安排，不自行启动无限新批次、分类研究或开发计划。已有授权内的必要修订仍完成，不把等待反馈作为未完成前述工作的理由。

## 6. 外层稳定，内层可迭代

稳定的是本批业务意图、两项产出、3–5 例范围、aidata 必经入口和 Owner 查看方式。找位置的筛选方式、计算辅助、回看跨度、解释角度及正文组织由专业者根据真实材料迭代，不预设固定算法和指标阈值。

发现表达缺口可以记录到本例：缺哪项信息、为何影响解释、已有词汇能否覆盖。当前不要求把每例都做成新 Feature，也不自动启动 Mission A、实现、新模型、完整 U2 依赖改造或跨用例能力认证。确有必要时由有权任务责任者决定后继，保留本例来历与证据。

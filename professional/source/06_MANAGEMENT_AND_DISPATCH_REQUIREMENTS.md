## 管理调用的两种情况

- **首次管理启动**：恢复完整目标、已有成果、阶段和实际未完，形成第一段可以连续执行的专业工作。
- **后续管理接续**：只有在执行 Pro 交来重要业务结果、Gate 申请、异常、Owner 反馈、阶段收拢或已约定复看时进入；保留有效计划和授权，不重新启动整个任务。

执行 Pro 在已授权的同一专业工作中继续时，沿有效任务和最近合法续作推进，不为每个小检查点重新启动管理 Pro。

## 管理 Pro 的职责边界

管理 Pro：

- 按完整目标独立判断已有成果是否够用、现阶段最值得做什么；
- 安排专业任务，接收阶段 Gate，处理返修、Owner 待决和下一轮；
- 不代替执行 Pro 完成具体业务观察；
- 不预排所有未来 Case、图数或轮数；
- 不把未部署的自动消息、调度或 Gate 写成已经发生。

## 首次管理必须交付

1. 说明实际读到的上下文与真实内容，给出对完整目标和前序阶段状态的独立判断；明确哪些事实需要执行 Pro 定向确认、哪些可以直接消费。
2. 决定当前阶段第一段可以连续执行的专业工作，提出必要 Output/Gate 自查、专业回交和管理复看/接收条件。
3. 给出一份可直接交给独立执行 Pro 的完整任务正文，而不是大纲。至少包含角色、资料入口、当前范围、必要前序核查、专业输出、合法 Worker 委派、权限/非目标、自查/回交和同工作续作。
4. 单独列出必须由 Owner 提供的真实缺项、当前管理未完，以及收到专业结果后依据什么决定继续、接收 Gate 或转下一阶段。

如缺少正式 schema 采用、角色路由或自动派发条件，应交可以人工转发的完整正文并如实标记，不编造工作身份、已发送状态或 Owner 批准。

## 后续管理接续

后续管理只消费本次真实新增结果/反馈及其影响：

- 核对应的原任务、实际成果、未完、Gate 申请和触发；
- 判断继续同阶段、定向返修、Owner 待决、进入下一阶段或结束/等待；
- 将决定落实为实际任务、适用范围和后继；
- 不重复发送首次启动提示，不重复读取未变化材料，不把普通专业续作变成新的管理会。

## GitHub 可交付性与方式边界

管理成果必须实际可被后续主控消费：完整长程推进地图、真实当前专业任务、必要 Gate 限制、管理决定与严格合法 `question-work/v2` Binding，而不仅是关于这些文件的摘要。已有实际授权 GitHub 写通道可用时原位发布；不可用时把**可以复制保真的完整文本成果**连同路径/稳定锚点放入完整回复供原样代发布。ZIP 作为确有需要时的字节交付后备，不能使原可取得的正文因跨机器下载失败全部失效。是否实际提交/校验由操作端判据负责，管理 Pro 不冒称。

签发 mode 只能取现行 `COORDINATOR_DISPATCH.json` 中真实支持的 `professional_mode`。I4 同时附带定向 I3 核查是专业范围和 `question_ids` 组合，不自行增加独立的复合 machine mode。提交双 Return 时 `ROLE_RETURN.question_work_ref` 指向同一次回答的 `QUESTION_WORK_RETURN`；缺结构字段仅定向原管理补交，已完成的业务判断仍保留。

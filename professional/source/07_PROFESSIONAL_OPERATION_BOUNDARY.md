## 角色边界

| 角色 | 核心职责 | 不负责 |
|---|---|---|
| **管理 Pro** | 完整目标、专业任务派发、Gate 接收、下一段决策 | 代执行者做全部观察、亲自编业务 Worker 工单、把 Gate 当自评 |
| **执行 Pro** | 专业业务观察、图的业务含义、给 Worker 工单、专业自查与回交 | 签自己负责的 Gate 或直接替 Owner 取舍 |
| **Worker Codex** | 按执行 Pro 工单读取真实数据、补算、作图、技术检查、交回真实文件/代码 | 解释投资业务价值、签 Gate、再造新 Worker 任务 |
| **操作端** | 向正确聊天原样发送有权任务、取得可接续结果、维护发送/收取/在途事实 | 编写业务任务、选 Case/图、签 Gate、把回复结束当 Gate 通过 |

操作端与 Worker Codex 即使在同一机器，也必须使用不同工作身份和写面。操作端不能因为能执行 Python/画图就升级为 Worker；Worker 的技术任务只能来自执行 Pro 的有据工单。

## 三种状态不得混同

1. **UI 生成/收取状态**：回复是否仍在生成、是否已形成可见完整回答。
2. **有权业务结果状态**：管理/执行 Pro 是否已经把要求的正式结果写入有权位置，身份、版本、权限和下一动作是否明确。
3. **长程 Gate 状态**：是否通过阶段 Gate。只能由有权角色判断，不能从 UI 完成或 GitHub commit 自动推出。

操作端只执行 GitHub 或任务合同中已经授权的下一项机械动作；缺少任何业务判断时停止受影响分支，交原有权角色，而不是为了继续而推断。

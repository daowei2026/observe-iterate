# 跨层业务完成全景与更新协议（候选控制设计 V0.1）

> **位置**：`control/`。本文件是 L0/L1/L2、Gate 和补证往返共用的控制面规则候选，不是新的专业 Skill，也不是当前已实现的数据库／程序。
>
> **关联**：[L0 总任务](01_L0_完整业务任务与双向衔接.md)｜[L1-M A～E](02_L1_观察材料准备流程.md)｜[L1-R](03_L1_合理性分析流程.md)｜[L2 I/O](04_L2_节点输入输出登记表.md)｜[Gate](05_三级Gate及后继路由.md)。

## 1. 为什么必须维护全景

每当一项工作取得新结果，必须把它在完整业务任务中的影响反映出来。任何一次正式进度查询都应能从 GitHub 上已核实的事实回答：

- 本轮目标、必答问题和当前完成边界是什么；
- M 的 A～E、R 的阶段／节点分别做到哪里；
- A～E 哪些阶段已形成真实可消费产物，哪些只部分完成、受阻或被返修；
- C1 是否已经明确待展示信息；C2 当前展示预期和唯一预期 HTML 是哪一版；C3 是否已整理出可注入代码；
- D 是否完成真实特征实例和 CAEGraph 仓库调用链的正式集成；是否直接纠正过 B／C，纠正是否有唯一依据和完整记录；
- E 是否只有候选运行事实，还是已由 executor 核图、形成正式取数准入、完成正式取数并通过图数据一致性检查；
- 哪些补证请求在途，返回哪个问题和版本；
- 哪些旧产物因代码、特征实例、位置、展示、定义或运行版本变化而失效；
- 父任务能结束、受阻，还是仍有合法工作可做。

全景由原生阶段产物、真实执行/取数证据、Gate 和业务决定投影生成，不因写了一份全景文档而改变真实完成状态。

## 2. 五级聚合

| 层 | 记录／汇总对象 | 完成或未完成的含义 | 聚合到 |
|---|---|---|---|
| **实际工作实例** | A／C／E 内部步骤、B 当前用法、D 单一集成动作、E 直接运行与取数、R 节点或一次复用 | 对应输入真实可用，输出被核实，返修／阻断／复用依据清楚 | 对应阶段实例 |
| **L1 阶段实例** | M-A、M-B、M-C、M-D、M-E；R 的现有阶段视图 | 本阶段必需产物已满足消费者，或形成被允许的限域结果 | M/R Workflow |
| **L0 两条专业 Workflow** | M 材料准备；R 合理性分析 | 本任务要求的材料／分析覆盖到什么范围 | 问题清单 |
| **业务问题** | `question_id`、材料和分析轮次／版本 | 是否回答到本轮约定深度；支持、反证、未决和不可调是业务结果 | 父业务任务 |
| **父业务任务** | `business_task_id` 和当前有效完成要求 | 必答问题是否满足，是否还有合法必做工作 | `TaskProgressOverview` |

不采用未经定义的“完成百分比”；先记录已完成、在途、受阻、待验和不适用的真实范围。

## 3. M 的 A～E 怎样记录完成

### 3.1 A 完成

至少有：

- 当前特征名称、代码版本、特征实例；
- 输入事件、业务主输出、中间处理结果；
- 各类事件自身发生位置和 occurrence 携带的其他位置；
- 处理关系及代码证据；
- 对 B／C／D 有影响的未确认项已明确。

只有“读过代码”或写出静态处理骨架，不等于 A 完成。

### 3.2 B 完成

普通用例按当前经验规则形成任务指定位置或默认钢铁板块、`2021-01-01` 至 `2022-12-31`；高频用例形成 1d→30m→1m→5s→tick 多尺度位置路径。B 目前是经验性用法，不要求伪造成熟选择理论。

### 3.3 C 完成

C 固定按 C1／C2／C3 记录：

#### C1 完成

- 待展示的输入事件、业务主输出和必要中间处理结果已经列清；
- 展示／不展示理由明确；
- 只带入 A 已确认的事件位置、身份和引用关系，没有自行补造业务语义。

#### C2 完成

- C2A 已直接阅读锁定版本 `CAEGraph使用手册.md` 的相关章节；手册不足时已记录补查的源码；
- C2B 已形成第一版展示预期和第一版可打开 HTML，而不只是文字构想；
- C2C 已从当前 HTML 中识别实际复杂点；
- C2D 每轮都同步更新展示预期、原型代码、复杂点记录和同一份预期 HTML；
- 循环结束时的当前 HTML 是唯一预期 HTML；未解决处已经形成真实能力缺口、替代方式和语义损失。

不存在另一个独立的“固化展示预期”或“最终再生成 HTML”完成项。

#### C3 完成

- 已从 C2 当前原型整理出位置、实例和字段可注入的 CAEGraph 代码；
- 外层真实特征实例和 B 最终位置没有被固化；
- 实例／Feature／数据入口、位置和字段注入合同完整；
- C3 代码与 C2 当前展示预期／当前 HTML 的页面、面板、图元和业务语义一致；
- 若整理代码必须改变展示预期，已经返回 C2D 同步修改，而非在 C3 无痕变化。

文字构想、截图、只有第一版 HTML 但未处理实际复杂点、不可替换的预览绑定，均不等于 C 完成。

### 3.4 D 完成

D 是一个单一集成动作。至少有：

- 锁定版本 CAEGraph／uplot 仓库理解记录，覆盖本次实际使用的导出、配置、布局、绘图、`PlotCtx`、Feature→CDS、数据树及涉及的动态／前端路径；
- 外层真实特征实例和正式数据入口绑定；
- B 位置和 A 真实字段绑定；
- C3 代码到最终代码的集成差异，且没有无痕改变 C2 当前展示预期；
- 可直接交 E 尝试运行的完整 Python CAEGraph 定义／脚本初稿；
- 当前可做的定义级检查和待 E 确认项。

若 D 发现 B／C 缺项或错误：

- 只有修法唯一、有准确依据、不引入新业务选择、不改变 B 位置或 C2 展示语义时，才可直接纠正；
- 直接纠正必须记录来源阶段、原内容、修改后内容、唯一依据、影响和为何不改变业务语义；
- 需要重新选择位置、改变展示预期、存在多个合理方案或拿不准时，必须返回 B／C；
- A 的事件、字段、位置或关系事实不清时，必须返回 A。

没有上游问题处理记录的“顺手改好”视为无痕修改，不能作为 D 完成依据。D 没有内部 Workflow，也不因理解仓库、绑定实例、绑定位置和形成脚本几个内容而拆成 D1～D8。

### 3.5 E 完成

新版 E 由同一 Codex executor 连续执行专业步骤与真实操作，其完成依据是：

1. **E1** 建立最小执行与核图基准；
2. 真实运行 D，并在授权范围内完成必要诊断、修复及记录，保留日志、diff 与有效运行引用；
3. **E2** 对候选结果与问题性质作出判断，需改变专业上游时正确回流；
4. **E3** 与 D 核对最终脚本、与 C2 当前预期及 HTML 核对真实图，形成明确的图接受记录；
5. 图接受后，**E4** 才冻结正式取数范围、脚本、HTML、运行与实例；
6. 直接导出绑定上述接受基准的正式数据，保留文件、图层、阶段和行数映射；
7. **E5** 核对图层、数据源、字段、对象、时间、数据阶段和必要缺失/转换；
8. **E6** 形成可交下游的交付及实际限制。

默认没有独立 W1/W2 工单。仅有 HTML、调试表、提前导出数据或缺 E5 核对，都不能记 DATA_READY。历史 Worker 路径按原 Run 采用版本解释，不回写既有事实。

## 4. R 和父任务完成

- R 的完成仍依据合理性分析 Skill、冻结预期、对照、诊断／标定中实际适用的结果和 `G-ANALYSIS-DELIVERY`。
- 可信反证、不可调和有界未决在完成合同允许时可以是合格终点；不强制所有问题走完 R0～R5。
- 父任务完成由 L0 H3 依据当前必答问题、材料、分析和结束条件判断。必需问题未解决且无合法动作时是具名停止／受阻，不是完成。

## 5. 必须刷新全景的事件

| 触发事件 | 全景更新 |
|---|---|
| 任务初始化／恢复 | 建立父任务、问题、M A～E 和 R 当前视图；未知边界显式保留 |
| A／B 阶段产物提交并核实 | 更新阶段完成、可消费后继和未确认项 |
| C1 提交或修订 | 更新待展示信息范围；判断哪些 C2 产物需要重做 |
| C2 第一版 HTML、复杂点轮次或当前 HTML 更新 | 记录当前展示预期、当前 HTML、循环轮次和能力缺口；旧版本留历史 |
| C3 可注入代码提交 | 记录注入合同以及与 C2 当前预期／HTML 的一致性；若改变展示语义则返回 C2 |
| D 单一集成动作提交 | 记录仓库理解、正式实例／位置／字段绑定、上游纠正或退回记录、完整定义及检查 |
| E1 基准形成 | 记录当前 D/C2、运行环境与核图基准及授权 |
| E 真实运行、修复与日志 | 更新执行事实和效果；运行成功不等于最终图已接受 |
| E2 返回 B／C／D | 只将受影响阶段置为返修／失效，保留其他有效产物；旧 E1/运行基准按版本失效 |
| E3 最终图核对完成 | 记录接受／限域接受／返修；只有接受后才可形成 E4 正式取数准入 |
| E4 正式取数准入形成或失效 | 记录准入版本、绑定对象和失效条件 |
| E4 后直接正式取数 | 记录数据文件、必要清单、映射和结果；文件存在不等于 E 已完成 |
| E5 图数据一致性检查完成 | 更新 E、M 和可交 R 的材料范围 |
| M→R 交接 | M 的交接事实与 R 待消费输入同时更新；不替 R 选探索／正式分支 |
| R→M 补证及返回 | 记录原问题、版本、补证工作和各种结果；只解锁相关范围 |
| 代码／实例／位置／展示／定义／运行版本变化 | 旧结果留历史，重算受影响的 A～E；不全盘清零 |
| Gate 通过、未过或限域接受 | 更新保留成果、阻断、返修目标和解除条件 |
| 中断、超时、效果未知 | 标记 Codex E 的具体执行/取数动作 `EFFECT_UNKNOWN`，先对账；独立合法工作继续 |
| H3 结案或有据停止 | 固化最终问题结果、材料和未决后继 |

## 6. 依赖失效传播

A～E 的依赖为：

```text
A → B
A → C1 → C2 → C3
外层输入 + A + B + C1/C2/C3 + CAEGraph仓库版本 → D
D + C2当前展示预期/HTML + 特征实例 + 环境/授权 → E1
E1 → 真实运行/修复 → E2 → E3核图接受
E3最终图接受记录 → E4 → 正式数据导出 → E5 → E6
```

因此：

- A 的事件／字段／位置语义变化，可能使 B、C、D、E 失效；
- B 位置变化只直接影响 D 和后续 E，不使 C 自动失效；
- C1 范围变化影响 C2、C3、D 和 E；
- C2 展示预期或 HTML 变化影响 C3、D 和 E，不使 B 自动失效；
- C3 注入接口变化影响 D 和 E；若只是代码整理且证明不改 C2 语义，C2 仍有效；
- 外层特征实例或 CAEGraph 仓库版本变化影响 D 和 E；
- D 的确定性上游纠正若后续被 B／C 修订替代，旧 D 和 E 失效；
- D 绑定变化使旧 E1、候选运行、E3 图接受、E4 准入和正式数据失效；
- E 运行的确定性 patch 若不改变语义，只更新 E；若改变位置、展示或绑定，必须先回 B／C／D 接受；
- 最终脚本、HTML、运行或 E4 准入变化使旧正式数据失效；
- 只是导出错误且准入不变时可由同一 Codex E 定向重试，不使 A～D 自动失效。

失效必须记录触发版本、受影响产物和重新验证条件；旧产物保留历史，不无痕覆盖。

## 8. 交付标签在全景中的含义

| 标签 | 全景解释 |
|---|---|
| `PLAN_READY` | A～D 已形成可执行方案，E 尚未完成真实运行、专业核图、正式取数和一致性判断 |
| `DATA_READY` | 最终图已由 E 接受，正式图数据和 E5 一致性检查均完成，材料可按声明范围交 R |
| `PARTIAL_WITH_LIMITS` | 只有部分位置／图层／数据完成，限制和消费者范围明确 |
| `BLOCKED` | 核心图或数据无法取得，原因、受影响范围和解除条件明确 |

`DATA_READY` 只表示材料准备质量，不表示特征业务合理。

## 9. 与长程 C/D/W 的关系

- 专业阶段、内部 Workflow 和字段级产物决定“应该完成什么”；
- 专业委派 D 决定本项 Skill 的身份与专业范围；Codex executor 直接操作仍须核 Owner/D 授权与工作区；
- 材料准备阶段 D 与长程专业委派 D 只是字母重合，必须按上下文区分；
- D 阶段不派 Worker；新版 E executor 直接运行及正式取数，不因没有 W 而缺少专业完成依据；
- E 的运行/取数操作不替代 E2/E3/E4/E5 专业判断；旧 W1/W2 仅适用历史采用版本；
- 执行线程发送成功、提交文件、专业阶段被接受、业务现象得到支持／反证、父任务完成是不同事实；
- E 形成完整专业结果后通过 V2 Executor Return 回原 manager；主控不能仅凭命令成功宣布完成。

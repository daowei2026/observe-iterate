# 跨层业务完成全景与更新协议（候选控制设计 V0.1）

> **位置**：`control/`。本文件是 L0/L1/L2、Gate 和补证往返共用的控制面规则候选，不是新的专业 Skill，也不是当前已实现的数据库／程序。
>
> **关联**：[L0 总任务](01_L0_完整业务任务与双向衔接.md)｜[L1-M A～E](02_L1_观察材料准备流程.md)｜[L1-R](03_L1_合理性分析流程.md)｜[L2 I/O](04_L2_节点输入输出登记表.md)｜[Gate](05_三级Gate及后继路由.md)。

## 1. 为什么必须维护全景

每当一项工作取得新结果，必须把它在完整业务任务中的影响反映出来。任何一次正式进度查询都应能从 GitHub 上已核实的事实回答：

- 本轮目标、必答问题和当前完成边界是什么；
- M 的 A～E、R 的阶段／节点分别做到哪里；
- A～E 哪些阶段已形成真实可消费产物，哪些只部分完成、受阻或被返修；
- C 是否仅形成预览绑定，D 是否已完成真实特征实例和 CAEGraph 仓库调用链的正式集成；
- E 是否只是 W1 运行，还是已经由 executor 核图、形成正式取数准入、完成 W2 正式取数并通过图数据一致性检查；
- 哪些补证请求在途，返回哪个问题和版本；
- 哪些旧产物因代码、特征实例、位置、展示或定义版本变化而失效；
- 父任务能结束、受阻，还是仍有合法工作可做。

全景由原生阶段产物、W1／W2 工单及回报、Gate 和业务决定投影生成，不因写了一份全景文档而改变真实完成状态。

## 2. 五级聚合

| 层 | 记录／汇总对象 | 完成或未完成的含义 | 聚合到 |
|---|---|---|---|
| **实际工作实例** | A／C／E 内部步骤、B 当前用法、D 单一集成动作、W1／W2、R 节点或一次复用 | 对应输入真实可用，输出被核实，返修／阻断／复用依据清楚 | 对应阶段实例 |
| **L1 阶段实例** | M-A、M-B、M-C、M-D、M-E；R 的现有阶段视图 | 本阶段必需产物已满足消费者，或形成被允许的限域结果 | M/R Workflow |
| **L0 两条专业 Workflow** | M 材料准备；R 合理性分析 | 本任务要求的材料／分析覆盖到什么范围 | 问题清单 |
| **业务问题** | `question_id`、材料和分析轮次／版本 | 是否回答到本轮约定深度；支持、反证、未决和不可调是业务结果 | 父业务任务 |
| **父业务任务** | `business_task_id` 和当前有效完成要求 | 必答问题是否满足，是否还有合法必做工作 | `TaskProgressOverview` |

不采用未经定义的“完成百分比”；先记录已完成、在途、受阻、待验和不适用的真实范围。

## 3. M 的 A～E 怎样记录完成

### 3.1 A 完成

至少有：

- 当前特征名称、代码版本、特征实例；
- 输入事件、业务主输出、中间处理结果；
- 各类事件自身发生位置和携带位置；
- 处理关系及代码证据；
- 对 B/C/D 有影响的未确认项已明确。

只有“读过代码”或写出静态处理骨架，不等于 A 完成。

### 3.2 B 完成

普通用例按当前经验规则形成任务指定位置或默认钢铁板块、`2021-01-01` 至 `2022-12-31`；高频用例形成 1d→30m→1m→5s→tick 多尺度位置路径。B 目前是经验性用法，不要求伪造成熟选择理论。

### 3.3 C 完成

至少有：

- 待展示信息和展示预期；
- 复杂点处理记录；
- 位置与实例可注入的 CAEGraph 展示代码；
- 特征实例／Feature／数据入口的注入合同；
- 可打开的预期展示 HTML；
- 真实能力缺口。

C 可以只读使用外层实例或临时生成预览 HTML，但必须证明正式代码未固化最终实例。文字构想、截图或不可替换的预览绑定不算 C 完成。

### 3.4 D 完成

D 是一个单一集成动作。至少有：

- 锁定版本 CAEGraph／uplot 仓库理解记录，覆盖本次实际使用的导出、配置、布局、绘图、`PlotCtx`、Feature→CDS、数据树及涉及的动态／前端路径；
- 外层真实特征实例和正式数据入口绑定；
- B 位置和 A 真实字段绑定；
- C 代码到最终代码的集成差异，且没有无痕改变展示语义；
- 可直接交 E 尝试运行的完整 Python CAEGraph 定义／脚本初稿；
- 当前可做的定义级检查和待 E 确认项。

D 没有内部 Workflow，不因理解仓库、绑定实例、绑定位置和形成脚本几个内容而拆成 D1～D8。只有伪码、片段、预览实例或“运行时再决定”的核心绑定不算完成。

### 3.5 E 完成

E 的专业完成必须同时满足：

1. executor 已建立执行与核图基准并签发 W1；
2. W1 在真实环境完成运行，patch、日志和未决问题已回 executor；
3. executor 已与 D 核对最终脚本、与 C 展示预期／HTML 核对最终图，并形成明确图接受记录；
4. 只有图被接受后才形成正式取数准入并签发独立 W2；
5. W2 正式数据绑定被接受的脚本、HTML、实例、位置和同一次有效运行；
6. executor 已完成图层、数据源、字段、对象、时间、数据阶段和缺失语义的一致性核对。

只有 W1 运行成功、只有 HTML、只有调试 CDS、提前导出的数据或只有 W2 文件而无专业一致性核对，都不能记 E 完成，也不能记 `DATA_READY`。

## 4. R 和父任务完成

- R 的完成仍依据合理性分析 Skill、冻结预期、对照、诊断／标定中实际适用的结果和 `G-ANALYSIS-DELIVERY`。
- 可信反证、不可调和有界未决在完成合同允许时可以是合格终点；不强制所有问题走完 R0～R5。
- 父任务完成由 L0 H3 依据当前必答问题、材料、分析和结束条件判断。必需问题未解决且无合法动作时是具名停止／受阻，不是完成。

## 5. 必须刷新全景的事件

| 触发事件 | 全景更新 |
|---|---|
| 任务初始化／恢复 | 建立父任务、问题、M A～E 和 R 当前视图；未知边界显式保留 |
| A/B/C 阶段产物提交并核实 | 更新阶段完成、可消费后继和未确认项；C 记录实例注入边界 |
| D 单一集成动作提交 | 记录 CAEGraph 仓库理解、正式实例／位置／字段绑定、完整定义及检查；不按虚构 D 子步骤汇总 |
| W1 工单、运行、patch | 更新在途动作和实际效果；派单或 Worker 成功不等于最终图已接受 |
| E 返回 B/C/D | 只将受影响阶段置为返修／失效，保留其他有效产物；旧 W1 基准失效时明确记录 |
| executor 完成 D/C 最终图核对 | 记录图接受／限域接受／返修；只有接受后才可形成正式取数准入 |
| W2 工单及正式数据回报 | 记录取数准入、数据文件、manifest、映射和结果；W2 文件存在不等于 E 已完成 |
| executor 完成图数据一致性检查 | 更新 E、M 和可交 R 的材料范围 |
| M→R 交接 | M 的交接事实与 R 待消费输入同时更新；不替 R 选探索／正式分支 |
| R→M 补证及返回 | 记录原问题、版本、补证工作和各种结果；只解锁相关范围 |
| 代码／实例／位置／展示／定义版本变化 | 旧结果留历史，重算受影响的 A～E；不全盘清零 |
| Gate 通过、未过或限域接受 | 更新保留成果、阻断、返修目标和解除条件 |
| 中断、超时、效果未知 | 标记具体 W1／W2 `EFFECT_UNKNOWN`，先对账；独立合法工作继续 |
| H3 结案或有据停止 | 固化最终问题结果、材料和未决后继 |

## 6. 依赖失效传播

A～E 的依赖为：

```text
A → B
A → C
外层输入 + A + B + C + CAEGraph仓库版本 → D
D + C展示预期 + 特征实例 + 环境/授权 → E-W1
E最终图接受记录 → E-W2
E-W2回报 → E图数据一致性判断
```

因此：

- A 的事件／字段／位置语义变化，可能使 B、C、D、E 失效；
- B 位置变化只直接影响 D 和后续 W1／W2，不使 C 自动失效；
- C 展示或实例注入接口变化影响 D 和 E，不使 B 自动失效；
- 外层特征实例或 CAEGraph 仓库版本变化影响 D、W1 和 W2；
- D 绑定变化使旧 W1 基准和后续图接受／取数准入失效；
- W1 的确定性 patch 若不改变语义，只更新 E；若改变位置、展示或绑定，必须先回 B/C/D 接受；
- 最终脚本、HTML、运行或取数准入变化使旧 W2 失效；
- W2 只是导出错误且准入不变时可定向重试，不使 A～D 自动失效。

失效必须记录触发版本、受影响产物和重新验证条件；旧产物保留历史，不无痕覆盖。

## 7. 工作实例和阶段状态

建议最少区分：

```text
NOT_STARTED
IN_PROGRESS
CANDIDATE_SUBMITTED
ACCEPTED
PARTIAL_ACCEPTED
RETURNED_FOR_REPAIR
BLOCKED
NOT_APPLICABLE
SUPERSEDED
EFFECT_UNKNOWN
```

这些是控制面投影状态，不替代 Skill 的业务状态和交付标签。

阶段可被消费者使用时，至少记录：

```yaml
stage_instance_id:

input_refs: []
input_versions: {}
output_refs: []
accepted_scope:
limitations: []
blocked_scope: []
continuation_targets: []

```


## 8. 交付标签在全景中的含义

| 标签 | 全景解释 |
|---|---|
| `PLAN_READY` | A～D 已形成可执行方案，E 尚未完成 W1、核图、W2 正式取数和一致性判断 |
| `DATA_READY` | 最终图已由 E 接受，W2 正式图数据和一致性检查均完成，材料可按声明范围交 R |
| `PARTIAL_WITH_LIMITS` | 只有部分位置／图层／数据完成，限制和消费者范围明确 |
| `BLOCKED` | 核心图或数据无法取得，原因、受影响范围和解除条件明确 |

`DATA_READY` 只表示材料准备质量，不表示特征业务合理。

## 9. 与长程 C/D/W 的关系

- 专业阶段、内部 Workflow 和字段级产物决定“应该完成什么”；
- 专业委派 D 与 Worker 工单 W 决定“这次由谁在什么权限下完成哪部分”；
- 材料准备阶段 D 与长程专业委派 D 只是字母重合，必须按上下文区分；
- D 阶段不派 Worker；E executor 分别签 W1、W2；
- Worker 运输成功、提交文件、专业阶段被接受、业务现象得到支持／反证、父任务完成是不同事实；
- E 的 W1／W2 回报必须先由 executor 作专业判断，不能直接跳到 manager 或父任务完成。

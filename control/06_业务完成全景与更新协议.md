# 跨层业务完成全景与更新协议（候选控制设计 V0.1）

> **位置**：`control/`，是 L0/L1/L2、Gate 和补证往返共用的控制面规则候选，不是新的专业 Skill，也不是当前已实现的数据库/程序。
> **来源**：【S-M】观察材料准备 Skill 的四种交付标签、实际取数和交接要求；【S-R】合理性分析四 Skill 的原生结果、版本和循环；【P】此前控制面落地计划的 Domain/Run/WorkItem/Action 状态、QuestionCompletionRecord、GitHub 权威提交；【N】本文件提出的**任务全景投影、逐层汇总与更新触发**。新增部分需确认后才转为强制规则。
> **关联**：[L0 总任务](01_L0_完整业务任务与双向衔接.md)｜[L1 材料准备](02_L1_观察材料准备流程.md)｜[L1 合理性分析](03_L1_合理性分析流程.md)｜[L2 节点](04_L2_节点输入输出登记表.md)｜[Gate](05_三级Gate及后继路由.md)；缺环和测试归入 `../review/`。

## 1. 为什么必须维护这个全景

当前三层流程已经明确“一个工作节点产出什么”“下一节点如何消费”，但还缺一项贯穿全过程的工作：**每当一项工作取得有意义的新结果，必须把它在全业务任务中的完成情况反映出来**。否则各处虽有回交文件，却仍要依赖聊天上下文才能回答：

- 本轮总体目标和必答问题是什么、目前各自已经回答到什么程度？
- M（观察材料准备）与 R（合理性分析）分别做到哪里？有没有多个分支同时开展？
- S0～S5、R0～R5 的哪些**具体范围/轮次**已经完成、哪些待办、哪些受阻？不能只看“当前 S3”。
- M01～M09、R01～R13 中哪些**实际工作实例**有已核实产物、哪些只提交了候选、哪些失败或因不适用而跳过？
- Gate 通过了哪些范围？未过的 Gate 缺哪项条件，保留了哪些此前成果，要返回哪项工作？
- 哪些补证请求在途、回原哪个分析问题/轮次？哪些证据因上游版本变化已不再适用于当前判断？
- 哪些工作可以合法继续，哪些必须等待新的事实/判断，整个任务可以结束还是只能具名停止？

**要求**：任意一次正式进度查询，都能够从 GitHub 上已核实的任务与业务结果重建这些答案，不要求管理角色重新阅读所有 R/W 回交或靠记忆维护“最新全景”。

## 2. 全景的五级聚合，不能混成一个百分比

| 层 | 记录/汇总对象 | 完成或未完成的含义 | 聚合到 |
|---|---|---|---|
| **实际工作实例** | `work_item_id`、节点 `node_id`（M01～M09、R01～R13）及执行/尝试 ID | 已核实结果、待验、阻断、需返修、必要时合法跳过；原生产物与证据精确引用 | 对应的 S/R 阶段实例 |
| **L1 阶段实例** | `stage_view`（S0～S5/R0～R5）＋ `stage_instance_id`、适用范围/问题/轮次 | 本次范围内规定的必需工作是否满足；适用的 Gate 是否获得有效结果；缺项及后继是否已明确 | M/R Workflow 汇总 |
| **L0 两条业务 Workflow** | M 材料准备；R 合理性分析（可以有多轮及定向补证） | 此任务要求的材料或分析交付覆盖到什么范围、哪些问题可以消费、哪些仍在进行 | 总任务/问题清单 |
| **业务问题** | `question_id`＋分析轮次、预期与材料版本 | 是否回答到本轮已明确的深度；支持/反证/有界未决/不可调等是**业务结果**而非 Gate 成败 | 父业务任务 |
| **父业务任务** | `business_task_id`、当前有效完成要求 | 本轮必答问题是否满足完成合同，是否还有合法必做工作；完成、受阻、停止与后继提议必须区别 | `TaskProgressOverview` 总视图 |

上表是**从事实记录生成的业务全景**，不是第五套互相独立的权威状态。原有的 Skill 结果、工作项、Gate、业务决定和 GitHub 回执仍是事实来源；全景只聚合/引用它们，不凭“生成一份全景 Markdown”改变完成状态。

特别注意：
1. **节点类型 ≠ 节点执行实例**：M06 可一次运行产出多项材料；同一逻辑节点亦可分不同问题/补证请求执行多轮。不能因出现一条 M06 结果就宣称所有 M06 工作均完成。
2. **阶段不是固定模型调用次数**：S0～S5/R0～R5 是管理视图，不要求每阶段独立派发一次 Pro，也不能仅因一个 R 轮结束就宣布所有阶段完成。
3. **Gate 结果、业务发现、执行回执分开**：Worker/Pro 运输成功、工作结果提交、专业 Gate 通过、业务现象得到反证、父任务完成，是五种不同事实。
4. **部分交付不缩小任务要求**：某一问题已可继续分析，不能把另一必需材料缺失从全景中抹掉。
5. **跳过与未做必须区分**：已认可的等价结果/条件性不适用可以登记不需执行及依据，不能用“没有该节点记录”推断完成。
6. **不采用未经定义的“完成百分比”**：先呈现有据的已完成/在途/受阻/未决及其范围；若未来需要数量指标，必须先定义不同工作量和条件节点的计算语义。

## 3. 每层什么时候才可以记为完成

### 3.1 L2：节点级

一次工作实例完成至少要有：

- 具体 `question_id / work_item_id / node_id`，必要时还有材料/分析轮次、输入版本与适用范围；
- 该工作合同要求的**真实输出或合法的无产物结论**（如已证实不可得、不适用）及核查引用；
- 当前工作必需的验证已满足，若属于 Gate 的正式接受范围须附有效 Gate/决定引用；
- 明确该结果让哪些后继节点具备输入、哪些只可作受限使用、哪些仍缺证。

**输出文件存在不等于已完成。** 结果仅为候选、前置验证未完成、工作项处于返修、版本失效时，不能记为当前有效完成。不可得调查完成可以记“该调查工作完成”，但**不能把原必需数据要求标为已满足**。

### 3.2 L1：阶段级

一个阶段实例的完成从**本次实际适用的必需工作**汇总，而不是强制所有 Mxx/Rxx 都执行。至少检查：

1. 对应阶段的目标范围和被激活的必要工作项已明确；
2. 这些工作各有合法完成、真实不适用或获认可的等价复用依据；条件节点未触发时不能当作遗漏；
3. 对本阶段真正适用的 Gate 已完成核验；硬检查 UNKNOWN/NOT_RUN 不算通过；
4. 阶段成果能够被声明的下一节点消费，或者已经形成有证据的、被允许的有界交付；
5. 仍受阻且属于本阶段**必需**范围的条件，不得隐藏在阶段“完成”之后。

例如，S3 中 M06 已得到 source/构图数据，但本次必需的视窗最终值 M07 未取得：**不能把这个 S3 范围写成完整完成**；其他不依赖 M07 的材料可以另记为可消费。R2 的对照有充分真实反证时，G-COMPARISON 可以通过：它并非“业务目标失败所以阶段未完成”。

### 3.3 L0：Workflow / 父任务

- **M 完成**：本轮材料要求已实际取得与核验，或依本轮明确完成合同以可接受的限域成果结束；单项材料包被交接不必等于 M 全任务结束。
- **R 完成**：本轮被要求分析的问题达到规定的交付深度，冻结预期和对照/诊断/标定等**实际适用**的结果已被核对；不强制所有 R 阶段均经过。
- **父任务完成**：L0 的 H3 依本轮已明确的必答问题、证据和结束条件判断；可信反证、不可调、受限结论在合同允许时也可能是合格终点。若必需问题仍未解决而没有合法动作，则是“具名停止/受阻”，**不是完成**。

完成范围一开始不必全部已知，但未知项必须留在全景；没有形成必要完成条件时，不能凭已跑完全部已知节点自动结束。

## 4. 哪些事件必须刷新全景；不是只在 Gate PASS 才更新

| 触发事件 | 工作/阶段事实变化 | 对全景的必要影响 |
|---|---|---|
| 任务初始化、既有任务恢复 | 业务目的、已知范围、问题及当前受控版本核实 | 建立或重建父任务与 M/R 两条线的当前视图；未知边界显式保留 |
| 工作项建立、依赖激活、正式派发 | 新的具名工作、依赖、占用及回交预期 | 更新在途/待办与合法后继；**派发不等于完成** |
| **L2 节点有效结果提交并被接受** | 候选→核实→必要 Gate/接收；记录输入、输出、适用范围 | 更新节点实例完成状态和可消费产物；重新判定受影响阶段、问题及父任务 |
| 节点结果部分有效、Gate 未通过、明确不可得 | 指定失败条件、已保留成果、返修节点、阻断和解除条件 | 展示部分成果/待返修/阻断；不能把此前其他有效工作抹掉 |
| **L1 阶段 Gate 通过与阶段完成** | 对应范围的必要工作和 Gate 全部满足 | 记录阶段实例的完成证据及后继；同时刷新 M/R Workflow 和父任务全景 |
| 阶段内工作满足但尚不能正式接受 | 还有待验、独立复核、必要数据缺口 | 阶段为“待验/在途/有条件”，不能仅凭所有候选提交就记已完成 |
| **L0 M→R 交接** | 材料包、真实质量及限制、当前可消费的问题 | M 的交接事实与 R 的待分析输入同时更新；不替 R 预选探索/正式分支 |
| **R→M 补证请求、返回及关闭** | 原问题/轮次挂起、补证工作启动、OBTAINED/PARTIAL/不可得等 | 两条 Workflow 同时可见该请求及其归属；返回时只解锁原问题的相关工作 |
| 新预期版本、新分析轮次、受影响结果失效 | 数据/代码/参数/预期的已登记上游依赖变化 | 旧成果留历史；当前有效完成范围重算，指出须重验的节点/阶段和理由 |
| 中断、超时、动作效果未知、恢复 | 外部动作实际效果可能未明确 | 标出 `EFFECT_UNKNOWN` 的具体动作及阻断范围；先对账，独立合法工作可继续 |
| 问题级结果被接受、H3 结案或有据停止 | `QuestionCompletionRecord` 和总体完成条件得到验证 | 更新父任务最终结果、未决与后继；**停止与成功完成分开** |

**更新粒度**：有新的、被核实的控制事实时刷新其受影响的全景部分；不要求每个子步骤、每条聊天或没有新事实的轮次都生成一个全新 Git commit。对同一事件及同一版本的重复通知，应得到相同的全景结果，不能重复计完成。

## 5. 更新过程：一次事件如何向上汇总

```text
真实工作输出/回交（可能仅候选）
  → 对齐 business_task / question / node / work / stage实例 / round / 输入版本
  → 核实实际结果及必要 Gate/接收；不满足则保留候选与阻断原因
  → 更新本工作实例的最新有效事实
  → 重算受影响阶段：完成条件、缺项、Gate、可消费结果、后继
  → 重算 M/R Workflow：已交付范围、在途工作、局部阻断、往返请求
  → 重算业务问题：本轮目标、已获证据、尚需动作及可否结案
  → 重算父任务：已完成、仍需做、阻断/待判断、完成/停止资格
  → 生成可查询 TaskProgressOverview + 事件/版本/证据引用
```

在实际实现中，**业务事实与其版本/回执须先形成有效受控记录**，全景只能由这些事实派生。可以按同一次受保护 Git 版本提交更新派生视图，或者根据受控事实按需计算；不允许全景文件成为另一份可以随意修改的状态真相。

如果先持久化事件、全景视图暂未刷新，查询时必须能发现 `as_of_control_version` 落后，并重建/标出陈旧，不可把旧全景当最新。GitHub 是本轮唯一持久化来源；身份保护、原子更新、版本比较与幂等仍属于后续工程实现和验收，不能因写了本协议就声称已有此能力。

### 5.1 重要的历史语义

- **已完成历史不删**：S3 曾按 v1 材料包合法交付，R 后来要求新 trace，可以创建 M 的一个**定向补证工作/阶段实例**。旧 S3 v1 交付仍是历史事实，不因此被写成“当时没完成”；父任务当前仍有补证在途。
- **当前有效性可变化**：如果 v1 产物的代码/数据/参数被替换，当前问题的旧对照可能失效，全景显示“历史已接受、当前需重验”，但不改写原验收回执。
- **一次运行多项成果**：一个 M06/CAEGraph 结果可能满足多个 MaterialRequirement；汇总按真实结果与需求映射，不按图元个数或材料条数重复计执行工作。
- **跨阶段复用不重复完成**：R4 标定触发一次 R2 `INSTANCE_REVALIDATION` 对照工作，R2 与 R4 的阶段汇总可分别引用同一验证结果，不得当作两次物理计算。

## 6. 全景至少要展示什么（候选查询/呈现合同）

建议把 `TaskProgressOverview` 视为**只读投影/页面**，它的内容引用已有业务证据，不再次生成新的专业报告：

```yaml
business_task_id: <父业务任务身份>
as_of_control_version: <最近被有效接收的控制版本或Git commit>
goal_and_known_constraints:
  business_goal: <原目标>
  required_questions: [<已经明确的必答问题>]
  completion_definition_status: confirmed | partially_defined | needs_decision
  unresolved_scope_questions: [<尚待明确的范围>]
overall:
  completion: incomplete | complete | stopped_with_unmet_requirements
  reason: <依据本轮合同的判断，非主观百分比>
  next_legal_work_refs: [<已有计划的合法后继>]
  pending_decision_refs: [<无法按现有规则确定后继的控制判断>]
  blockers: [<具名缺项、被阻断的范围、解除条件>]
workflows:
  M:
    active_stage_instances: [<S阶段和补证工作范围>]
    accepted_material_refs: [<材料及可用范围>]
    still_required_materials: [<未满足需求>]
    handoff_refs: [<已交给R的材料>]
  R:
    active_stage_instances: [<R阶段和问题/轮次>]
    accepted_analysis_refs: [<冻结预期、证据对照、诊断/标定>]
    still_required_analysis: [<尚需的合法工作>]
    return_to_material_requests: [<补证请求及状态>]
stages:
  - stage_instance_id: <含 M/R、Sx/Rx、关联问题/轮次/补证范围>
    current_view_status: <从已核实事实推导出的阶段表现>
    accepted_work_refs: [<哪些必要节点已有合格结果>]
    pending_work_refs: [<尚需工作>]
    gate_decision_refs: [<已核实的Gate及适用范围>]
    retained_results_and_limits: [<可复用成果及限制>]
questions:
  - question_id: <当前问题>
    required_depth: <已经确认的深度或待明确>
    current_finding: <支持/反证/未决/不可调等，仅引用原生Skill结果>
    completion_eligible: <依据H3及QuestionCompletionRecord，不根据正负结论猜测>
    missing_or_blocked_work_refs: [<尚需的工作和解除条件>]
    latest_analysis_round_ref: <当前有效轮次>
history_and_recovery:
  latest_event_and_receipt_refs: [<可审计来源>]
  superseded_or_invalidated_refs: [<旧成果、失效原因与受影响范围>]
  effect_unknown_action_refs: [<待对账的真实执行动作>]
```

上面的 `current_view_status` 是为阅读全景而生成的**展示结果**，不是取代此前提议的 `DomainState/RunState/WorkItemState/ActionState` 的新权威枚举。具体机器字段与如何存 GitHub 尚未批准，不在这份业务 Workflow 文档中自行落实 Python 或运行数据库。

### 6.1 最低可读全景：一眼看清四块

| 内容 | 不足以回答的问题 |
|---|---|
| **整体**：本轮目标、是否已达到原完成条件、剩余必须回答的问题 | “最新跑到 R3”不能回答整个任务完成度 |
| **两条线和阶段**：M/R 各阶段当前有效范围、局部完成、在途、需要复验和待定 | “S3 完成”未绑定问题/版本时无法回答 |
| **工作/材料**：已接受的节点/材料/分析成果及各自来源、被保留的有效部分 | “Worker Return 成功”不能证明材料合格 |
| **问题与后继**：关键阻断、必要决策、下一合法动作、等待/恢复条件 | “继续调查”没有具体对象和退出条件，无法驱动后继 |

实际全景展示可以通过 Markdown/JSON 查询视图实现；**本轮只定义需要表达和更新的业务语义，不在此预设每个阶段额外增加一次独立 Pro 轮次或重复汇报。**

## 7. 按真实控制场景走查更新（示意，不代表已经运行）

**场景 A：节点完成 → 阶段完成。**

```text
Q1 需要 BP-07 和 BP-09 对应的材料
→ M06 一次受控取数得到两份材料，均有真实来源和版本
→ 工作项产物核查通过：全景将对应 M06 工作实例记为已核实完成
→ M08/G-MATERIAL 只核实 BP-07，BP-09 仍缺必要时间核对
→ S4：BP-07 范围完成；BP-09 待核；M 全线不能报告“所有材料完成”
→ 补齐 BP-09 的实际时间核验并经相关 Gate 接受
→ 更新 S4 对应范围、M 交付范围及 Q1 可供分析的证据；允许进入相应 L0/R 后继
```

**场景 B：阶段历史完成 → R 补证 → M 重新有工作。**

```text
M 已交付 v1 材料，S5 v1 的交接有合法验收记录
→ R3 诊断需要一条原材料包未包括的中间 trace
→ 产生 REQ-1，绑定原 Q1 / analysis_round_id / origin_work
→ 全景：R/Q1 该证据路径等待；M 出现 REQ-1 定向补证工作；S5 v1 的历史仍保留
→ M 返回 PARTIAL：已取得 trace-1，trace-2 证明当前无法可靠得到
→ 全景：REQ-1 有结案结果；只解锁可用部分；trace-2 对应判断仍未决
→ R 根据原任务完成条件继续有界诊断或有据停止；不得无限重发 REQ-1
```

**场景 C：结果失效与中断恢复。**
